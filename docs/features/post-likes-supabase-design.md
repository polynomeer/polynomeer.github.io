# Supabase Post Likes Design

This document defines a practical `like` feature for individual posts using Supabase from a static Jekyll blog.

## Goal

Add a lightweight per-post like button that:

- shows the current like count
- lets a visitor toggle one like per browser
- works without a custom application server
- stays compatible with static hosting

## Why Supabase

For this repository, Supabase is a good fit because:

- the blog is static and should avoid a dedicated backend
- the public `anon` key is acceptable for browser use when RLS is configured correctly
- a single table plus RLS is enough for a basic like toggle

## Product Decision

This implementation is intentionally simple:

- one like per browser profile, not one like per authenticated user
- browser identity is stored in `localStorage`
- likes are keyed by post path
- the UI is optimistic only after a successful response

This is suitable for a personal blog, not a fraud-resistant voting system.

## Configuration Model

Add a top-level config block:

```yml
likes:
  provider: supabase
  supabase:
    url: https://YOUR_PROJECT.supabase.co
    anon_key: YOUR_PUBLIC_ANON_KEY
    table: post_likes
```

Rules:

- `likes.provider` controls whether the feature renders
- `likes.supabase.url` is the project URL, not the REST path
- `likes.supabase.anon_key` is the public browser-safe anon key
- `likes.supabase.table` defaults to `post_likes`

## Data Model

Use a single table:

```sql
create table public.post_likes (
  id bigint generated by default as identity primary key,
  post_path text not null,
  visitor_id text not null,
  created_at timestamptz not null default now(),
  unique (post_path, visitor_id)
);
```

Recommended index:

```sql
create index post_likes_post_path_idx on public.post_likes (post_path);
```

## RLS Model

Enable Row Level Security:

```sql
alter table public.post_likes enable row level security;
```

Minimal public policies for this blog feature:

```sql
create policy "public can read likes"
on public.post_likes
for select
to anon
using (true);

create policy "public can insert likes"
on public.post_likes
for insert
to anon
with check (true);

create policy "public can delete likes"
on public.post_likes
for delete
to anon
using (true);
```

## Tradeoff

These permissive public policies are simple but not strong protection.

With a static site and no authenticated identity, a determined attacker can still script requests.

That tradeoff is acceptable only if:

- the feature is low-stakes
- counts are informational
- abuse resistance is a future concern, not a current requirement

If abuse becomes a real problem, move to a Supabase Edge Function or another server-side gate.

## UI Placement

Render the like control in the post header metadata row, next to pageviews and read time.

## Client Behavior

On page load:

1. derive the post identifier from `page.url`
2. load or create a stable browser `visitor_id` from `localStorage`
3. request the current like count from Supabase
4. request whether the current browser already liked the post
5. render count and active state

On click:

1. if already liked, delete the `(post_path, visitor_id)` row
2. otherwise insert the row
3. refresh count and liked state

## Failure Handling

When Supabase is not configured or a request fails:

- do not break post rendering
- show the button in a disabled or unavailable state
- log errors only in the browser console

## Verification

Structural verification:

```bash
bundle exec jekyll build --limit_posts 20
```

Functional verification after deployment or local browser load:

1. open a post page
2. confirm the like button renders
3. click once and confirm count increments
4. reload and confirm active state persists for the same browser
5. click again and confirm count decrements

## Future Improvements

- replace public table access with a Supabase Edge Function
- add rate limiting or captcha for abuse reduction
- expose likes in feed cards or search results
- track reaction types instead of a single like
