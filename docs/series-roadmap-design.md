# Series and Roadmap Feature Design

## Goal

This feature adds two structured navigation layers on top of the existing post system:

- `series`: ordered posts that belong to one continuous sequence
- `roadmap`: curated learning paths that group series and standalone posts into a larger track

The design must work with the current Chirpy-based Jekyll structure, avoid breaking existing posts, and support gradual adoption.

## Why This Feature Fits This Repository

This blog already has:

- a large number of posts
- strong category and tag usage
- post-to-post related recommendations
- archive, category, and tag navigation

What it lacks is an explicit reading order for:

- multi-part technical explanations
- beginner-to-advanced learning paths
- grouped long-form content such as backend, database, Spring, interview, and reference tracks

Series and roadmap features solve the "what should I read next?" problem better than tags alone.

## Non-Goals

- Do not migrate all existing posts immediately.
- Do not replace categories, tags, or related-posts.
- Do not require a database or dynamic backend.
- Do not introduce build-time dependencies that conflict with static hosting.

## Design Principles

- Opt-in only: posts without series or roadmap metadata continue to work unchanged.
- Front matter first: use post metadata before creating custom plugins.
- Static generation friendly: all outputs must be generated by Jekyll at build time.
- Gradual rollout: ship post-level UI first, then roadmap pages, then richer recommendation logic.

## Data Model

### Post front matter

Recommended fields:

```yaml
series: "redis-fundamentals"
series_title: "Redis Fundamentals"
series_order: 3
series_description: "Understand Redis from core concepts to operational patterns."
roadmaps:
  - backend-core
  - redis-engineer
roadmap_stage: "intermediate"
roadmap_topics:
  - redis
  - caching
  - consistency
```

Rules:

- `series`: stable machine-readable identifier
- `series_title`: optional human-readable override
- `series_order`: numeric ordering inside the series
- `series_description`: optional summary for display blocks
- `roadmaps`: zero or more roadmap ids
- `roadmap_stage`: optional label such as `beginner`, `intermediate`, `advanced`
- `roadmap_topics`: optional list for future recommendation or filtering logic

### Roadmap data file

Store roadmap definitions in `_data/roadmaps.yml`.

Recommended shape:

```yaml
backend-core:
  title: "Backend Core Roadmap"
  description: "A structured path from HTTP basics to data consistency and operations."
  icon: "fas fa-diagram-project"
  order: 1
  stages:
    - id: beginner
      title: "Beginner"
      description: "Core web and backend concepts."
    - id: intermediate
      title: "Intermediate"
      description: "Persistence, transactions, and application structure."
    - id: advanced
      title: "Advanced"
      description: "Scalability, consistency, and operational depth."
```

This keeps roadmap metadata centralized and prevents repeating display strings in every post.

## Rendering Model

### 1. Post page series block

Add a series block near the top or bottom of [`_layouts/post.html`](../_layouts/post.html).

Display:

- series title
- current position such as `3 / 8`
- previous item in series
- next item in series
- optional expandable full series list

Behavior:

- only render when `page.series` and `page.series_order` are present
- collect posts from `site.posts` where `post.series == page.series`
- sort by `series_order`, then by date as a secondary fallback

### 2. Post page roadmap block

Render a roadmap membership block when `page.roadmaps` exists.

Display:

- roadmap title(s)
- current stage
- link to roadmap page

This allows one post to belong to multiple broader learning paths.

### 3. Roadmap index page

Add a top-level page such as `/roadmaps/`.

Possible implementation paths:

- add `_tabs/roadmaps.md` plus a `roadmaps` layout
- or add a normal page under a custom layout if sidebar tab expansion is not yet desired

Display:

- all roadmap cards
- title, description, stage count, post count
- major topics

### 4. Individual roadmap page

Each roadmap page should show:

- roadmap overview
- grouped stages
- series blocks inside stages
- standalone posts not part of a series

Recommended grouping logic:

- first group by `roadmap_stage`
- then inside each stage, group by `series`
- standalone posts appear in a separate list

## URL Strategy

Recommended URLs:

- `/roadmaps/`
- `/roadmaps/<roadmap-id>/`
- optionally `/series/<series-id>/` later if standalone series landing pages become necessary

Series landing pages are not required for phase 1. A post-level series navigator gives most of the value with less implementation cost.

## Sorting Rules

### Series sorting

Primary:

- `series_order` ascending

Fallback:

- `date` ascending
- then title

### Roadmap sorting

Primary:

- roadmap `order` from `_data/roadmaps.yml`

Within a roadmap:

- stage order from `_data/roadmaps.yml`
- then series order
- then standalone posts by date or explicit weight if introduced later

## Rollout Plan

### Phase 1: Series navigation on post pages

Scope:

- front matter convention
- series block in post layout
- no new tab required

Value:

- immediate reading-order improvement
- minimal risk

### Phase 2: Roadmap data and roadmap index page

Scope:

- `_data/roadmaps.yml`
- roadmap list page
- roadmap membership links from posts

Value:

- better top-level discovery
- curated learning paths

### Phase 3: Dedicated roadmap detail pages

Scope:

- roadmap detail layout
- stage grouping
- series and standalone post grouping

Value:

- strongest learning experience
- better onboarding for large topics

### Phase 4: Recommendation upgrades

Future improvements:

- use `series`, `roadmaps`, and `roadmap_topics` in related-posts scoring
- add "continue this roadmap" recommendations
- show completion-like progress context

## Compatibility Notes

- Existing posts remain valid with no changes.
- This design works even if only a subset of posts adopt the new metadata.
- Posts without front matter should not be touched automatically.
- The repository includes mixed content types, so roadmap adoption should start with curated high-value articles first.

## Suggested Initial Roadmaps

Good first candidates for this repository:

- `backend-core`
- `database-internals`
- `spring-backend`
- `system-design`
- `interview-prep`

These align with the existing post taxonomy and likely user intent.

## Risks

### Metadata inconsistency

Risk:

- series ids or orders drift over time

Mitigation:

- define stable ids
- document the front matter contract
- optionally add a lightweight validation script later

### Build complexity

Risk:

- overusing custom plugins can slow local builds

Mitigation:

- start with Liquid and `_data` driven rendering
- avoid plugin work until the data model is stable

### Content overlap

Risk:

- categories, tags, series, and roadmaps may feel redundant

Mitigation:

- keep clear semantics:
  - categories = subject buckets
  - tags = keyword labels
  - series = ordered sequence
  - roadmaps = curated learning path

## Recommended First Implementation

Implement in this order:

1. add front matter conventions to selected posts
2. add series navigator to post layout
3. add `_data/roadmaps.yml`
4. add roadmap index page
5. add roadmap detail pages

This keeps the initial implementation tractable and lets the feature prove value early.
