# 블로그 기능·UI 개선 제안서

상용 블로그 플랫폼과 비교해 이 저장소에 무엇이 모자라고 무엇이 넘치는지 정리하고, 손댈 순서를
제안한다.

측정일 2026-10-05. 측정 대상은 배포본(<https://polynomeer.github.io>)과 로컬 빌드다.

운영·확장 쪽은 이미 [`blog-scale-and-growth-strategy.md`](./blog-scale-and-growth-strategy.md)와
[`blog-baseline-monitoring.md`](./blog-baseline-monitoring.md)에 있다. 이 문서는 **읽는 사람이
보는 것**에 대한 것이고, 겹치는 부분은 참조만 한다.

## 결론 먼저

**이 블로그의 문제는 기능 부족이 아니다.** 발견 표면(discovery surface)은 velog 나 Medium 보다
많다. 토픽 허브, 역량 맵, 학습 성과, 인용 관계, 수정 이력, 커넥션 맵, 채용자 모드까지 있다.
기능을 더 붙이는 제안서를 쓰는 건 이 저장소에 맞지 않는다.

측정해 보니 실제 문제는 세 가지였다.

1. **고칠 수 있는 낭비** — 홈 1,352 KB 중 **493 KB(36%)가 아바타 한 장과 아이콘 폰트**다
2. **읽기를 방해하는 결함** — 업데이트 토스트가 모든 페이지에서 본문을 덮는다
3. **다시 오게 할 고리가 없다** — 글은 거의 매일 올라오는데 구독 수단이 RSS 뿐이다

1번과 2번은 하루치 작업이고, 3번이 유일하게 "새로 만들" 가치가 있는 기능이다.

## 2. 측정한 문제

### 2.1 홈 1,352 KB 중 493 KB 가 아바타와 아이콘

홈 첫 로드, 요청 34개, 디코드 기준 1,352 KB.

| 자원 | 크기 | 문제 |
| --- | --: | --- |
| `assets/img/avatar.jpg` | **224 KB** | **1024×1024 원본을 80×80 자리에 쓴다** |
| `fa-solid-900.woff2` | 154 KB | Font Awesome 전체 |
| `fa-brands-400.woff2` | 115 KB | Font Awesome 전체 |
| `jekyll-theme-chirpy.css` | 227 KB | |
| Pretendard subset ×10 | ~160 KB | 이미 subset — 정상 |

아바타는 **80×80 css px** 자리에 들어간다. DPR 2 를 감안해도 160 px 이면 충분하다. 1024 px
원본을 쓰고 있어 **약 95% 가 버려진다.** 모든 페이지에 들어가는 이미지다.

아이콘은 실제로 **147종**을 쓴다. Font Awesome 전체 세트(수천 종)를 받아서 147개를 쓰는
중이다.

아바타를 160 px 로 줄이면 224 KB → 약 10 KB, 아이콘을 147종만 subset 하면 269 KB → 약
55 KB 다. 둘 합쳐 **약 430 KB**, 기능을 하나도 건드리지 않고 **1,352 KB → 약 920 KB(−32%)**
가 된다.

### 2.2 업데이트 토스트가 본문을 덮는다

[`_javascript/pwa/app.js:13`](../../_javascript/pwa/app.js) 은 이렇게 한다.

```js
if (registration.waiting) {
  popupWindow.show();
}
```

대기 중인 서비스 워커가 있으면 **페이지를 열 때마다** 토스트를 띄운다. 사용자가 "업데이트"를
누르기 전까지 계속이다. 이 블로그는 거의 매일 배포되므로 서비스 워커는 상시 갱신된다.

실제로 홈과 글 양쪽에서 본문 한가운데를 가리는 것을 확인했다. Chirpy 기본 동작이고, 글이
드물게 올라오는 블로그에서는 문제가 안 되지만 **매일 쓰는 블로그에서는 상시 방해물**이 된다.

### 2.3 0 을 보여 주고 있다

글 머리에 `0 좋아요 · 10 조회` 가 그대로 나온다. 좋아요 0 은 "아직 아무도 안 눌렀다"를 명시해
주는 것이라 **안 보여 주는 쪽이 낫다.** Medium 도 박수 0 이면 숫자를 숨긴다.

### 2.4 작성자 이름이 둘이다

블로그 이름은 `Polynomeer`, 글의 작성자 표기는 `August`. 같은 사람인지 읽는 사람은 모른다.

### 2.5 읽기 환경은 문제가 아니다

의심해서 쟀는데 경쟁력이 있었다. 기록해 둔다.

| | 이 블로그 | velog |
| --- | --: | --: |
| 본문 폭 | 654 px | 736 px |
| 본문 크기 | 17.3 px | 18 px |
| 줄 길이 | 76자 | 82자 |
| 행간 | 30.2 px | 30.6 px |

**타이포그래피는 손대지 않는다.** 비슷하거나 더 촘촘한 수준이고, 바꿀 이유가 측정에서 나오지
않았다.

### 2.6 모바일 카드가 길다

375×812 에서 글 카드 하나가 약 340 px 을 쓴다. 한 화면에 **2.3개**가 보인다. velog·Medium 은
3~4개다. 제목 아래 유형 배지가 한 줄을 통째로 차지하는 것이 주원인이다.

### 2.7 빌드 81초

`bundle exec jekyll build` 가 81초다. 읽는 사람과는 무관하지만 **글 쓰는 사람의 반복 주기**를
결정한다. 원인과 대응은 이미 [`blog-scale-and-growth-strategy.md`](./blog-scale-and-growth-strategy.md)에
정리돼 있다. 여기서는 숫자만 갱신해 둔다.

## 3. 벤치마킹에서 가져올 것

### velog — 직접 비교 대상

시리즈 표시가 **한 줄**이다. 제목 + `목록 보기` 접기 + `1/2` + 이전·다음 화살표가 한 행에
들어간다. 이 저장소도 최근에 같은 방향으로 압축했으므로 추가로 가져올 것은 없다.

가져올 수 없는 것: 팔로우, 트렌딩 노출. 플랫폼이 트래픽을 들고 있어서 되는 기능이다.

### Substack·Ghost — 이메일 구독

두 플랫폼의 핵심은 에디터가 아니라 **구독자 목록**이다. 읽는 사람이 돌아올 이유를 플랫폼이
아니라 발행자가 갖는 구조다.

이 블로그에 **없는 유일한 중요 기능**이다. RSS 는 있지만 실제로 쓰는 사람은 적다.

### Medium — 읽기 신호

읽는 시간 표시(이미 있음), 하이라이트 공유, 0 일 때 숫자 숨김. 세 번째만 가져올 만하다.

### dev.to·Hashnode — 교차 게시

`rel=canonical` 로 원문을 자기 블로그에 두고 플랫폼에 복제 게시한다. SEO 를 해치지 않으면서
플랫폼 트래픽을 쓴다. 이 저장소는 velog 에서 **빠져나온** 이력이 있는데
([`velog-migration-plan.md`](./velog-migration-plan.md)), 교차 게시는 되돌아가는 것이 아니라
**원문을 여기 두고 복제만 보내는** 반대 방향이다.

### Bear Blog — 빼기

기능이 거의 없고 매우 빠르다. 이 저장소와 정반대다. 참고할 것은 하나다 — **표면이 늘수록
각 표면의 방문은 줄어든다.** 16개 탭이 전부 값을 하는지는 측정된 적이 없다.

## 4. 제안

### P0 — 측정된 낭비 (반나절)

| | 작업 | 효과 |
| --- | --- | --- |
| 1 | 아바타를 160 px(또는 320 px)로 다시 내보내기 | 약 −215 KB, 전 페이지 |
| 2 | Font Awesome 을 쓰는 147종만 subset, 또는 인라인 SVG 로 교체 | 약 −215 KB, 전 페이지 |
| 3 | 업데이트 토스트를 세션당 1회로 제한하고 하단 고정으로 변경 | 본문 가림 제거 |

1·2번은 코드 변경이 아니라 자산 교체다. 되돌리기도 쉽다. **기능 손실이 0 인데 페이지 무게가
약 32% 줄어든다.**

3번은 `_javascript/pwa/app.js` 에서 `registration.waiting` 분기를 `sessionStorage` 로 한 번만
띄우게 막으면 된다. 열 줄 안쪽이다.

### P1 — 작은 결함 (반나절)

| | 작업 |
| --- | --- |
| 4 | 좋아요·조회수가 0 이거나 임계값 미만이면 숨기기 |
| 5 | 작성자 표기를 `Polynomeer` 로 통일하거나, 소개에서 `August` 와의 관계를 밝히기 |
| 6 | 모바일 카드에서 유형 배지를 제목 줄 끝으로 올려 한 줄 회수 |

### P2 — 이메일 구독 (1~2일)

**유일하게 새로 만들 가치가 있는 기능이다.**

- 이미 있는 RSS(`/feed.xml`)를 입력으로 쓰고, 발송은 외부 서비스에 맡긴다
  (Buttondown, listmonk, Mailchimp RSS 캠페인 중 택1)
- 정적 사이트에 필요한 건 **구독 폼 한 개**뿐이다. 서버는 필요 없다
- 위치: 글 하단(관련 글 위), `/start/`, 소개 페이지
- 매일 발송이 아니라 **주간 요약**이 맞다. TIL 이 605편이라 일 단위로는 메일함을 망친다

근거: 1,021편을 쓰는 동안 읽는 사람이 다시 올 수단이 RSS 밖에 없었다. 구독은 플랫폼이 아니라
발행자가 가져야 하는 유일한 자산이다.

리스크: 이메일 주소를 받으면 개인정보 취급 책임이 생긴다. 외부 서비스에 맡기고 이 저장소는
주소를 저장하지 않는 구성으로 한다.

### P3 — 측정 먼저, 그다음 정리

16개 탭 중 무엇이 쓰이는지 **지금은 아무도 모른다.** 지우자고 제안하지 않는다. 대신:

| | 작업 |
| --- | --- |
| 7 | 페이지별 방문 수를 90일간 수집 |
| 8 | 그 결과로 하위 표면을 접거나 상위 표면에 합치기 |

순서를 뒤집으면 잘 쓰이는 페이지를 지우게 된다.

### P4 — 교차 게시 (선택)

대표 글 10편 정도를 `rel=canonical` 을 걸어 dev.to 또는 velog 에 복제한다. 원문은 여기 두고
트래픽만 가져온다. **전량 복제는 하지 않는다** — 1,021편은 관리 불가능하고, 이 블로그의 값은
개별 글이 아니라 토픽·시리즈 구조에 있다.

## 5. 하지 말 것

- **새 발견 표면 추가.** 이미 16개다. P3 의 측정 결과가 나오기 전까지는 늘리지 않는다
- **팔로우·구독자 수 표시.** 정적 사이트에서는 0 이 박힌 버튼이 된다
- **타이포그래피 손질.** 측정해 보니 velog 와 대등하다. 바꿀 근거가 없다
- **조회수 경쟁.** 이 블로그의 값은 트래픽이 아니라 1,021편이 서로 연결된 구조다
