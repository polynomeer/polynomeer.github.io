**Q. 이제 간단히 자기소개 해주시겠어요?**

안녕하세요, 저는 백엔드 개발을 한지 3년이 조금 넘었고, 프로필에 나와있듯이 어려운 문제를 쉽게 풀어나가는 것을 지향합니다. 이를 위해 기획, 운영팀 등 다른 팀과의 협업을 통해 좀 더 나은방향을 모색하는 개발자입니다.

**Q. 이력서에 보니까 레거시 개편한 프로젝트가 있네요? 어떤 프로젝트인지 상세히 설명해주시겠어요?**

먼저, 저는 MCP라는 팀에 소속되어서 업무를 했습니다. MCP에 대해서 설명드리기 전에 회사의 업무 도메인을 설명드리겠습니다. 우선, 제가 다닌 회사는 음원 스트리밍 업을 하는 회사입니다. 음원 스트리밍 서비스를 하기 위해서 우선 음원을 유통사를 통해서 입수합니다. 유통사가 특정 스토리지에 DDEX라는 규격에 맞춰서 음원을 업로드하면, 스트리밍할 수 있는 형태로 변환하는 트랜스코딩이라는 과정을 거칩니다. 그리고 각종 메타정보나 데이터를 파싱하고 추출해서 저장 및 관리하는 과정이 있는데, 이 모든 과정에서의 연결고리를 MCP라는 백오피스가 담당하고, 이를 서버팀으로 전송하여 메타연계를 하여 디스플레이 영역으로 전송하는게 MCP팀의 업무영역 범위입니다.

**Q. API가 단편적으로 구성되어서 개선했다는 내용이 있는데, 어떤 내용인지 상세하게 설명해주시겠어요?**

기존의 JSP기반의 시스템에서는 자바스크립트에서 많은 검증로직과 비즈니스 로직을 포함하고 있었습니다. 그리고 API 설계서나 문서가 없었고, 또한 MyBatis기반의 쿼리 매퍼가 작성되어있었지만, 실제 쿼리에서 FE로부터 이어지면서 입력되지않는 필드들도 다수 있었습니다. 이런 문제를 개선하기 위해서 실제 동작하는 서비스 기반으로 리버스 엔지니어링 수준으로 분석하는 과정이 필요했고, FE팀과 협의를 해가면서 일부 API구조를 개선했습니다.

트랜잭션 단위로 묶여서 정합성을 보장해야함에도 단편적인 호출을 하며, 실제로는 타이밍이나 UI/UX 상으로만 정합성이 보장될 가능성이 높은 구조가 있었습니다. 따라서 일부 UI가 변경되면 얼마든지 데이터 정합성이 틀어질 수 있다고 판단했고, 데이터 정합성을 보장하는 애그리게이트 묶음으로 원자성을 보장하도록 재설계 했습니다.

**Q. SPA 화면상에서 성능을 최적화한 사례로 이해가 되는데요, 5.2초에서 2.3초로 개선한다고하면 사실 성능이 여전히 부족하다고 생각되는데, 구체적으로 어떤 부분을 개선하신걸까요?**

성능을 개선한 페이지는 앨범 상세 페이지의 가장 느린 성능의 일부 앨범을 예시로 측정한건데요, 앨범 하위의 트랙이 있고, 또 그 트랙의 연관데이터인 참여아티스트, 아티스트, 그리고 또 그 아티스트의 참여역할, 악기 등 여러가지 데이터를 한 번에 로딩하려다보니 JSON 용량을 초과하는 수준에 이르렀습니다. 물론, 모든 앨범이 그런 상황은 아니고 일부 앨범이 로딩이 매우 지연되는 상황이었습니다. 예를 들면, 마이클 잭슨의 몇주년 기념앨범 같은 경우에 하위 트랙만해도 100개가 넘고, 또 참여아티스트도 엄청나게 많은 경우가 있습니다. 이럴때 DB응답 속도는 1초내외라고 해도, JSON응답하는 시간에 특히나 프론트엔드에서 렌더링할때, 특정 컴포넌트에 따라 오래걸리는 경우도 많았습니다. 그 부분에서 렌더링하기 용이한 API 구조를 협의했고, 재설계하는 방식으로 일부 최적화했습니다.

**Q. 레거시 개선 프로젝트에서 전체적인 구조를 어떻게 개선했는지 상세히 설명해주시겠어요?**

먼저, 프론트엔드에서 담당하던 검증 로직을 일부 백엔드로 위임했고, 어디에서 어디까지 담당할지, 그리고 어떤 부분은 이중으로 FE/BE에서 모두 검증할지 등등을 논의하고 나누었습니다. 백엔드에서는 Map을 통해 전달받던 파라미터를 모두 DTO구조로 변경했고, Package by component 라는 구조로 패키지를 구성했습니다. 이는 헥사고날과 레이어드 아키텍쳐의 절충된 형태라고 생각되는데요, 쉽게 말해 web과 나머지는 도메인 패키지로 구성해서 web 패키지에는 다른 도메인 패키지의 구현체가 직접 의존하지 못하는 형태로 구성하는 것입니다. 이 과정에서 Mapstruct를 사용해서 계층간의 연결에서 매핑을 강제했습니다.

**Q. 대규모 레거시 개편이다보니 한번에 모든 기능이 수월하게 옮겨지진 못했을것 같은데요, 어떻게 옮겼는지 방법론과 그 결과를 설명해주세요. 특히 Map으로 작성된 필드들을 DTO로 모두 옮기는 과정에서 완벽히 한 번에 깔끔하게 진행되기는 어려웠을것 같은데요.**

아무래도 일정도 타이트하고 레거시가 테스트하기 어려운 구조이다보니, TDD처럼 테스트를 빡빡하게 작성해서 진행하지는 못 했습니다. 말씀하신대로 QA중에 버그나 마이그레이션 과정에서 발생한 에러 및 기존 에러를 확인하고 개선할 수 있었습니다. 그래도 최대한 단순 필드 매핑 버그를 최대한 줄이기 위해서 Mapstruct를 적극 도입했고, 또 그 과정에서 일부는 AI를 활용해 필드 매핑 자동화 및 검증을 수행하였습니다.

**Q. Mapstruct라는 도구를 계층간의 매핑에 사용하신 부분은 이해했는데요, 이 도구를 쓰면서의 이점이나, 별도의 커스터마이징을 통해서 장점을 얻은 사례가 있을까요?**

**Q. 계약코드 생성과정에서 시퀀스 테이블의 병목을 개선한 사례를 상세히 설명해주시겠어요?**

계약코드 생성 시 DB의 시퀀스 테이블을 점유해서 프로시저를 호출해서 대량의 시퀀스를 점유하는 구조입니다. 그 과정에서 시퀀스를 점유하면 스스로 경합에 빠져서 성능이 급격하게 저하되는 경우가 종종 발생했습니다. 자주 쓰는 기능은 아니라서 개선포인트로 우선시 되지 않았지만, 레거시를 개편하는 과정에서 제가 담당하게 되면서 개선 포인트로 잡아서 진행하게 되었습니다.

**Q. 더 구체적으로 시퀀스를 점유하면서 성능이 저하된 원인이 어디였고, 어떻게 탐지해내었나요?**

그냥.. MySQL의 프로시저가 작성되어있었는데, SELECT ... FOR UPDATE 기반이었습니다. 그 과정에서 락경합이 발생했다고 추정한 부분은 그냥 로컬에서 해당 API를 벌크로 등록하면서 실행해보았을때, 디버깅하면서 그 지점에서 성능이 오래걸리는 것을 판단했기 때문입니다. 로컬에서 개발환경 DB에 접근해서 테스트를 진행했습니다.

**Q. 여기에 적힌 낙관적인 락 방식이라는게 다시 어떤건지 설명해주실 수 있나요?**

그러니깐 말 그대로 낙관적으로 서버에서 1부터 1000까지 시퀀스를 점유하고 마지막 업데이트 하는 시점에서 다른 프로세스? 스레드가 동시에 1부터 1000까지를 점유하고 계약 데이터 셋을 생성한다면, 마지막 업데이트 시점에 last index만 확인해서 만약 1001번 이런식으로 안맞는 경우에는 예외처리하는 방식으로 진행했습니다.

**Q. 여기에서 시퀀스를 담아서 낙관적인 방식으로 동시성 제어를 구현했다고 하셨는데요, 시퀀스를 담을때 사용하신 자료구조는 무엇인가요?**

음.. 그냥 Integer 타입으로 시퀀스의 last index를 저장했습니다.

**Q. 네, 그러면 동시성을 고려할 수 있을까요?**

동시작업이 거의 없는 부분이라 크게 고민하지 않았지만, 그 부분을 고려한다면 AtomicInteger나 ConcurrentHashmap같은 자료구조를 사용할 것 같습니다.

**Q. 이 방식을 개선한다면 어떻게 개선하시겠어요?**

... 글쎄요, 해당 기능은 엑셀을 업로드하고 모두 읽어들인 다음에 row단위로 insert 데이터를 생성하고 벌크로 insert 쿼리가 나가는 방식입니다. 또한 해당 row 데이터간의 의존성이나 순서가 중요하지도 않았습니다. 그러다보니 미리 row를 읽으면서 chunk 단위로 별도의 스레드로 병렬처리할 수 있다고 생각합니다.

**Q. 구현을 구체적으로 어떻게 할 수 있을까요?**

자바 기반으로 한다면 CompletableFuture로 모두 쪼개어서 병렬처리를 수행한다음, 마지막에 join으로 묶어서 처리하는 식으로 구현할 것 같습니다.

**Q. 서버가 한 대라서 상관없다고 하셨는데, 서버가 만약 두 대나 그 이상이라면 어떻게 해결하시겠어요?**

서버가 두 대라고 가정한다면.. 일단 A서버에서 1~1000까지를 점유하고, B서버에서 1~1000까지를 동시에 점유하는 상황이 충분히 생길 수 있습니다. 그때 동일한 문제를 개선하려고 한다면, 중간에 레디스를 두고 줄을 세운다던지 비동기로 끊어낼 수 있을것 같습니다. 아마도 DB에서 직접 락을 제어하는것보다는 성능상 유리하지 않을까 생각합니다.

**Q. MSA 구조에서 업스트림으로부터 다운스트림으로 이어지는 과정에서 다운스트림의 여러 서버중에 한 대가 이상이 생겼다고 가정해볼게요. 그때 서버가 응답을 아예 못 해서 타임아웃이 발생하는 경우에 retry를 계속하는게 맞을까요?**

글쎄요.. 제가 MSA를 잘 모르지만 상상으로만 답변드리겠습니다. 우선, retry의 임계치를 찾기위해서 여러가지 실험을 할 것 같습니다. 최악의 경우, retry의 횟수를 3회까지하고 timeout을 최대까지 설정한다면 서버군이 견딜 수 있을지 테스트를 진행할겁니다. 그리고 임계치를 특정해서 적절한 retry횟수와 타임아웃을 지정할 것 같습니다.

**Q. 아까 시퀀스를 1000개씩 chunk단위로 점유해서 시퀀스 생성을 한다고 하셨는데요, 1만개의 시퀀스를 생성한다고 가정하면 11번 실행될 것 같은데요, 개선방안이 있을까요?**

음.. 잘 모르겠습니다.

**Q. 혹시 이 경우에 1개만 생성하다던지, chunk 단위를 훨씬 못 미치거나 살짝 넘으면 비효율적이지는 않을까요? 그 경우에는 어떻게 개선할 수 있을까요?**

아마도 적절한 chunk의 단위를 찾기 위해서 사례 기반으로 잘 측정하겠지만, 우선 해당 시스템의 경우에 한정해서는 엑셀을 모두 읽어서 row를 가지고 insert 데이터를 생성하다보니, chunk 단위로 시퀀스를 생성하는 시점에 이미 row 개수를 알고있을거라서 적절하게 chunk 단위를 조절할 수도 있을 것 같습니다.. 그리고 다른 방법으로는 그냥 DBMS의 옵티마이저처럼 통계기반의 데이터를 확보해서 그 옵티마이저를 수행하는 서버를 하나 둔다거나해서 적절한 chunk단위를 제안할 수 있을것 같습니다.

**Q. 기존 시스템에서 키 생성 전략을 완전히 새로 구성할 수 있다면 어떻게 하는게 좋을까요?**

우선, 가장 간단하면서도 확실한 방법으로는 DBMS에 키생성 전략을 위임하는 AUTO_INCREMENT 전략을 취할 것 같습니다. 그러나 이 시스템의 시퀀스 규칙을 따라야한다면, DBMS보다는 좀 더 앞단의 빠른 메모리기반의 DB인 레디스 같은것을 통해서 키생성 전략을 수행하도록 할 것 같습니다. 물론, 키의 prefix나 규칙이 비교적 덜 중요한 기능이나 메뉴에서는 Time-based UUID같은 전략으로 시퀀스 테이블과의 연관성을 좀 끊어낼 것 같습니다.

**Q. 입수 파이프라인의 구성이 이해하기로는 단일장애지점을 가지는 구조로 파악이 되는데, 장애 시 어떻게 대응했나요? 별도의 재처리할 수 있는 방법이 구성되었나요?**

별도로 재처리를 위한 방법이나 서버가 구축되어있지는 않았습니다. 보통 문제나 장애상황이 발생하면, 로그를 기반으로 재처리를 진행하거나, 재입수가 필요한 경우 별도로 유통사에 연락하여 재전송을 요청할때도 있었습니다.

**Q. Datadog을 사용하셨다고 했는데, 입수 파이프라인에도 구성이 되어서 별도의 기능으로 재처리가 가능하지는 않았나요?**

아쉽게도 비용 등의 문제로 입수 관련 서버군에는 Datadog을 설정하지는 못 했습니다. 그냥 단순히 Spring Boot Admin과 Actuator로만 구성된 모니터링을 진행했습니다.

**Q. 그러면 만약에 좀 더 개선한다면 어떻게 할 수 있을까요?**

음.. 제가 이벤트 소싱이라는 개념을 최근에 학습했는데, 이를 통해 보완이 가능할 것 같습니다. 입수 자체도 하나의 이벤트라고 보고, 입수 이벤트가 발생하면 입수에 대한 이벤트 정보를 상세히 기록하고, 만약에 도중에 끊기거나 실패했을때, 특정 프로세스만 재처리하거나 하는 식으로 개선 가능할 것 같습니다.

**Q. RabbitMQ를 사용해보셨나요?**

네, 입수 파이프라인에서 파일옵저버라는 서버가 음원 파일을 읽어들이고 비동기로 음원의 메타정보를 추출하는 서버 및 트랜스코딩하여 음원을 스트리밍할 수 있는 형태로 바꾸기위한 트랜스코더 서버로 요청하는 과정에서 RabbitMQ로 전송했습니다.

**Q. 그렇다면 메시지는 어떤 방식을 사용했나요?**

음.. 두 가지 방식이 있는것으로 아는데, 정확히 기억이 안 납니다.

**Q. 메시지는 별도의 TTL이나 이런 설정없이 사용하셨나요?**

...

**Q. 그러면 직접 규격이나 등등 구축해보신 건 아니고, 마찬가지로 기존의 레거시 시스템에 구축되어있었던 거군요?**

네, 맞습니다.

**Q. 만약에 메시지가 DLQ가 되었을때는 어떻게 했나요? 아니면 어떻게 처리하는게 좋을까요?**

...

**Q. RabbitMQ로 구축된 입수 파이프라인이 있다고 하셨는데, 그러면 여기에서도 메시지가 유실될 수 있을텐데, 어떻게 재처리한 걸까요?**

네, 맞습니다.

그냥 아까 말씀드렸듯이 로그 기반으로 특정 지점에 명확히 남은 로그기반의 재처리나 재입수를 통해 입수 데이터를 보정했습니다.

**Q. AWS로 마이그레이션도 하셨다고 했는데, RabbitMQ도 직접 설치하고 구성하신걸까요? 어디까지 담당하셨나요? 메시지큐 담당 팀이 따로 있었나요?**

AWS에서 구성하고 설치하는 과정들은 클라우드 팀이 따로 있어서 구성해주셨고, 그 내부에 메시지큐를 구성하고, 콘솔을 통해서 모니터링하면서 메시지가 잘 디큐되었는지 등 확인하는 작업은 모두 직접 팀 내부에서 담당했습니다.

**Q. 대량 배치 개선은 하신 내용중에 JPA기반 배치 개선을 설명해주시겠어요?**

네, 처음에 JPA 기반의 배치 잡에서 OOM이 발생했고, 힙덤프를 생성하도록 설정해서 확인해보니 특정 엔티티를 과도하게 퍼시스턴스 영역에 적재하면서 결국 OOM이 발생하는 것으로 확인되었습니다. 

**Q. 그러니까 Job 전체에 @Transactional을 붙여서 chunk 단위로 처리하면서 계속 퍼시스턴스 영역에 엔티티가 누적되어서 OOM이 발생했다는 말인가요?**

네, 맞습니다.

**Q. GC는 G1GC만 사용해보신 건가요?**

네, 사실 그 MDS라는 프로젝트에서 배치를 개선하는 과정에서 처음에는 메모리 사용량이 많아졌고, GC부터 변경해보았습니다. 하지만, 모니터링을 통해서 아까 말씀드렸듯이 datadog에서의 메모리 사용량 정책, CPU사용량 정책 기준에서 알람이 발생하기도 했고 직접확인해보니, 메모리 사용량 관점에서는 크게 소득이 없었습니다. 그리고 CPU사용량은 오리려 더 늘어났는데요, 이 원인은 ZGC가 더 동시성을 극대화하기 위한 연산들을 많이 수행하다보니 CPU사용량은 다소 늘어난다는 내용으로 알고 있습니다. 따라서 해당 서버에서는 그냥 ZGC로 롤백하는 과정을 거쳤었습니다.

**Q. Job 전체에 @Transactional을 설정한 이유가 있을까요?**

없습니다. 그 당시에 지식이 부족하기도 했고, JPA의 동작에 대한 속성을 잘 고려하지 못 했습니다.

**Q. 네, 그래도 좋은 과정으로 탐지했고 해결해내셨네요.**

**Q. 잡에서 시퀀스 chunk의 단위는 어떻게 정하셨나요? 적정값을 측정하신 방법이라던가 따로 결정한 기준이 있을까요?**

그냥.. best practices를 검색을 통해서 5000개 정도로 특정했고, 모니터링을 통해 메모리 사용량이나 CPU 사용량 등의 모니터링을 통해 적절한 양을 대략적으로 지정하게 되었습니다.

**Q. 엔티티 매니저의 flush()와 clear()의 차이점을 아시나요?**

... 잘 모르겠습니다.

**Q. DB는 주로 MySQL을 사용하신거죠? 보통 그러면 chunk단위로 작업을 수행하고 중간에 끊어지거나 실패하면 어떻게 하셨죠?**

보통 전체를 로그 기반으로 재처리하는 식으로 진행했습니다.

**Q. 아? 아까 flush(), clear() 이야기를 하셨는데, 그러면 flush는 하면서 또 별도의 중간서버나 로직를 거치면서 최종적으로 DB에 반영될지말지를 제어하는 무언가가 있다는 말씀이신가요?**

아, 아니요. 잘못 말씀드렸습니다. 기존의 배치서버는 대부분 실패하면 모두 예외를 던지면서 다 실패하는게 맞는데요, 해당 시스템은 신규로 구축한거라서 말씀하신대로 flush하면 그 까지는 처리가 되는 식으로 진행했습니다.

**Q. 그러면 1000개 중에서 100개를 chunk단위로 실행하면서 200개 까지만 성공했다면, 재처리 시 0번부터 다시 시작하나요?**

아니요, 제 기억에는 DB에 단순히 마킹하는 방식으로 처리한 데이터는 처리됨이라고 찍어놓고, 다음에 재처리하게되면 그 데이터는 건너뛰고 진행했습니다.

**부족한 점**

- 협업 강조는 좋으나, 본인의 기술적 강점/차별성 언급 부족
- 커뮤니케이션이 어떻게 문제해결로 이어졌는지 구체성 부족

**Best Practice 답변**

```
안녕하세요. 저는 3년간 대규모 음원 스트리밍 플랫폼의 백엔드 개발자로 일하며, 복잡한 문제를 시스템적으로 분석하고 개선하는 데 강점을 가진 개발자입니다. 실무에선 다양한 부서와의 협업 경험을 바탕으로, 기술적인 문제뿐만 아니라 조직적인 이슈까지 전체적으로 개선해 본 경험이 많습니다. 특히 레거시 시스템의 대규모 리팩토링과 대용량 데이터 처리, 실시간 장애 대응 등 현업에서 빈번히 발생하는 문제들을 기술과 협업으로 해결해온 것이 저의 차별점입니다.
```

## 2. 레거시 개편 프로젝트 설명

**부족한 점**

- MCP 역할/의미 설명이 장황하고, 핵심 파악이 어려움
- 본인의 구체적 기여(전환, 개선 포인트, 임팩트 등) 드러나지 않음

**Best Practice 답변**

```
MCP(Music Content Platform)는 음원 유통부터 메타데이터 관리, 트랜스코딩까지 음원 서비스 전 과정을 연계하는 백엔드 시스템입니다. 저는 MCP의 레거시 개편 프로젝트에서, 단순 파일 처리/메타 연동을 넘어 각 모듈 간 데이터 흐름을 표준화하고 API 기반으로 재설계하는 역할을 맡았습니다.  
구체적으로는 유통사로부터 DDEX 기반으로 음원을 받아 트랜스코딩, 메타데이터 파싱, 운영팀 연동까지 모든 프로세스를 일원화했고, 업무 흐름별 장애 대응 프로세스와 품질 관리 자동화를 도입해 전사적으로 데이터 정합성과 운영 효율성을 크게 높인 경험이 있습니다.
```

## 3. 단편적 API 개선 경험

**부족한 점**

- 문제상황 → 구체적 원인 → 개선안 → 효과 구조가 약함
- 설계 의도, 기술적 난이도, 협업의 구체적 과정 등이 드러나지 않음

**Best Practice 답변**

```
기존 시스템은 문서화되지 않은 API와 FE 중심의 비즈니스 로직이 혼재해 있었습니다. 이로 인해 데이터 정합성 보장에 문제가 있었고, 단편적 API 호출이 늘어남에 따라 트랜잭션 일관성도 취약했습니다.

개선 방향은 다음과 같습니다:
- 실제 서비스 동작을 기준으로 API Reverse Engineering → Restful 구조로 재설계
- 프론트/백엔드 간 비즈니스 책임 분리, 데이터 정합성을 위한 트랜잭션 내 aggregate 처리 도입
- API 문서화 및 테스트 자동화 도입(JUnit + Swagger)

결과적으로 데이터 정합성 이슈가 현저히 줄었고, 장애 대응 속도 및 신규 기능 개발 생산성이 크게 향상되었습니다.
```

------

## 4. SPA/프론트엔드 성능 최적화

**부족한 점**

- 구체적 원인 진단/개선 내용/수치적 결과/FE-BE 협력 과정이 모호함

**Best Practice 답변**

```
앨범 상세 페이지의 렌더링 지연은 대용량 트랙 및 아티스트, 참여정보를 한 번에 로딩하면서 발생했습니다. 병목 원인을 아래와 같이 단계적으로 진단했습니다:
1. 대량 JSON 직렬화 및 네트워크 지연 → DB 조회는 1초 미만이었으나 FE에서 3초 이상 지연
2. 불필요한 관계데이터 과다 조회 → 필요 범위로 쿼리/필드 축소, 페이징/지연로딩 도입
3. 프론트엔드와 협업해, 필요한 데이터만 먼저 내려주는 endpoint 분할 및 비동기 prefetch 전략 적용

이로 인해 일부 앨범 페이지의 로딩 속도를 5.2초 → 2.3초로 단축했고, 대용량 앨범도 빠르고 안정적으로 제공할 수 있었습니다.
```

## 5. 전체 구조 개선 (백엔드 리팩토링)

**부족한 점**

- 구조적 변화와 기대 효과, 구체적 설계 패턴, 검증/테스트 전략 등이 부각되지 않음

**Best Practice 답변**

```
기존에는 파라미터 전달이 Map 기반으로 불명확했고, 비즈니스/도메인 레이어 경계도 흐릿했습니다. 이를 아래와 같이 개선했습니다:
- DTO/엔티티 구분 및 계층 간 명확한 역할 분리
- ‘패키지 바이 컴포넌트’ 구조로 도메인별 패키징, 구현체/인터페이스 분리(헥사고날+레이어드 절충)
- MapStruct + ArchUnit을 활용해 계층간 매핑 규칙 및 의존성 위배 자동 검증
- 도메인별 유효성 검증 로직을 계층화하여, 책임/검증 포인트를 명확히 분리

이 구조는 신규 도메인 추가/변경에도 유연하며, 팀 내 코드 품질/일관성도 크게 개선되었습니다.
```

## 6. MapStruct 활용 경험

**부족한 점**

- 도구의 장점, 커스터마이징/자동화 경험 등 구체적 사례/효과 미흡

**Best Practice 답변**

```
MapStruct는 타입 세이프한 매핑 자동화로, 필드 누락/오타 등을 컴파일 타임에 체크할 수 있습니다.  
저는 공통 매핑 로직을 디폴트 메서드로 인터페이스에 정의해, 도메인/DTO간 일관된 변환을 재사용했습니다.  
아울러 ArchUnit을 통해 계층 간 잘못된 의존성이 발생할 경우 빌드 시점에 자동 검증되도록 해, 코드 품질 관리에 크게 기여했습니다.  
복잡한 매핑이 필요한 경우 커스텀 매퍼/Expression 사용으로 업무 요구사항도 유연하게 반영했습니다.
```

## 7. 시퀀스/키 생성 병목 개선

**부족한 점**

- 병목의 구체 원인, 현업적 탐지 방법, 개선방안/적용기술 등 설명 미흡

**Best Practice 답변**

```
계약코드 시퀀스 생성 과정에서 SELECT FOR UPDATE 기반 프로시저로 인한 락 경합이 주요 병목 원인이었습니다.
실제 장애 상황은 대량 병렬 요청 시 DB 락 대기가 급증하면서, API 응답이 수 초 이상 지연되어 발견했습니다.  
실제 트랜잭션 실행 시, 락/대기시간/실행계획 모니터링(MySQL Performance Schema + SHOW ENGINE INNODB STATUS 등)을 병행해 원인을 진단했습니다.

개선 방향으로,  
- Chunk 단위의 병렬 시퀀스 점유(CompletableFuture 등으로 병렬화)
- 분산 환경에서는 Redis 기반의 분산락/원자적 INCR 커맨드 등으로 컨텐션 완화  
- 장기적으로는 Time-based UUID, DBMS의 AUTO_INCREMENT/SEQUENCE 등 전략으로 전환 검토
를 제안하고, 일부 PoC도 진행했습니다.
```

## 8. MSA 장애 대응, 서킷브레이커

**부족한 점**

- 장애 유형별 사례, 업계 표준 패턴(서킷브레이커, 재시도 정책 등) 활용 경험 부족

**Best Practice 답변**

```
MSA 환경에서 다운스트림 서버 장애 발생 시, 무한 재시도는 전체 서비스 장애로 이어질 수 있어 바람직하지 않습니다.
현업에서는
- Circuit Breaker 패턴(Hystrix, Resilience4j 등) 도입: 장애 탐지 시 임계치 초과 시 자동 차단/복구
- 재시도 정책(최대 횟수, 점진적 백오프, 데드레터큐 등) 명확히 설정
- 장애 전파 최소화 및 fallback 처리
를 적용하는 것이 표준입니다.

특히 대용량 트래픽/배치 작업 시에는 메시지 브로커(Kafka 등)를 활용해 장애/트래픽 버퍼링, 재처리, 사후 추적이 용이하도록 설계합니다.
```

## 9. 배치 OOM/JPA chunk 처리 개선

**부족한 점**

- 문제 원인/분석/개선 구조, 구체적 결과와 교훈 부족

**Best Practice 답변**

```
JPA 기반 배치 Job에서 @Transactional을 잘못 사용해, 전체 데이터가 1 트랜잭션에 적재되어 퍼시스턴스 컨텍스트가 OOM에 빠지는 문제가 있었습니다.
문제 진단을 위해 Thread Dump/Heap Dump/GC 로그를 분석해, 엔티티 누적이 힙 메모리 급증의 원인임을 파악했습니다.

개선 방법은  
- 일정 건수(chunk)마다 EntityManager.flush()/clear() 호출로 컨텍스트 누수 방지
- 각 단계별 모니터링(Datadog, JVM GC 로그 등) 및 트랜잭션 범위 재설계
를 적용했고, 그 결과 GC 빈도/처리시간 대폭 감소, 전체 처리 속도 2배 이상 개선 등 효과를 얻었습니다.
```

## 10. 장애/재처리, 이벤트 소싱

**부족한 점**

- 재처리/모니터링 체계, 이벤트 기반 설계 등 구체적 제안 부족

**Best Practice 답변**

```
초기에는 장애 발생 시 로그 기반 수동 재처리, 유통사 재전송 의존 등 수작업이 많았습니다.
개선 방향으로,  
- 각 단계(입수/메타/트랜스코딩 등)의 상태/이력을 이벤트/로그 테이블에 기록
- 이벤트 소싱/메시지 큐 기반 재처리 시스템 도입(부분 실패 시 특정 단계만 재처리)
- 모니터링 도구(Datadog, Prometheus, Spring Actuator 등)로 실시간 상태 감시, Slack/Webhook 알림 연계  
를 제안/구축하여 장애 대응력과 자동화, 재처리 효율을 크게 높일 수 있었습니다.
```

기타 자주 나오는 항목(실무 기술/협업/문서화 등)도 Best Practice 중심으로 정리해두시면 좋습니다.
