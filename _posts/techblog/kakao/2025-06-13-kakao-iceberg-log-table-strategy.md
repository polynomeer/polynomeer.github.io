## 한 줄 요약

카카오 데이터분석플랫폼팀은 서비스 DB의 변경(DB 로그)을 Flink CDC로 Iceberg에 UPSERT하고, 서버 로그는 ORC로 쌓아 왔다. 이 글은 서버 로그도 Iceberg로 옮기면 어떻게 다뤄야 하는지를 실험으로 정리한다. 결론은 **로그 유형에 따라 전략이 갈린다**는 것이다. DB 로그는 PK 기준 UPSERT + bucket 파티션 + 10분 커밋 + 하루 2회 전체 compaction, 서버 로그는 APPEND + 처리 시간 문자열 identity 파티션 + 1분 커밋 + 매시간 직전 파티션 compaction + 별도 DELETE. 곁가지로 zstd 압축 레벨 실험이 있는데, 레벨 9까지 올려도 지연은 없고 ORC 대비 파일이 절반으로 준다.

## 배경

팀 미션은 서비스 팀 데이터를 모아 일 단위 지표를 뽑는 것이다. 서비스 DB를 직접 읽으면 운영에 부담이 되어 CDC로 Iceberg에 연동했다(시리즈 1·2편). 로그는 클라이언트 로그, 서버 로그, DB 변경 로그 셋이고 팀이 직접 수집하는 것은 뒤의 둘이다. DB 로그는 운영 중인 방식이고 서버 로그는 **테스트 중인 방향**이라는 점을 원문이 먼저 밝힌다.

## DB 로그: 지금 운영하는 방식

MySQL PK 기준 UPSERT로 적재해 항상 최신 상태를 조회할 수 있게 한다. PK 기준 **bucket transform** 파티션(bucket 5)으로 프루닝과 compaction을 돕는다. 커밋 주기는 Flink 체크포인트와 같은 10분. 작은 파일 문제와 신선도 사이의 타협이다. 이 덕분에 매일 MySQL 전체를 소싱하거나 MySQL 부하 때문에 Spark 성능을 일부러 제한할 필요가 없어졌다.

## 서버 로그: 왜 APPEND인가

서비스마다 형식이 달라 팀이 정한 JSON 스펙으로 Kafka에 보내 달라고 요청한다. Flink가 **처리 시간**을 붙여 일·시간 파티션에 저장한다. 이벤트 타임과 워터마크를 쓰지 않는 이유는 재처리해도 최종 지표가 변하지 않는 멱등성을 위해서다. 지연 데이터가 다음 파티션에 들어가는 예외는 Spark 소싱 단계에서 보정한다.

서버 로그에도 고유 ID가 있어 UPSERT로 중복을 제거할 수 있지만 양이 너무 많아 최적화 비용이 이점을 넘는다. 중복 제거는 어차피 Spark 지표 계산에서 하니 **APPEND**를 택했다. 그리고 Kafka lag을 줄이려 체크포인트를 3분에서 더 짧게 하고 싶은데, 그러면 파일이 작아진다. 해법은 시간 단위 파티션을 두고 **매시간 직전 파티션에 compaction·스냅샷 만료·고아 파일 제거**를 돌리는 것이다.

## 압축 실험: zstd 레벨을 올려도 되는가

Iceberg 기본은 Parquet + zstd(1.4.0부터 gzip에서 변경). 서버 로그는 DB 로그의 수십 배라 압축 레벨까지 봐야 했다. 일 평균 30억 건, 초당 5만 건 토픽으로 실험했다.

**CPU.** Flink FlameGraph에서 압축 메서드가 차지하는 비율은 레벨 1에서 10% 이하, 3에서 9~14%, 6에서 18~27%, 9에서 29~38%, 12에서 41~53%, 15에서 75~84%. 그런데 TaskManager 전체 CPU 사용률에는 큰 차이가 없었다.

**지연.** 4시간 커밋 레코드 수는 레벨 간 최대 0.6% 차이, 1시간 lag 감소량은 0.3% 차이, Flink 연산자 처리율은 약 46,400 msg/s로 0.3% 차이. 지연은 사실상 없다고 판단했다.

**크기.** 주중 하루치 합계(체크포인트 1분 기준).

| 레벨 | 1 | 3 | 6 | 9 | 12 | 15 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 크기 | 473.4GB | 453.5GB | 402.9GB | 364.4GB | 358.1GB | 347.1GB |
| ORC(750.3GB) 대비 감소 | 36.9% | 39.6% | 46.3% | 51.4% | 52.3% | 53.7% |

9 이후로는 체감이 작다. 로그가 적은 토픽(9,000만·2,000만·200만 건)에서는 레벨 9의 ORC 대비 감소가 24~32%로 낮았다. 그리고 중요한 대조 실험: **Iceberg 없이 Parquet + zstd로 바로 쓴 것(469.1GB)과 Iceberg 레벨 3(469.6GB)이 같았다.** 크기 감소는 Iceberg가 아니라 포맷과 코덱에서 온다. Spark 하루치 소싱 시간은 레벨 3과 9 사이 약 4분(10%) 차이였지만 compaction을 안 한 상태였고 실제로는 시간 단위로 소싱하니 더 줄 것으로 봤다.

## 파티션: 타임존 함정

서버 로그의 처리 시간을 timestamp 타입에 넣고 hour transform을 쓰면 시 단위 파티션이 되지만 **타임존 문제**가 생긴다. Iceberg는 시간 컬럼 값을 항상 UTC로 간주하고 타임존 처리는 엔진(Spark·Trino) 몫이다. Flink가 KST로 만든 값을 넣으면 값은 그대로인데 UTC로 인식돼, KST로 설정된 Spark 세션에서 읽으면 +9시간이 붙는다. 생성 시 -9시간을 빼면 조회는 맞지만 hour transform 파티션은 9시간 전 파티션(15시 로그가 06시 파티션)에 들어간다. 팀은 타임존을 아예 피해서 **분 이하를 버린 문자열**로 저장하고 identity transform을 걸어 시 단위 파티션처럼 동작하게 했다.

## 최적화: 두 로그의 차이

compaction 전략은 둘 다 binpack이다. DB 로그는 전체 테이블 조회, 서버 로그는 전날 하루치 조회가 주 패턴이라 sort·z-order가 필요 없다. 설정에서 놓치기 쉬운 것 둘.

- `rewrite-all=true`. 안 켜면 기본 `min/max-file-size-bytes`(target의 0.75~1.8배)에 드는 파일이 후보에서 빠지고, 그 파일이 참조하는 삭제 파일이 리텐션이 지나도 안 지워진다.
- `partial-progress.enabled=true`. compaction 중에도 커밋되지만 매니페스트가 많이 생긴다. 중간에 쿼리를 안 돌리는 환경이면 false를 권한다.

| 설정 | DB 로그(운영) | 서버 로그(테스트) |
| --- | --- | --- |
| 적재 | UPSERT | APPEND |
| 파티션 | PK bucket(5) | 처리 시간 문자열 identity |
| target-file-size | 256MB(HDFS 블록) | 256MB |
| max-concurrent-file-group-rewrites | 5(bucket과 동일) | - |
| compaction 주기·대상 | 일 2회, 모든 파티션 | 매시간, 직전 시간 파티션 |
| 커밋 주기 | 10분 | 1분 |
| compaction 후 딜레이 | 30분(주기 3배) | 3분 |
| 스냅샷 만료·고아 파일 리텐션 | 20분(주기 2배) | 2분 |
| DELETE 쿼리 | 불필요 | 필요 |

딜레이와 리텐션을 체크포인트 주기의 배수로 잡은 것은 경험적 조율이다. 서버 로그는 1분 체크포인트로 lag을 기존의 1/3 이하로 낮추면서, 약 6MB로 쌓인 파일이 최적화 후 약 256MB로 합쳐지는 것을 확인했다. 마지막 차이가 중요하다. APPEND는 스냅샷 만료만으로 옛 데이터가 지워지지 않아 **주기적 DELETE 쿼리**로 리텐션을 따로 관리해야 한다.

모니터링은 참조 상태 파일(쿼리 성능에 직결)과 스토리지의 물리 파일(고아 포함) 두 관점으로 지표를 수집한다.

## 읽고 남는 질문

- 처리 시간을 문자열로 저장하는 우회는 동작하지만, Iceberg 1.x의 `timestamp_ntz`(타임존 없는 timestamp)를 쓰면 hour transform을 유지하면서 문제를 피할 수 있다. 검토했는지 궁금하다.
- 압축 레벨은 어디로 정했는지 최종 결론이 없다. 표를 보면 9가 균형점으로 보이는데 명시가 있으면 좋겠다.
- 서버 로그의 시간 단위 DELETE는 APPEND 테이블에서 삭제 파일(positional/equality delete)을 만드는지, 파티션 drop으로 처리하는지에 따라 비용이 크게 다르다. 그 방식이 없다.

## 한 줄로 가져가기

같은 테이블 포맷이라도 "갱신되는 데이터"와 "쌓이기만 하는 데이터"는 다른 물건이다. 전자는 키 기준 버킷과 느린 커밋, 후자는 시간 기준 파티션과 빠른 커밋 + 부지런한 compaction + 명시적 삭제로 다뤄야 한다.
