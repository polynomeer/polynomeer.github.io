## 한 줄 요약

카카오 로그 수집 플랫폼 kemi-log는 수년간 Fluentd를 중심으로 돌았다. 설정 관리 시스템(tug)을 직접 만들고 Fluentd에 기여도 했지만, Ruby라 멀티코어를 못 쓰고, match 구문이 많으면 메모리가 90%까지 차고, tag마다 Kafka 커넥션이 생겨 4,000개에 이르고, 설정을 바꾸면 재시작에 버퍼 디렉터리까지 옮겨야 하는 구조적 한계가 있었다. 사내 수만 대 서버의 Fluentd 에이전트를 한꺼번에 바꿀 수는 없으니, **Fluentd 프로토콜을 그대로 받는 수집기 Logriver를 Go로 새로 만들어** aggregator만 교체했다. 결과는 메모리 90% → 15%, 커넥션 4,000 → 200, 서버 50% 절감.

## 배경: kemi-log의 구조와 tug

aggregator는 두 층이다. 1층은 사용자로부터 로그를 받아 버퍼링만 하고, 2층은 1층에서 받아 스토리지(HDFS·Kafka 등)로 보낸다. 스토리지 전송이 자원을 많이 쓰고 문제가 잦아서, 한 층이면 특정 스토리지 장애가 모든 aggregator를 흔들기 때문이다. 2층은 스토리지별·대형 서비스별로 그룹을 나눠 한쪽 장애가 다른 적재에 번지지 않게 했다.

Fluentd는 설정이 파일이라 새 로그를 받거나 바꿀 때마다 파일을 고치고 재시작해야 한다. 처음엔 Ansible로 했고, 실수를 줄이려 여러 Fluentd를 클러스터로 묶어 중앙에서 관리하는 tug(tug-server + 각 서버의 tug-agent)를 만들었다. 그래도 한계에 부딪혔다.

## 왜 오픈소스 대안이 아니라 자체 개발인가

새로 나온 오픈소스들을 검토했지만 두 가지가 걸렸다. 첫째, 사내 표준이 Fluentd라 수만 대 서버에 에이전트가 깔려 있고 이것을 동시에 바꾸는 것은 불가능하다. 다행히 Fluentd 통신 프로토콜은 공개돼 있으니 **같은 프로토콜로 받는 수집기**를 만들면 에이전트는 손대지 않아도 된다. 둘째, 대규모 클러스터를 중앙에서 관리하는 기능을 가진 오픈소스가 없어서 무엇을 도입하든 tug 같은 시스템이 또 필요하다. 그래서 처음부터 중앙 제어 구조를 가진 Logriver(에이전트 + 컨트롤러)를 만들었다.

## 자세히 보기: 무엇을 어떻게 고쳤나

**무중단 설정 변경.** Fluentd는 설정 적용에 graceful shutdown 후 재시작이 필요하고 잔여 데이터가 많으면 오래 걸린다. Logriver 에이전트는 컨트롤러에서 새 설정을 받아 **새 설정을 가진 고루틴을 띄워 트래픽을 받게 하고 기존 고루틴을 graceful하게 종료**한다. 같은 포트를 쓰도록 TCP 서버에 `SO_REUSEPORT`를 준다. 재시작도 끊김도 없다. 검증용으로 트래픽 발생기와 검증기를 직접 만들어 단위 시간당 로그가 스토리지에 다 들어갔는지 하나씩 확인했다.

**CPU.** Ruby 프로세스는 코어 하나만 쓴다. CPU가 남는데도 load가 수백까지 올라갔다. Go로 옮기자 같은 데이터에 CPU 사용량은 줄고 load는 5를 넘지 않았다. flame graph에서 가장 큰 부분은 버퍼 파일 읽고 쓸 때의 JSON 인코딩/디코딩이었고, 여러 라이브러리를 비교해 go-json을 골랐다. 단, go-json의 스트림 디코딩에 미해결 이슈가 있어 **쓰기에만 go-json, 읽기는 표준 라이브러리**를 쓴다.

**메모리 90% → 15%.** Fluentd의 HDFS·Kafka 플러그인은 match 구문이 많을수록 메모리를 많이 쓴다. 서비스 구분 때문에 match가 많았고, 이미 한 match에서 여러 서비스를 처리하도록 1,000개 → 30개로 줄여 워커당 메모리를 30% → 3%로 낮춘 상태였다. 그래도 서버 메모리의 90%에 이르렀다. Logriver는 match를 일괄 처리하도록 만들어 15%로 낮췄다.

**커넥션 4,000 → 200.** Fluentd는 tag 단위로 처리해서 Kafka로 보낼 때 tag마다 커넥션을 만든다. Fluentd 서버가 늘면 Kafka 쪽 커넥션이 비례해 는다. Logriver는 tag 수와 무관하게 **브로커당 커넥션을 재사용**한다.

**버퍼 통합.** Fluentd는 설정 id로 버퍼 디렉터리를 만드는데 tag가 수천 개라 디렉터리도 수천 개다. 설정을 바꾸면 id가 바뀌어 디렉터리명이 바뀌고, 재시작하면 옛 디렉터리의 데이터를 처리하지 않는다. 유실을 막으려면 사람이 옛 버퍼를 새 디렉터리로 옮겨야 했다. Logriver는 tag와 무관하게 버퍼를 통합 관리한다.

**RateLimit.** 기념일·사건으로 트래픽이 급증하면 증설하면 되지만 DDoS면 다 처리하면 안 된다. 커넥션당 트래픽 제어를 넣었다.

**메트릭 내장.** tag별 건수·크기를 별도 플러그인으로 Prometheus에 넣던 것을 내장했다.

## 실서비스 검증: 순서가 보장되지 않는 환경에서 같음을 증명하기

운영 트래픽을 미러링해 테스트 환경으로 받을 수는 있었지만, 여러 서버를 거치니 들어오는 순서도 적재 순서도 보장되지 않았다. 검증기를 다시 만들어 로그의 timestamp로 **1분 단위로 묶어** 건수를 비교했고, 시작 시점 차이는 있어도 단위 시간당 건수가 같아지는 것을 확인했다.

내용도 같은지 봐야 했다. 분당 30만 건이 넘어 메모리에 들고 1:1 매칭하는 것은 불가능하므로 해시로 비교했다. 그런데 JSON은 멤버 순서가 바뀌면 같은 데이터라도 해시가 달라진다. 그래서 JSON을 한 문자열로 만들어 **알파벳순으로 정렬한 뒤** 해시했다. 이 과정에서 인코딩 이슈 몇 건을 찾아 고쳤다.

## 숫자

| 항목 | Fluentd | Logriver |
| --- | --- | --- |
| 서버 메모리 | 약 90% | 약 15% |
| Kafka 커넥션 | 최대 약 4,000 | 약 200 |
| 시스템 load | 수백 | 최대 5 이하 |
| 서버 사용량 | 기준 | 50% 절감 |

## 결론: 무엇을 내재화할 것인가

오픈소스는 초기 구축이 빠르지만, 여러 해 운영하면 회사 고유의 정책·기능이 필요해지고 이를 어떻게 넣을지 고민하게 된다. 기여가 원칙이지만 프로젝트 활성도가 떨어지거나, 메인테이너가 거부하거나, 사내에서만 필요한 기능은 기여 자체가 불가능하다. 카카오의 선택이 좋은 점은 **Fluentd의 모든 기능을 다시 만들지 않고, 수년간 운영하며 실제로 쓰고 있는 필수 기능만 골라 내재화**했다는 것이다. 무엇을 쓰는지 알고 있었기에 가능한 전략이다.

## 읽고 남는 질문

- 에이전트 쪽 Fluentd는 남아 있다. 수만 대의 Ruby 에이전트가 여전히 코어 하나로 도는 셈인데, 장기적으로 에이전트도 바꿀 계획인지, 아니면 에이전트는 부하가 작아 그대로 둘 만한지가 궁금하다.
- 무중단 설정 변경에서 기존 고루틴이 graceful 종료하는 동안 버퍼에 남은 데이터의 소유권이 어떻게 넘어가는지(통합 버퍼라 자연히 되는지)가 있으면 이해가 더 완결된다.
- 커넥션 200개는 브로커 수 × 무엇인지가 없다. 브로커당 1개라면 브로커가 200대라는 뜻인데, 그 규모면 처리량 수치도 같이 있으면 좋겠다.

## 한 줄로 가져가기

거대한 시스템의 부품을 바꿀 때는 "인터페이스(프로토콜)는 유지하고 구현만 바꾼다"가 가장 싼 길이고, 무엇을 다시 만들지는 기능 목록이 아니라 실제 사용 목록에서 골라야 한다.
