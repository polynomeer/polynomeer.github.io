## 한 줄 요약

카카오의 자체 모니터링 솔루션 MATRIX(OpenTelemetry·APM·에러 로그·Prometheus를 묶은 멀티 테넌트 서비스)에 AI를 붙인 이야기다. 모니터링 사이클(모니터링 → 감지 → 원인 분석 → 조치 → 반영)의 각 단계에 LLM을 넣되, 설계에서 챙긴 것이 넷이다. **롤(Role)** 도메인으로 시스템 메시지·LLM 체인(fallback)·파라미터·응답 포맷을 재배포 없이 바꾸고, LLM 사용을 ElasticSearch에 로깅해 비용까지 추적하며, 외부 LLM에 보내기 전 JDBC URL 같은 **민감 정보를 랜덤 토큰으로 치환**했다가 응답에서 역매핑하고, 서비스 상태는 절대값이 아니라 **24시간 전·일주일 전과의 상대 비교**로 판단한다. 사례는 인시던트 AI 리포트, 배포 전후 자동 감시(체인지 트래킹), AI 온콜, 코드 튜닝 에이전트다.

## 매트릭스 AI: 여러 LLM 앞의 교두보

LLM은 춘추전국시대라 상황에 맞는 모델을 고르는 것이 중요해졌다. 매트릭스 안팎에서 AI 기능을 쓰려면 반드시 매트릭스 AI를 거친다. 그 중심이 **롤**이다. 인시던트 관리자, 에러 로그 분석가, 형상 변경 추적자 같은 역할마다 롤을 정의하고, 클라이언트는 롤을 고른 뒤 사용자 메시지를 붙여 대화한다. 롤의 속성은 코드, 시스템 메시지, LLM 체인, 파라미터, 응답 포맷, 요청 제한 간격이며 어드민 화면에서 만들고 고친다.

- **LLM 체인**: 가장 널리 쓰이는 LLM도 자주 장애가 난다. 롤마다 하나 이상의 대체 LLM을 두거나 같은 LLM의 다른 모델로 체이닝해, 모델이 교체되거나 응답을 못 해도 이어 간다.
- **파라미터**: temperature, top_p 같은 값은 여러 번 조정해야 최적 조합이 나온다. 이것이 번거로우면 품질을 적당히 타협하게 된다. 권한 있는 사용자가 쉽게 바꾸고, 프리뷰 모델이 예고 없이 빠져도 재배포 없이 대응해야 한다.
- **로깅**: 클라이언트 식별, 요청(모델·파라미터), 응답(답변·지연), 토큰 사용량을 ElasticSearch에 남긴다. 누가 언제 왜 썼는지, 사용량과 예상 요금, 답변 품질 추이, 파라미터 조정 근거가 여기서 나온다.

## 사례 1: 인시던트 AI 리포트

기존 알람은 "SlowSQL 알람, 이 파드에서 1회"였다. 감지 다음의 원인 분석 시간을 줄이려고 **Agent Alert Analyzer** 롤을 만들었다. APM의 트랜잭션 프로파일(실행 시간, 콜스택, SQL, 외부 API 호출)을 LLM에 주면 [요약]·[트랜잭션]·[프로파일 분석]·[조치 방안] 네 섹션으로 답한다. 예시에서는 전체 응답 11,354ms 중 SQL 11,327ms, 그중 특정 CTE 쿼리가 8,003ms라는 것을 짚고 EXPLAIN 확인·CTE 재검토·캐싱 검토를 제안한다. 느린 SQL, 커넥션 지연, 네트워크 지연, 특정 예외, 과도한 SQL·fetch 건수를 다룬다.

포맷은 시스템 메시지에 비교적 간단히 정의했는데 **운영에서 한 번도 깨진 적이 없다**고 한다. 시스템 메시지는 Context(프로파일에 무엇이 있는지) → Task(한국어로 분석 리포트) → Conditions(심각한 저하가 없으면 정상이라고 말해도 됨, 외부 API 지연이면 주소 포함) → Output Format → Constraints(분석·조치는 각 3개 이하) 구조다.

**민감 데이터.** SQL, HTTP URL, JDBC URL은 개인정보가 아니어도 사내 시스템 구조의 힌트라 외부 노출에 여러 번 재검토 의견이 나왔다. 해법은 `jdbc:mysql://real-database-url.com:3306/real_db`를 `jdbc:mysql://xcu2t3cc3xz:3306/c4ysd`처럼 랜덤 토큰으로 바꿔 보내고, 응답에서 토큰을 원래 값으로 역매핑해 사용자에게 주는 것이다.

## 사례 2: 체인지 트래킹

"아무것도 안 건드리면 아무 일도 안 난다"지만 배포를 멈출 수는 없다. 장애를 100% 막을 수 없다면 빨리 감지하고 대응해야 하고, 배포 전후가 그 시점이다. 카카오릴리즈(전사 배포 관리, 사전 계획과 리뷰어 승인)와 연동해 AI가 사람 대신 감시한다. 배포 30분 전, 배포 후 10분·30분·1시간, 4시간·8시간, 12시간·24시간. 배포 전 점검에서 문제가 없을 때만 배포가 진행되고, 직후에는 촘촘히, 갈수록 성기게 본다.

상태 판단 데이터는 처리량과 에러 요청, 응답 시간(p50/p90/p95), 에러 로그 레벨 통계, Top Issue, 인시던트 알람 이력이다. 핵심은 **절대값으로는 판단할 수 없다**는 것이다. p50이 2초라도 원래 그런 서비스일 수 있다. 그래서 24시간 전·일주일 전과 비교해 에러가 급증했거나 응답이 현저히 늘었으면 비정상으로 본다.

LLM 응답은 텍스트가 아니라 **JSON 스키마**로 받는다. "에러 트랜잭션이 지난주보다 크게 늘었다"는 문장은 애플리케이션이 더 할 일이 없지만, `{application_name, issue_start_time, issue_end_time, issue_metric: "error_transaction"}`이면 해당 메트릭을 추가 조회해 덧붙일 수 있다. 실제 스키마는 애플리케이션 배열(name, applicationId, state ∈ {STABLE, MOSTLY_STABLE, UNSTABLE}, metric ∈ {TRANSACTION, ALERT, ISSUE}, comment)과 전체 state·comment로, `additionalProperties: false`다. 미리 정의한 키를 보고 LLM이 정확히 채워 넣는다는 점을 원문이 놀라워한다.

## 사례 3·4: AI 온콜과 코드 튜닝 에이전트

체인지 트래킹의 건강성 감시를 확장한 것이 AI 온콜이다. 365일 24시간 온콜 담당자를 두는 것은 연휴·워크샵 때 특히 어렵다. AI 온콜은 건강성 모니터링, 사용자 문의 대응, 담당자 알림을 맡고, 심각하면 전화 API와 TTS로 **직접 전화**를 건다.

코드 튜닝 에이전트는 계획 단계다. 매트릭스가 MCP 서버를 열어 에러 스택트레이스·메시지·코드, 느린 트랜잭션의 스택트레이스 집합, 느린 SQL을 코딩 에이전트에 주면, 기준 브랜치와 연계해 코드를 고치고 PR까지 만든다. 매일 새벽 GitHub Actions로 돌리면 담당자는 출근해서 PR을 검토·병합만 하면 된다는 그림이다.

결론은 모니터링·감지·원인 분석·조치까지는 AI에 위임할 수 있게 됐고, '반영'은 아직 과제라는 것이다.

## 읽고 남는 질문

- 토큰 치환은 URL·SQL의 식별자 수준인데, SQL 안의 테이블·컬럼명이나 스택트레이스의 패키지명도 구조 힌트다. 어디까지 치환하는지, 치환하면 LLM의 분석 품질이 얼마나 떨어지는지가 궁금하다.
- 상대 비교는 주간 패턴이 규칙적일 때 잘 맞는다. 명절이나 이벤트처럼 지난주와 다른 것이 정상인 날은 오탐이 늘 텐데 그 보정이 있는지.
- 인시던트 AI 리포트의 정확도(제안한 원인이 실제 원인이었던 비율)나 원인 분석 시간 단축 수치가 없다. 사례집이라 그럴 수 있지만 "포맷이 한 번도 안 깨졌다"만큼 "분석이 몇 번 맞았다"도 알고 싶다.

## 한 줄로 가져가기

운영에 LLM을 붙이는 일의 대부분은 프롬프트가 아니라 그 주변이다. 모델을 갈아 끼울 수 있는 롤, 비용을 볼 수 있는 로그, 밖으로 나가기 전의 토큰 치환, 파싱할 수 있는 JSON 응답, 그리고 "정상"을 절대값이 아니라 과거의 자기 자신과 비교해 정의하는 것.
