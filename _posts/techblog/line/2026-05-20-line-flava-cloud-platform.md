## 한 줄 요약

구 LINE의 Verda(2016~, 하이퍼바이저 11,000+, VM 130,000+, OpenStack 클러스터 4개, 오브젝트 스토리지 200PB+)와 구 Yahoo Japan의 YNW(2013~, 하이퍼바이저 27,000+, VM 220,000+, OpenStack 클러스터 160개+, 100PB+)를 차세대 기반 **Flava**(2023 하반기 착수, 2025 출시, VM 9,000+)로 통합하고 있다. 설계 철학은 "장애를 전제로"(VM 루트 디스크는 임시, 가용성은 애플리케이션과 함께, 원인 규명보다 IaC로 즉시 재구축), 운영은 IaC 완전 자동화와 AZ 단위 배포, 거시(Prometheus/Grafana)와 미시(커널 트레이스·패킷 캡처)를 오가는 관찰. 기술은 OpenStack·Envoy·eBPF/XDP·FRR·Ceph 같은 OSS를 쓰되 **업스트림에 기여**하고(SRv6 BGP를 FRR·Linux 커널에 커밋), 범용 x86으로 네트워크 제품까지 돌리며, OSS로 안 되는 것(오브젝트 스토리지 Dragon, SDN 컨트롤 플레인)은 풀 스크래치. Flava에서 바꾼 것은 전용 환경 폐지 → 단일 리소스 풀, 과도한 커스터마이징 → **업스트림 추종**, **VPC 기본화**, 개발 환경 리소스 유효 기간 필수화다.

## 설계 철학: 장애를 전제로

서비스 개발 속도를 극대화하려면 인프라 단독으로 과도한 가용성을 보장하는 데 집착하지 않는다. 세 가지가 핵심이다.

- **무상태성**: VM 루트 디스크의 데이터는 일시적이라 정의하고 영속 데이터는 외부 스토리지로 분리한다.
- **애플리케이션 주도 가용성**: 인프라와 애플리케이션 구성을 조합해 신뢰를 확보하고 인프라 복잡성을 없앤다.
- **신속한 복구**: 장애 시 최우선은 현상 복구가 아니라 서비스 지속이다. 원인 규명에 시간을 쓰기보다 IaC로 환경을 즉시 재구축한다.

이 철학은 사용자(사내 개발 조직)의 이해가 있어야 성립하므로 지속적으로 알리고 컨설팅한다.

## 운영: 자동화와 관찰

OS 설정, 패키지, 네트워크 투입까지 모든 구성을 코드화해 CI/CD로 적용하고, 배포는 **AZ 단위**로 실행해 장애 영향을 국소화한다. 모니터링은 두 층이다. 숲(Prometheus/Grafana와 자체 대시보드로 전체 건전성·트렌드)과 나무(이상 감지 시 커널 레벨 트레이스, 패킷 캡처). 도구와 함께 그것을 다뤄 전체에서 근본 원인까지 추적하는 팀의 기술력이 핵심이라고 한다.

수만 대 하이퍼바이저와 PB급 스토리지에서는 매일 어딘가 하드웨어가 고장 난다. 고장 감지 → 데이터센터 현지 작업자 요청 → 교체 후 클러스터 재투입까지 대부분 자동화했고, 남은 예외 패턴은 LLM으로 더 자동화할 계획이다.

## 기술과 마인드: 소프트웨어 정의, OSS 기여, 풀 스크래치

- **OSS 활용과 기여**: OpenStack과 Ceph에 업스트림 패치를 보내고, Flava의 VPC에 필요한 SRv6 BGP 기능을 설계·구현해 FRRouting과 Linux 커널에 커밋했다. 필요한 기능을 자체 개발에 그치지 않고 OSS 본체에 넣는 이유는 독자 패치의 장기 유지보수 비용을 줄이고 커뮤니티와 함께 발전시키기 위해서다.
- **범용 하드웨어**: 컴퓨트 노드뿐 아니라 VPC·DNS·LB 같은 네트워크 제품도 고가 전용 장비 대신 x86 서버에서 돌린다.
- **풀 스크래치**: HDD 용량 효율과 운영성을 최우선으로 설계한 오브젝트 스토리지 Dragon, SDN 컨트롤 플레인·LB 헬스체크 에이전트·서비스 디스커버리를 Rust·Go·Python으로.

## Flava에서 바꾼 것

| 구 클라우드 | Flava |
| --- | --- |
| 특정 제품·서비스용 전용 환경(클러스터·리소스 풀)이 다수 → 용량 관리가 퍼즐, 활용 효율 저하 | **전용 환경 폐지**, 거의 모든 제품을 하나의 거대 리소스 풀로 |
| OpenStack을 과도하게 커스터마이징 → 업그레이드 곤란 | **업스트림 추종** 아키텍처 |
| 방화벽·전용 VLAN으로 물리 분리, 보안 환경 준비에 수개월 | **VPC 기본화**. 멀티 테넌트에서 통신이 간섭하지 않는 모델을 표준으로. 전사 규모 VPC 기본화는 최초 시도 |
| | 개발 환경 리소스에 **유효 기간 필수** → 좀비 리소스 자동 삭제. 오브젝트 스토리지는 High Performance/Scalable 등 버킷 클래스를 엔드포인트 변경 없이 전환 |

과제는 셋이다. 최소 제품만 출시한 상태라 기능 확장이 시급하고, 속도를 우선하다 출시 후 버그와 미고려 사항이 드러났으며, 무엇보다 구 기반에서의 **마이그레이션**이다. 투명한 이전과 도구로 부담을 줄이지만 수동 대응이 남고, 신구 기반 중복 투자 기간을 어떻게 줄일지가 이제 시작된 도전이다.

## 읽고 남는 질문

- Verda와 YNW는 OpenStack 클러스터 수가 4 vs 160+로 운영 철학이 크게 달랐을 텐데(대형 소수 vs 소형 다수), Flava가 어느 쪽을 택했고 왜인지가 이 통합의 핵심 결정일 텐데 언급이 없다.
- VPC 기본화의 데이터 플레인이 SRv6 기반 x86 소프트웨어 라우팅이라면 그 성능(처리량, 지연, 컴퓨트 노드의 CPU 오버헤드)이 "극히 높은 신뢰성과 성능이 요구된다"는 문장 뒤에 있어야 한다.
- 35만 VM을 옮기는 마이그레이션의 방식(라이브 마이그레이션인지, 재생성인지)과 목표 기간, 그리고 그 기간 동안의 중복 투자 규모가 인프라 관점에서 가장 궁금하다.

## 한 줄로 가져가기

두 거대 클라우드를 합칠 때 새로 만든 것보다 버린 것이 더 중요하다. 전용 환경을 버리고, 커스터마이징을 버리고, 물리 분리를 버리고, 그 자리에 단일 풀·업스트림 추종·VPC 기본을 두면서, 부족한 것은 OSS 본체에 넣어 남에게도 쓰이게 하는 것이 이 팀의 방식이다.
