## 한 줄 요약

LY의 차세대 프라이빗 클라우드 Flava에서 데이터베이스는 쿠버네티스 오퍼레이터 패턴으로 제공된다. IaaS 자원(VM, 스토리지, 도메인)은 **인프라 오퍼레이터**가 쿠버네티스 커스텀 리소스로 추상화하고, 그 위에서 각 DBMS는 **API 서버·매니저·에이전트** 세 컴포넌트가 커스텀 리소스 하나를 놓고 "선언한 상태"로 수렴시킨다. 기존 Verda(구 LINE)와 YNW(구 Yahoo Japan)의 DBMS를 통합하면서 100GiB 단위 스토리지, 블록 스토리지 최대 5TiB, TDE·TLS 기본, Custom DB Role, Parameter Group, Restore backup 같은 기능을 더했다. 새 플랫폼의 역할은 마이그레이션 도구(MySQL용 DMB, 2026년 2분기까지 전 DBMS 목표)까지이고, 다음은 서버리스(TiDB, OpenSearch), Slack 봇 기반 DBA as a Service, 오토 스케일링이다.

## 배경

Verda와 YNW라는 두 거대 클라우드를 Flava로 통합하는 중이고, DBaaS는 그 안에서 DB를 서비스로 제공하는 계층이다. 저자는 "새 DBaaS를 만들어 주는 것으로 끝이 아니라 기존 플랫폼에서 쉽게 옮겨 올 방법까지 제공하는 것이 신규 플랫폼의 몫"이라고 못 박는데, 이 글은 그 관점에서 아키텍처 → 개선점 → 마이그레이션 → 미래 순으로 정리돼 있다.

## 아키텍처: 선언하면 컨트롤러가 수렴시킨다

**오퍼레이터 패턴**은 운영자가 도메인 지식으로 손으로 하던 작업을 컨트롤러 코드로 만들어, 사용자가 "이런 상태의 DB가 필요하다"고 선언하면 컨트롤러가 그 상태에 도달할 절차를 계속 수행하는 방식이다. 절차 지향보다 구현 난이도는 높지만 운영이 편하다. 문제가 나면 커스텀 리소스의 사양(spec)과 상태(status)를 비교하고 컨트롤러 로그를 보면 원인이 나온다.

DB 클러스터 하나에는 VM 여러 대, 스토리지, 도메인이 필요하다. IaaS API를 직접 호출하는 대신 **인프라 오퍼레이터**가 IaaS 자원을 쿠버네티스 리소스로 다루게 해 준다. `server.yaml`에 VM을 선언하면 VM이 생긴다. DBaaS는 IaaS API나 호출 순서를 몰라도 된다.

| 계층 | 역할 |
| --- | --- |
| DBaaS (MySQL, Redis, …) | DBMS 종속 비즈니스 로직 |
| 인프라 오퍼레이터 | IaaS를 쿠버네티스 리소스로 추상화 |
| IaaS | VM, 스토리지, 네트워크 |

책임이 분리되니 IaaS 자원을 여러 DBMS가 같은 방식으로 다루고, 각 DBaaS 개발자는 DBMS 로직에만 집중한다.

각 DBMS는 클러스터를 커스텀 리소스 하나로 표현한다. 예시는 프라이머리 + 복제 멤버 1개, VM 4 vCPU·16GiB·100GiB 디스크, 별도 200GiB 블록 스토리지. 이를 참조하는 세 컴포넌트가 있다.

| 컴포넌트 | 역할 |
| --- | --- |
| API 서버 | 사용자용 REST API. 커스텀 리소스 생성·수정·삭제 |
| 매니저 | 커스텀 리소스 변화에 맞춰 spec과 status가 일치하도록 계속 조정(reconcile)하는 컨트롤러 |
| 에이전트 | DB가 도는 VM 안에서 실행. OS·DB 명령 수행, 프로비저닝 로직에 깊이 관여 |

MySQL 클러스터 생성을 따라가면, 사용자가 API를 호출하면 API 서버가 MySQL 커스텀 리소스를 만들고(복제 구성과 서버 사양이 spec에 기록되어 etcd에 저장), 매니저가 이를 감지해 인프라 오퍼레이터의 서버 리소스를 만들어 VM을 띄우고, VM이 준비되면 에이전트가 복제 명령을 수행한다.

## Flava에서 나아진 것

- **DBMS 종류 확대**: Verda와 YNW가 각각 제공하던 DBMS를 통합.
- **유연한 스토리지**: 100GiB 단위 구성, 블록 스토리지 사용 DBMS는 최대 5TiB. 기존에는 VM 로컬 디스크라 하이퍼바이저의 VM 스펙에 용량이 묶였고 그 한계 때문에 샤딩을 검토하는 경우가 있었다. 블록 스토리지 자체는 5TiB 이상도 가능하지만 기존 사용 사례 분석에서 5TiB로 대부분이 커버됐고 블록 스토리지 서버 단편화를 막기 위해 상한을 정했다.
- **통일된 경험**: 모든 DBaaS가 같은 아키텍처와 UI. MySQL에서 서버 사양을 바꿔 봤으면 Redis도 같은 방식으로.
- **보안 기본값**: TDE와 TLS를 DBaaS 차원에서 제공.
- **편의 기능**: Custom DB Role(원하는 권한의 DB 사용자를 만들고 재사용), Database Parameter Group(파라미터 세트 재사용), Restore backup(특정 백업으로 새 클러스터 생성, 장애 복구나 실데이터 성능 테스트용).

사용자 만족도 조사 결과를 반영한 것이고 결과적으로 사내 조사에서 높은 점수를 받았다고 한다(수치는 없음).

## 마이그레이션도 플랫폼의 일

같은 DBMS 사이의 이전 방식 세 가지를 먼저 정리한다.

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| 덤프 & 복구 | 가장 단순 | 정합성을 위해 애플리케이션 중단 필요 |
| 복제 | DBMS 자체 복제로 정합성 확보, 페일오버로 전환 | 페일오버 시점 최소 중단, 엔드포인트 변경 등 절차가 길고 복잡 |
| CDC | Kafka 등으로 논리 복사, 토폴로지 한계를 넘음 | 별도 시스템 구축 |

마이그레이션은 운영자와 개발자가 긴밀히 협업해야 하는 일이고 대규모 DB를 운영자 혼자 다 옮기는 것은 불가능에 가깝다. 그래서 **개발자가 직접 쓰는 도구**가 필요하다. 현재는 MySQL용 **DMB(data migration bridge)**만 있고, 2026년 2분기까지 Flava의 모든 DBMS에 대해 도메인 지식 없이 UI 지시만 따르면 되는 도구를 제공하는 것이 목표다.

## 미래

- **기존 DBMS 지원 확대**: YNW의 Fractal DB, DBA 지원으로 쓰던 HBase도 DBaaS로.
- **보안 등급별 격리**: 데이터 중요도에 따른 분리 관리 환경을 단계적으로 확충하되, 보안 등급에 따라 사용성이 달라지지 않게.
- **서버리스 DBaaS**: 독립 클러스터는 안정적이지만 이중화 때문에 플랫폼 전체 활용률이 낮다. 멀티 테넌트 공통 인프라로 활용률을 올리고 업그레이드·백업을 표준화한다. 우선 MySQL 호환 TiDB 서버리스와 Serverless OpenSearch. 고성능·전용 인프라가 필요한 워크로드는 여전히 독립 클러스터.
- **인텔리전트 DBaaS (DBA as a Service)**: DBA와 상담하던 것을 Slack 봇으로. 알람 분석(지표·로그로 원인 파악 후 대응 제안), 이슈 대응("13:05부터 db-prod-01 쿼리 지연이 늘었는데 왜?"에 답하고 후속 질문도), 문의 대응(예상 QPS·데이터 크기로 사양·구성·백업 정책 제안). 콘솔 리포트 탭은 백업 시간이 배치와 겹치면 변경 추천, 리소스 절감 제안, 느린 쿼리 패턴 분석과 인덱스 추천, 개인정보로 판단되는 데이터 발견 시 암호화 제안.
- **오토 스케일링**: CPU·메모리·스토리지·커넥션 지표 기반 정책으로 자동 확장·축소. AI 에이전트가 사용 패턴을 보고 정책 자체의 적절성을 검토하는 것까지.

## 읽고 남는 질문

- 에이전트가 VM 안에서 도는 구조라 DBaaS 자체의 배포(에이전트 업그레이드)가 곧 수천 대 VM의 롤아웃이 된다. 에이전트 버전 관리와 호환성은 어떻게 하는지가 운영에서 가장 큰 이슈일 텐데 언급이 없다.
- 5TiB 상한의 근거로 "서버 단편화 방지"를 들었는데, 5TiB를 넘는 소수의 사용자는 어떤 경로(샤딩 안내? 예외 승인?)를 타는지.
- 서버리스 TiDB와 독립 클러스터 MySQL 사이의 마이그레이션도 DMB 범위인지. "MySQL 호환"이 마이그레이션 관점에서 어디까지 호환인지가 실제 채택을 가른다.
- DBA as a Service가 제안까지 하는 것과 실행(파라미터 변경, 인덱스 생성)까지 하는 것은 다른 문제다. 어디까지 자동 실행을 허용할 계획인지.

## 한 줄로 가져가기

DBaaS를 오퍼레이터 패턴으로 만들면 "왜 이 상태인가"를 spec과 status의 차이로 설명할 수 있고, IaaS를 한 겹 더 추상화하면 DBMS마다 인프라 코드를 다시 쓰지 않아도 된다. 그리고 새 플랫폼을 만드는 팀의 일은 옮겨 오는 길까지 닦는 데서 끝난다.
