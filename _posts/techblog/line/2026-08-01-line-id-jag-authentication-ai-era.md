## 한 줄 요약

AI 에이전트가 검색·DB·메신저·티켓 시스템을 도구처럼 쓰게 되면서, 연결할 서비스가 늘수록 인증·인가 운영 비용과 복잡도가 늘어 AI가 오히려 병목이 되는 역설이 생긴다. ID-JAG(Identity Assertion JWT Authorization Grant)는 IETF OAuth 워킹 그룹에서 Okta 주도로 표준화 중인 초안으로, **SSO로 확립한 IdP 신뢰를 앱 간·에이전트-서비스 간 API 접근으로 확장**한다. RFC 8693(토큰 교환)과 RFC 7523(JWT 인가 그랜트)을 결합해, 에이전트가 ID 토큰을 IdP에 제시하면 IdP가 관리자 정책을 평가해 서명된 JWT "소개장"(ID-JAG)을 주고, 대상 앱의 인가 서버가 그것을 믿고 액세스 토큰을 발행한다. 결과는 사용자 동의 팝업 감소, 감사 가시성의 IdP 집중, 섀도우 AI를 통제 안으로, 리프레시 토큰 없는 갱신으로 토큰 스프롤 억제다. 단, 아직 RFC가 아니고 기밀 클라이언트에만 권장되며 JWT라 즉시 무효화가 어렵다.

## 배경: 왜 새 표준이 필요한가

2026년 AI 패러다임은 채팅에서 실행으로 옮겨 갔다. 에이전트가 조직의 여러 서비스를 도구로 다루는데, 서비스마다 OAuth 클라이언트를 등록하고 사용자 동의를 받고 토큰을 관리하면 시스템 이면의 비용이 폭증한다. ID-JAG는 2024년 3월 개별 초안으로 나와 2025년 6월 Okta가 공식 지지하는 차세대 표준 후보로 발표했고, MCP 인증 문서도 2026년 6월 stable이 되며 이를 참조한다.

## 핵심 아이디어

한 문장으로: "SSO에서 IdP를 믿듯, 어떤 앱이 어떤 앱의 API에 어떤 권한으로 접근할 수 있는지를 **IdP의 중앙 정책으로 일원화**한다." 기술적으로는 IdP가 서명한 검증 가능한 JWT를 소개장으로 발행하고, API 리소스 측이 그 소개장을 신뢰해 최종 액세스 토큰을 발행한다.

등장 인물은 넷이다. **요청 에이전트**(다른 앱의 API를 부르려는 AI 에이전트나 앱), **기업 IdP**(SSO 제공, 중앙 인가 정책 보유), **인가 서버**(호출 대상 앱의), **리소스 서버**(실제 API).

흐름은 다섯 단계다.

1. **SSO 로그인**: 사용자가 요청 에이전트에 로그인하면 에이전트가 IdP에서 ID 토큰을 얻는다.
2. **토큰 교환 요청**: 에이전트가 IdP에 ID 토큰을 제시하고 토큰 타입으로 ID-JAG를 지정해 교환을 요청한다(RFC 8693).
3. **정책 평가·응답**: IdP가 관리자 정책을 평가해 허용하면 ID-JAG를 반환한다.
4. **액세스 토큰 교환**: 에이전트가 ID-JAG를 인가 서버에 제시해 액세스 토큰을 얻는다(RFC 7523).
5. **API 접근**: 액세스 토큰으로 리소스 서버를 호출한다(RFC 6749).

주목할 점은 **허가 판단 시점이 에이전트-리소스 서버의 개별 관계에서 IdP-인가 서버의 조직 관계로 이동**했고, 그 결과물이 암호학적으로 검증 가능한 JWT라는 것이다.

## 조직에 가져올 이점

- **사용자 경험**: 앱 연동마다 동의 화면에서 권한을 허용하던 것을 IdP 관리자 정책에 통합한다. 도구가 늘수록 동의 팝업이 늘던 문제가 완화된다. 초안은 인가 서버가 "리소스 오너로부터 직접 동의를 얻을 필요가 없다"고 명시한다.
- **감사 가시성**: ID-JAG에는 `sub`(원래 권한을 가진 사람), `client_id`(대신 요청하는 에이전트), `aud`(어느 인가 서버로), `scp`(어떤 범위로), `iss`, `exp`, `iat`, `jti`가 담긴다. 서비스 간 복잡한 연결이 IdP를 경유하므로 발행 이벤트가 IdP에 모이고, 사고 시 책임 소재와 컴플라이언스 증적을 IdP에서 뽑을 수 있다. 사람과 에이전트 양쪽의 컨텍스트가 토큰에 있어 위임의 감사 추적이 명확하다.
- **중앙 통제**: IT 승인 없는 AI 도구를 임의로 연동하는 **섀도우 AI**를 IdP가 중간에서 판단해 정상 프로세스로 편입시킨다. 에이전트가 요구하는 범위와 조직이 허용하는 범위를 분리해 IdP가 덮어쓴다(초안: scope가 있으면 IdP가 정책을 평가해 granted scope를 결정). 차단이 필요할 때 엔드포인트마다 찾아다니지 않고 IdP에서 신규 발행을 막으면 된다.
- **토큰 스프롤 억제**: API 키, 리프레시 토큰, 서비스 계정 자격이 증식하는 문제에 대해, 초안은 인가 서버가 **리프레시 토큰을 발행하지 말고** 클라이언트가 ID-JAG를 다시 제출해 갱신하도록 권장한다.

## 주의 사항

아직 IETF 인터넷 초안이라 RFC가 아니며 동작이 바뀔 수 있으므로 핵심 아키텍처를 강하게 결합하면 위험하다. 사양의 전제 조건은 요청 에이전트가 IdP와 인가 서버 양쪽에 OAuth 클라이언트로 등록되어 있고, IdP-에이전트·IdP-인가 서버 간 신뢰 관계가 사전에 확립되어 있으며, IdP가 정책에 따라 에이전트에 범위를 사전 부여해 두어야 한다는 것이다. 그리고 **IdP는 자신이 발행한 ID-JAG에 대해 액세스 토큰을 발행해서는 안 된다**(권한의 의도치 않은 확대 방지, 8.3 Cross-Domain Use).

구현·운영에서는 시크릿을 안전하게 보관하는 **기밀 클라이언트에만** 권장하고, 모바일 같은 공개 클라이언트는 기존 인가 코드 그랜트를 쓴다. IdP가 주체 토큰의 인증 컨텍스트가 정책에 못 미치면 **step-up 인증**을 요구할 수 있으므로(`insufficient_user_authentication`), 재인증을 유도하는 오류 처리 로직이 필요하다. 그리고 JWT라 한 번 발행되어 전파된 토큰을 **중앙에서 즉시 무효화하기 어렵다.**

LY의 오픈소스 권한 관리 플랫폼 Athenz가 ID-JAG를 공식 지원하기 시작했고, 다음 글에서 Athenz와 오픈소스 IdP로 발행해 AI와 연동하는 핸즈온을 예고한다.

## 읽고 남는 질문

- 인가 서버가 리프레시 토큰 대신 ID-JAG 재제출을 요구하면 ID-JAG의 수명이 곧 세션 수명이 된다. 그 수명을 얼마로 두는 것이 즉시 무효화 불가와 갱신 편의 사이의 균형인지, Athenz에서는 어떻게 설정했는지가 궁금하다.
- "IdP 관리자 정책이 사용자 동의를 대신한다"는 것은 개인정보 관점에서 사용자의 자기결정권과 부딪힐 수 있다. 엔터프라이즈 내부 앱은 괜찮지만 외부 SaaS에 사내 데이터를 넘기는 경우의 경계가 어디인지.
- 에이전트가 에이전트를 부르는 다단 위임(사람 → 에이전트 A → 에이전트 B → API)에서 `sub`와 `client_id` 두 필드로 체인을 표현할 수 있는지, 아니면 별도 확장이 필요한지가 AI 에이전트 맥락에서 핵심이다.

## 한 줄로 가져가기

에이전트 시대의 인가 문제는 "토큰을 어디에 저장하나"가 아니라 "누가 허가를 판단하나"이고, ID-JAG의 답은 그 판단을 각 서비스에서 IdP로 옮기는 것이다. 대가는 IdP가 단일 정책 지점이자 단일 의존점이 된다는 것, 그리고 아직 초안이라는 것이다.
