## 한 줄 요약

팀원이 늘었는데 더 바빠졌다. VOOM 운영, HomeTab 준비, 새 클라우드 플랫폼 Flava 전환이 겹치며 문의와 배포 요청이 쏟아졌고, 배포 요청 하나를 처리하려면 Slack → Confluence → Jira를 오가며 복사-붙여넣기를 해 평균 1시간이 걸렸다. **일주일을 재 보니** 주 약 50건, 약 15시간, 팀원 한 명당 매주 반나절이 반복 작업이었다. "개발자는 Slack만 보면 되고 SRE는 버튼만 클릭하면 되는 세상"을 목표로 Slack 워크플로로 요청을 받아 Jira 티켓·Fix Version·Epic·스프린트·체크리스트·배포 매뉴얼·이전 배포 링크를 자동으로 잇고, 👀/✅ 이모지로 할당·완료하는 봇을 만들었다. 배포 요청 처리는 30분 → 1분 이내, 긴급 요청 지연은 30~40분 → 1분. 그 과정에서 DI 컨테이너가 옛 설정을 붙잡는 문제와 Redis GET-SET 경쟁 조건을 겪었다.

## 배경: 정량화한 문제

Flava 도입 후 "파드 로그는 어떻게 보나요", "배포 파이프라인 권한은 어디서", "이 에러는 무슨 뜻" 같은 문의가 매일 쏟아졌다. 가장 큰 것은 배포 요청이었다. Slack에서 확인 → Confluence 체크리스트 열기 → 내용을 Jira 티켓에 옮기기 → Fix Version 없으면 생성 → Epic 링크·스프린트 추가 → Slack에 링크 공유 → 배포 매뉴얼 요청. 기준과 규칙은 있었지만 자동화되지 않아 매번 사람이 했고, Fix Version 오설정, Epic 누락, 체크리스트 일부 누락 같은 실수가 반복됐다. 일반 문의는 Slack 멘션에 묻혀 누가 처리 중인지도 몰랐다.

| 유형 | 주간 건수 | 건당 | 주간 합계 |
| --- | ---: | ---: | ---: |
| 배포 요청 | 약 10건 | 평균 1시간 | 약 10시간 |
| 일반 요청 | 약 40건 | 평균 20분 | 약 14시간 |
| 종합 | 약 50건 | 평균 30분 | 약 15시간 |

가시성이 없어 처리 중인 건수조차 파악이 어려웠고, 성과로 인정받기도 어려운 구조였다.

## 설계 철학과 단계

Single Point of Truth(Slack이 모든 요청의 시작점이자 추적점), Zero Manual Work(규칙 기반 작업 100% 자동화), Instant Visibility(상태를 Slack에서 실시간으로), Permission Control(SRE만 작업 가능). 1단계는 워크플로로 요청 접수와 티켓 자동 생성(Fix Version·스프린트), 2단계는 Confluence 체크리스트 자동 반영·서비스별 배포 매뉴얼 자동 검색·이전 배포 티켓 자동 링크, 3단계는 Slack 버튼과 이모지(👀 할당, ✅ 완료, 🔄 재오픈)로 상태 관리와 SRE 그룹 권한 체크.

## 네 가지 기술 결정

1. **Slack 워크플로 vs 슬래시 명령어.** 슬래시는 구현이 쉽지만 사용자가 형식에 맞춰 텍스트를 쳐야 한다. 워크플로는 양식을 직관적으로 채우고 **필수 항목을 Slack UI에서 검증**하므로 빈 값이 애초에 안 들어오며 별도 UI 개발이 없다. 원문이 성공의 핵심으로 꼽는 결정이다.
2. **동기 vs 비동기.** Slack은 3초 안에 응답해야 하는데 Jira·Confluence·스프린트 API를 순차 호출하면 넘긴다. 즉시 "접수되었습니다"를 돌려주고 백그라운드에서 처리한다.
3. **상태 저장.** Slack 스레드 ↔ Jira 티켓 매핑을 봇 메모리에 두면 재시작에 사라지고, Slack 메타데이터 API는 조회가 느려 이모지 클릭 같은 실시간 상호작용에 안 맞는다. **Redis + TTL 30일**로 100ms 미만 조회와 영구 저장을 얻었다.
4. **헥사고날 아키텍처.** Slack·Jira·Confluence·Redis 통합이 핵심이라 포트(인터페이스)로 외부를 격리했다. Jira API 버전이나 Slack SDK가 바뀌어도 비즈니스 로직은 한 줄도 안 바뀐다. 인바운드 어댑터(Slack 이벤트) → 유스케이스 → 아웃바운드 어댑터.

## 전후 비교

| 시나리오 | 도입 전 | 도입 후 |
| --- | --- | --- |
| 배포 요청 | SRE 약 30분, 실수 가능성 높음 | 개발자 워크플로 5분 → 봇 10초(Fix Version 생성, 티켓, Epic, 스프린트, 매뉴얼 링크) → SRE 1분 이내 |
| 긴급 요청 | 멘션이 묻혀 30~40분 지연, Priority·스프린트 누락 | '긴급' 선택 시 Priority Highest 자동, 🚨 알림, 👀 5초 할당, 지연 1분 |
| 일반 요청 | 10분 이상, 추적 어려움 | 5분 이내(실제 작업 시간만), 스레드에서 티켓 상시 확인 |
| 이전 배포 참고 | Jira에서 JQL로 검색해 티켓 3개를 열어 보며 5분 이상 | 새 티켓에 이전 배포 링크 자동 첨부, 10초 |

## 두 가지 도전

**Central Dogma 설정 핫 리로드.** Epic 키나 라벨을 설정 저장소(Central Dogma)에서 바꾸면 봇에 반영돼야 하는데 새 티켓에 적용되지 않았다. ConfigWatcher가 변경을 감지해 Settings를 갱신하는 것까지는 정상이었지만, **의존성 주입 컨테이너가 초기화 시점의 설정을 캡처**해 두어 옛 값을 계속 썼다. Settings 갱신과 동시에 컨테이너 설정도 갱신하게 고쳤다. 교훈은 DI 컨테이너에서 설정 변경이 전파되는 경로를 정확히 알아야 한다는 것과, Factory Provider는 매번 재평가하므로 컨테이너 설정만 맞으면 자동 반영된다는 것.

**동시 클릭의 Redis 불일치.** 여러 인스턴스로 운영하는데 같은 스레드에서 SRE A와 B가 거의 동시에 할당 버튼을 누르면 A의 할당이 B로 덮였다. `GET → 수정 → SET` 패턴의 경쟁 조건이다. **Redis 트랜잭션(WATCH/MULTI/EXEC) 낙관적 락**으로, 키를 감시하다 다른 프로세스가 바꿨으면 취소하고 재시도(max_retries)한다.

## 부수 효과와 계획

모든 요청이 구조화되어 "가장 많이 배포하는 서비스", "평균 배포 소요 시간"(SLA 근거), "요청 집중 시간대"(온콜 최적화), "월간 처리 건수"(성과 가시화)를 볼 수 있게 됐다. 신규 SRE 온보딩은 동료가 1:1로 2~3일 교육하던 것에서 #help-sre 채널의 처리 기록을 보며 학습하는 것으로 줄었다. 계획은 n8n·make 같은 로우코드 워크플로 통합, Kubernetes MCP로 파드 재시작·스케일을 Slack에서, GitHub·Confluence·Jira MCP로 자연어 조회, RAG + LLM으로 일반 문의 1차 자동 응답이다.

마지막 조언이 실용적이다. 먼저 1주일간 시간을 측정하고, 가장 자주 하는 세 가지부터 자동화하고, 피드백을 받아 작게 시작하라. 봇도 처음엔 "Slack → Jira 티켓 생성"만 했다.

## 읽고 남는 질문

- 제목의 "10분의 1"은 배포 요청(30분 → 1분 이내 = 1/30)과 일반 요청(20분 → 5분 = 1/4)의 어디쯤인데, 도입 후 주간 합계 15시간이 실제로 몇 시간이 됐는지 후속 측정이 있으면 완결된다.
- 워크플로 필수 항목 검증으로 빈 값은 막지만 잘못된 값(존재하지 않는 Confluence 페이지, 오타 난 버전)은 어떻게 처리하는지. 봇이 실패했을 때 사용자에게 무엇을 돌려주는지.
- 여러 인스턴스에서 같은 Slack 이벤트를 중복 처리하지 않도록(티켓 두 개 생성) 어떤 멱등성 장치를 두었는지가, 낙관적 락 이야기와 함께 있었으면 좋겠다.

## 한 줄로 가져가기

자동화의 첫 단계는 코드가 아니라 일주일치 측정이고, 둘째는 사용자가 형식을 외우지 않게 하는 입력 방식이며, 셋째는 3초 안에 응답하고 뒤에서 일하는 구조다. 그리고 여러 인스턴스가 같은 키를 만지는 순간 GET-SET은 반드시 깨진다.
