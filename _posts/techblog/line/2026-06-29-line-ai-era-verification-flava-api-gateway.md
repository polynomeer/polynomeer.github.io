## 한 줄 요약

코딩 에이전트는 빠르지만 출력이 들쭉날쭉하고, 개발 사이클의 느린 단계(CI 왕복, 반나절 걸리는 환경 프로비저닝)가 그 속도를 다 갉아먹는다. Flava API Gateway 팀은 2025년 중반 결성 때부터 세 가지를 세웠다. 코드 첫 줄 전에 OpenAPI 스펙과 OpenSpec 산출물로 방향을 고정하는 **스펙 주도 개발**, 2,754개 테스트가 개발자 기기에서 약 15초에 끝나고 모든 통합 테스트 응답이 OpenAPI 준수를 자동 검증하는 **검증 자동화**, Nix 기반 Devenv로 PostgreSQL은 물론 사내 인증 시스템 Athenz까지 로컬에서 띄우는 **빠르고 독립적인 로컬 환경**. 결론은 새롭지 않다. 테스트, 린터, 빠른 로컬 환경, 사전 설계는 늘 중요했고, 달라진 건 중요한 정도뿐이다.

## 배경: 왜 "검증력"인가

저자들은 AI 코딩의 함정을 논문 여러 편으로 뒷받침한다. 같은 프롬프트도 실행마다 다른 출력, 역량을 일반화하기 어려운 불안정성, 개발자마다 다른 경험, 리뷰 속도보다 빠른 생성 속도, 심지어 "좋은 출력"의 측정법조차 미정. 그래서 AI가 코드에 더 많이 기여할수록 신뢰를 지키는 건 개발자의 전문성과 세심함이고, 이를 받쳐 주는 것이 테스트·린터·빠른 로컬 환경·사전 설계라는 입장이다.

Flava API Gateway는 사내 프라이빗 클라우드 Flava의 제품 중 하나로, 각 팀이 웹 API를 만들고 배포하고 모니터링한다. 데이터 플레인은 Kong, 컨트롤 플레인은 팀이 독립적으로 API를 구성하는 멀티 테넌트 RESTful API(Go)다.

## 실천 1: 스펙 주도 개발

초기에 설계가 확정되기 전 에이전트로 구현을 시작했더니 에이전트가 설계 결정을 스스로 내리며 비결정성을 키웠다. 그래서 코드 전에 OpenAPI 스펙을 먼저 써서 설계를 고정했다. 스펙은 에이전트가 따를 기준이자 이탈을 잡아내는 구체적 기준이 된다.

문제는 원본 OpenAPI YAML이 장황하고 반복적이라 손으로 유지보수하면 금세 구현과 어긋난다는 점이다. 해법은 구성 언어 **Nickel**이다. 리소스를 `editable = 'none`(업데이트 엔드포인트 없음), `timestamped = true`(created_at/updated_at 자동), `sortable`, `filterable`, `filter_contains` 같은 선언 몇 줄로 기술하면 CRUD 생성기가 `listPaths`, `createPath`, `getPath`, `deletePath` 전체 세트를 페이지네이션·정렬·필터·ETag 낙관적 잠금·일관된 오류 응답까지 포함해 뽑아낸다.

작업 흐름은 **OpenSpec**을 쓴다. 변경마다 네 산출물을 만든다.

| 산출물 | 내용 |
| --- | --- |
| 제안(proposal) | 왜, 무엇을 바꾸는가 |
| 설계(design) | 기술 결정과 트레이드오프 |
| 델타 스펙(delta specs) | 변경별 행동 요구사항, Given-When-Then 시나리오 |
| 작업 목록(task list) | 구현 단계 체크리스트 |

개발자가 에이전트와 함께 기능을 검토(에이전트가 빠진 세부·에지 케이스·설계 옵션을 드러내도록 안내) → 에이전트가 네 산출물 생성 → 작업 목록을 따라 구현하며 체크 → 완료 후 델타 스펙을 메인 스펙 라이브러리에 병합해 API 계약의 버전 기록을 남긴다.

## 실천 2: 검증 자동화

에이전트는 첫 시도에 자주 틀린다. 빌드가 안 되거나 없는 API를 지어낸다. 모든 요구사항을 한 번에 주입하는 대신 테스트와 린터가 문제를 점진적으로 드러내게 하면, 실패한 테스트가 "무엇이 어디서" 틀렸는지 정확히 알려 준다(TDD와 LLM 코드 생성 연구도 같은 결론). 프로젝트 스킬 하나가 테스트·린터·포매터를 번들로 제공하고 AGENTS.md가 언제 그것을 불러올지 알려 준다.

과거에는 CI와 공유 테스트 환경에 의존했지만 에이전트의 반복 속도에 원격 파이프라인 왕복은 맞지 않는다.

| 계층 | 범위 |
| --- | --- |
| 단위 | 비즈니스 로직 분리 |
| 통합 | 실제 PostgreSQL(제약, 트리거, 소프트 삭제 연쇄, 트랜잭션), 인프로세스 HTTP 스택 전체, 모든 응답의 OpenAPI 준수 |
| E2E | 실제 Athenz 인증, Kong 데이터 플레인, API 키, 멀티 테넌트 격리 |
| 합계 | 2,754개, 개발자 기기에서 약 15초 |

스펙 이탈은 미묘하게 일어나므로 `setupTestServer`가 항상 래핑된 `http.Handler`를 돌려주고, 래퍼의 `ServeHTTP`가 요청을 내부 핸들러로 보낸 뒤 기록된 응답을 `openapi3filter`로 검증한다(`IncludeResponseStatus: true`로 스펙에 없는 상태 코드도 실패). 테스트를 쓰는 사람은 아무것도 추가로 하지 않아도 모든 통합 테스트 응답이 스펙 검사를 통과해야 한다.

린터는 에이전트에게 더 중요하다. 사람 팀은 리뷰 문화, 공유된 멘탈 모델, 암묵적 규칙에 기대지만 에이전트가 따를 수 있는 관습은 자동화 검사뿐이다. 그래서 golangci-lint는 옵트인이 아닌 **옵트아웃** 규칙으로, SQL·마이그레이션 린터(SQLFluff, Squawk), 빌트인과 커스텀 규칙을 포함한 Semgrep까지 최대한 넣었다.

## 실천 3: 로컬 개발 환경

포괄적 검증은 그것을 돌릴 환경을 쉽게 만들고 바꿀 수 있을 때만 유지된다. Nix 기반 **Devenv**로 모든 개발자와 CI 러너가 macOS·Linux에서 같은 `devenv shell`로 같은 버전의 같은 도구를 쓴다(direnv가 디렉터리 진입을 감지해 자동 로드). Nix가 패키지·서비스·설정을 표현하는 단일 언어라는 점이 핵심이다. 예를 들어 `-tags=extdep`를 항상 주입하는 gopls 래퍼를 Nix 패키지로 인라인 빌드해 `languages.go`에 연결하면 에디터와 에이전트가 개발자별 설정 없이 올바른 구성을 쓴다. 컨트롤 플레인 서버는 Devenv가 생성한 YAML에서 런타임 설정을 읽으므로 PostgreSQL 포트가 바뀌면 YAML도 따라 바뀐다. Nixpkgs 120,000개 이상 패키지가 고정·재현 가능하고, PostgreSQL 활성화는 몇 줄이면 된다.

가장 인상적인 부분은 **Athenz를 로컬에서 띄운 것**이다. E2E가 실제 Athenz 인증에 의존하는데 인증서 기반 서비스 인증, 도메인·역할·정책 계층이 복잡해 충실한 목을 만들면 Athenz가 아니라 "우리가 Athenz를 얼마나 이해했는가"를 테스트하게 된다. 그래서 서비스 ID, 도메인 계층, 역할과 정책을 Devenv 서비스 선언과 함께 두고 시작 시점에 프로비저닝한다. 상당한 노력이 들었지만 Devenv가 환경 구성과 의존성 연결을 맡아 준 덕에 그 노력은 주변 인프라가 아니라 Athenz 자체를 이해하는 데 쓰였다.

## 세 실천을 합치면

설계 단계에서 개발자와 에이전트가 함께 에지 케이스와 옵션을 도출하고 에이전트가 OpenSpec 산출물을 만든다. 구현 단계에서 에이전트가 작업 목록을 따라가며 변경마다 테스트와 린터를 돌리고 실패는 다음 반복으로 바로 피드백된다. 모든 검사를 통과하면 델타 스펙이 아카이브된다. 검증이 모든 단계에 들어가 있고, 그 검증이 15초에 끝나는 로컬 환경 위에서 돈다.

## 읽고 남는 질문

- 15초는 2,754개 중 E2E(실제 Kong, Athenz)까지 포함한 수치인지 궁금하다. E2E까지 15초라면 인프로세스 구성이 매우 잘 된 것이고, 아니라면 계층별 시간이 있으면 더 설득력 있었을 것이다.
- OpenSpec 산출물 네 개를 변경마다 만드는 비용은 어느 정도인지. 작은 버그 수정에도 제안·설계·델타 스펙·작업 목록을 다 쓰는지, 아니면 규모에 따른 생략 규칙이 있는지.
- 옵트아웃 린트 규칙은 에이전트에게는 좋지만 사람에게는 소음이 될 수 있다. 팀이 실제로 끈 규칙 목록과 그 이유가 있으면 다른 팀이 따라 하기 쉬울 것이다.
- 스펙과 구현의 동기화를 Nickel 생성기로 풀었는데, 생성기 자체의 변경(예: 오류 응답 형식 변경)이 모든 엔드포인트에 퍼지는 것은 장점이자 위험이다. 생성기 변경을 어떻게 리뷰하는지.

## 한 줄로 가져가기

에이전트를 잘 쓰는 팀의 비결은 프롬프트가 아니라 "틀렸다는 것을 15초 안에 알려 주는 환경"이다. 스펙으로 방향을 고정하고, 스펙 준수를 테스트 러너에 심고, 그 테스트가 로컬에서 즉시 돌게 만드는 것, 전부 예전부터 좋은 관행이었고 이제는 선택이 아니다.
