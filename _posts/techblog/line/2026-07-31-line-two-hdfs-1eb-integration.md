## 한 줄 요약

구 LINE과 구 Yahoo Japan의 HDFS를 합치면 1EB가 넘는다. 두 회사는 Namespace를 묶는 방식(클라이언트 측 ViewFS vs 서버 측 RBF), 권한 단위(DB/테이블 vs HDFS Path), 운영 책임 경계까지 달랐다. 통합 후 "데이터를 서로 쓰자"는 요구에 새 통합 플랫폼을 짓는 대신, 권한 모델은 테이블 기반의 새 영역을 구 Yahoo Japan 쪽에 신설해 단계적으로 맞추고, 전송은 S3 경유를 DistCP 직결로 바꾸되 Kerberos Cross-Realm, 전용 큐와 NodeLabel, 대역폭 상한, 보안·법무 검토 흐름까지 함께 설계했다. 전반부의 운영 교훈은 두 개다. 노드 증감이 Balancer 트래픽으로 네트워크를 흔들고, 라우터 CallQueue 정체처럼 보인 병목의 진짜 원인은 Observer NameNode 클라이언트의 과도한 msync였다.

## 배경: 같은 Hadoop, 다른 역사

| 관점 | 구 LINE | 구 Yahoo Japan |
| --- | --- | --- |
| 발전 경위 | 여러 분석 환경을 통합하는 플랫폼으로 Hadoop 3.x 시대에 구축 | Hadoop 0.2.x 시대의 제한된 분석에서 전사 플랫폼으로 발전 |
| 사용 경로 | 포털, 데이터 카탈로그, BI, ETL 등 다수 | 접근 경로를 좁혀 표준화 |
| 권한 관리 | HDFS를 의식할 필요 없는 역할 기반 신청·승인('Project' 단위) | HDFS Permission(POSIX 유사) 기준 |
| 권한 단위 | DB/테이블 | HDFS Path |
| Namespace | 기존 환경 Namespace를 가져오며 통합, ViewFS로 클라이언트가 해석, 모든 Namespace가 DataNode 공유 | 단일 Namespace → RBF(router-based federation)로 분할, 라우터가 서버 측에서 해석 |
| 변경 시 | 사용 경로와 연계 시스템 영향 확인 필요 | 플랫폼 측에서 영향 범위 정리 용이 |

HDFS는 커질수록 메타데이터를 메모리에 들고 있는 NameNode가 병목이라 양쪽 다 Namespace를 나눴지만, "어느 NameNode로 갈지"를 누가 판단하느냐가 다르다. ViewFS는 클라이언트의 마운트 테이블이, RBF는 라우터가 결정한다. 이 차이가 나중에 DistCP를 어디서 어떤 설정으로 실행할지에 직접 영향을 준다.

## 파트 1: 크게 운영하며 마주친 것들

**구 LINE: 용량 → 블록 수 → 응답 지연.** 두 클러스터를 합쳐 전사 활용을 시작하자 이용량이 예상을 웃돌았다. 새 서버 납품보다 용량 고갈이 빨라 오래된 서버를 임시 투입했다가 교체하는 잦은 추가·철거가 생겼고, 이 규모에서 노드 수가 급변하면 블록 재배치와 HDFS Balancer가 매우 큰 트래픽을 만들어 네트워크 팀과 협의하며 작업해야 했다. 용량이 진정되자 블록 수 증가로 NameNode 힙이 문제가 됐다. FSImage를 정기 덤프해 Hive 테이블로 저장해 두었기에 누가 어느 경로에 파일·블록을 얼마나 갖는지 분석해 블록 많은 테이블부터 사용자와 함께 줄여 나갔다(그래프상 전체 증가 추세를 정기 감축으로 억제). 부하 양상은 Namespace마다 달라, 테이블 데이터가 몰린 곳은 만성적으로 느리고 임시 파일이 많은 곳은 평소엔 조용하다가 DataNode 추가 때 Balancer로 급등했다.

**구 Yahoo Japan: 라우터가 아니라 msync였다.** 2020~2025년 HDFS 조작 요청 수는 계속 증가했고 지연이 체감되기 시작했다. 처음엔 라우터 계층이 병목이라 보고 라우터를 늘렸다. CallQueue 정체는 어느 정도 분산됐지만 기대만큼은 아니었다. 조사해 보니 Observer NameNode를 쓰는 클라이언트가 읽기 전에 Active의 갱신 상태를 확인하는 **msync**를 대량으로 호출하고 있었고, 그 부하가 Active NameNode에 쏠려 있었다. 읽기 결과에 영향이 없는 범위에서 msync 빈도를 재검토해 해결. 교훈은 "표면의 대기 행렬이 아니라 그 배후에서 무엇이 처리되고 있는지 보라"이다.

## 파트 2: 두 플랫폼을 잇기

새 통합 플랫폼은 중장기 과제로 미루고, 두 가지 당면 과제를 풀기로 했다. 서로 다른 권한 체계 아래서 어떻게 안전하게 전송·관리할 것인가, 그리고 매번 중간 수단을 거치는 연계를 어떻게 효율화할 것인가.

### 권한 모델: 새 영역을 만들어 단계적으로

구 LINE은 'Project'라는 활용 목적 단위로 DB/테이블 권한을 주는 역할 기반 모델이고, 구 Yahoo Japan은 Path 단위라 유연하지만 관리 대상이 늘수록 설정과 재점검이 복잡하다. 테이블 기반이 거버넌스에 유리해 구 Yahoo Japan 쪽도 맞추고 싶었지만, 이미 운영 중인 데이터를 Path 기반에서 테이블 기반으로 옮기는 것 자체가 큰 일이었다.

| 안 | 내용 | 특징 |
| --- | --- | --- |
| 1안 | 구 Yahoo Japan 구조를 유지한 채 구 LINE의 권한 관리 시스템에 연결 | 사용자는 공통 도구·흐름을 쓰지만 내부에는 테이블 기반과 Path 기반이 공존 |
| 2안 (채택) | 구 LINE 모델에 맞춘 새 영역을 구 Yahoo Japan 쪽에 신설, 대상 데이터를 그리로 이전 | 거버넌스가 일관되고, 신규·연계 필요 데이터부터 단계 적용해 이전 부담 시점을 조절 가능 |

한 번에 전체를 바꾸는 것이 아니라 두 설계 철학의 차이를 인정한 채 거버넌스와 현실 운영을 함께 만족시키는 쪽이다.

### 데이터 전송: S3 경유에서 DistCP 직결로

기존에는 플랫폼 밖의 교환 구조와 Amazon S3를 거쳐 주고받았다. 결합도는 낮지만 절차·조정·비용이 부담이었다. DistCP(Hadoop 표준 클러스터 간 병렬 복사)로 직결하되 세 층위를 정리했다.

- **인증**: 양쪽 모두 Kerberos라 각자의 KDC를 그대로 쓰되 서로 다른 Realm을 넘는 **Cross-Realm** 구성. DistCP 허가 계정은 양쪽 계정 이름을 동일하게 맞춰 주변 시스템에서도 같은 주체로 취급되게 했다.
- **인가**: 회사가 허가한 데이터만 보낸다는 정책에 따라 CapacityScheduler에 **DistCP 전용 큐**를 두고 제출 가능 계정을 제한.
- **기술(OSI 4계층·7계층)**: 전용 큐에 **전용 NodeLabel**을 연동해 DistCP가 일반 사용자와 같은 NodeManager에서 돌며 통신 경로가 섞이지 않게 했다. 7계층에서는 Cross-Realm 외에 HDFS 최소 블록 크기 차이 같은 오류 유발 지점을 맞추고, 환경마다 다른 네트워크 규칙·ACL을 계층별로 정리해 무엇을 열어야 하는지 명확히 했다. 구축 중 양쪽 네트워크에 같은 IP가 쓰이는 곳을 발견해 KDC를 겹치지 않는 위치에 재구축하기도 했다.
- **대역폭**: 서로 다른 데이터 센터라 WAN에 무리를 주지 않도록 스몰 스타트로 병렬도와 대역폭 상한을 조정하며 단계 확대.
- **운영 흐름**: 보안 책임자·네트워크 담당자 협의, 전송 데이터의 사용 목적과 개인정보 영향 검토, 필요 시 법무 확인, 각종 설정 일괄 수행을 하나의 흐름으로.

저자들의 결론은 "옮길 수 있는가"가 아니라 "누가 어떤 권한으로 어떤 경로로 어떤 범위를 다루는가"를 인증·인가·통제·네트워크까지 총체적으로 파악해야 DistCP가 실제 운영 가능한 아키텍처가 된다는 것이다.

## 읽고 남는 질문

- 2안은 "새 영역으로 옮기는" 비용을 사용자에게 지우는 셈이다. 어떤 인센티브(연계 데이터만 그 영역에서 접근 가능 등)로 이전을 유도하는지, 옮기지 않은 Path 기반 데이터는 언제까지 공존시킬지가 궁금하다.
- DistCP 직결이 생겼으니 S3 경유 경로는 폐지하는지, 아니면 결합도를 낮추는 용도로 남기는지. 두 경로가 공존하면 "어느 쪽으로 보낼지" 자체가 새 운영 규칙이 된다.
- msync 빈도 재검토는 어떤 값에서 어떤 값으로 바꿨는지, 그리고 그 결과 읽기 일관성이 어느 정도 느슨해졌는지(stale read 허용 범위)가 실무자에게 가장 궁금한 부분인데 빠져 있다.
- ViewFS(클라이언트 해석)와 RBF(서버 해석)를 장기적으로 어느 쪽으로 수렴시킬지 언급이 없다. 통합 플랫폼이 중장기 과제라면 이 선택이 그 첫 결정일 것이다.

## 한 줄로 가져가기

대형 시스템 두 개를 잇는 일의 대부분은 데이터 파이프가 아니라 "누가 무엇을 어떤 단위로 허가하는가"를 맞추는 일이고, 그것을 한 번에 통일하는 대신 새 영역을 만들어 단계적으로 옮기는 쪽이 현실적이다. 그리고 병목은 큐가 쌓이는 곳이 아니라 그 큐를 비우는 쪽에 있을 때가 많다.
