## 한 줄 요약

메트릭·로그·트레이스·프로파일이 다른 화면에 있으면 장애 때 "시간 범위, 서비스명, 라벨, 트레이스 ID"를 옮겨 적는 컨텍스트 스위칭 비용이 크다. Home SRE는 자체 호스팅 LGTM-P로 데이터를 모았지만, **어떤 데이터소스를 어떤 라벨로 조회할지는 여전히 사람 머릿속**에 있었다. SRELens는 Grafana 앱 플러그인으로 자연어 질문을 받아 Mimir·Loki·Tempo·Pyroscope를 함께 조회하고 원인 후보를 정리한다. 오픈소스 PoC에서 권한 전파·프롬프트 제어·도구 호출 라운드·라벨 차이·라이선스 한계를 확인하고 직접 만들었다. 핵심은 시스템 프롬프트를 **베이스(조직 정책, 관리자만) / 데이터소스 프래그먼트(환경별 라벨·UID 지식, YAML) / 사용자 프롬프트(개인 맥락, 덮어쓰기 불가)** 세 층으로 나눈 것과, 에이전트 루프의 상한·중복 차단·재시도 제한·결과 크기 제한·히스토리 치환을 백엔드 코드로 둔 것이다.

## 배경: 모아도 조회 방법은 사람이 알아야 했다

메트릭은 Grafana나 사내 IMON, 로그는 LaaS·IU, 트레이스는 IMON 트레이스나 Tempo, 프로파일은 별도 도구였다. 자체 호스팅 LGTM-P(Loki·Grafana·Tempo·Mimir·Pyroscope)로 쿼리 성능·보관 기간·샘플링·라벨 규칙·데이터 연결을 직접 조정할 수 있게 됐지만, 같은 서비스명이 Prometheus 계열은 `service_name`, Tempo는 `resource.service.name`인 식의 차이는 숙련 SRE의 경험에만 있었다. SRELens는 "모인 데이터를 자연어로 탐색하고 원인 분석 흐름으로 잇는 인터페이스"다.

## 왜 직접 만들었나

Grafana에 LLM을 붙이는 오픈소스 플러그인으로 PoC를 했더니 다섯 가지가 걸렸다. Grafana가 인증한 사용자 기준으로 대화 기록·사용량 한도·권한을 관리해야 하는데 안 됐고, 운영 도구의 프롬프트는 단순 문장이 아니라 정책이라 통제가 필요했으며, 장애 분석은 도구 호출 한 번으로 끝나지 않는데 라운드 제한이 있었고, 데이터소스별 라벨 차이를 다룰 수 없었고, 원하는 수준으로 수정해 사내 배포하기에 라이선스 부담이 있었다. 결론은 "자연어 질의보다 **LLM 에이전트의 행동을 통제할 제어권**이 중요하다."

## 아키텍처

프런트엔드(TypeScript·React·Grafana UI: 채팅, 스트리밍, 이미지 첨부, Markdown), 백엔드(Go·Grafana Plugin SDK: 에이전트, 프롬프트 합성, 도구 호출 제어, 사용량 제한), LLM(툴 호출 지원 GPT 계열), MCP 게이트웨이(FlavaMCP로 관측성 도구 호출), Redis(대화·사용자 프롬프트·사용량 카운터). 백엔드는 프록시가 아니라 어떤 시스템 프롬프트를 쓸지, 몇 번 호출할지, 결과가 크면 어떻게 할지, 비용을 어떻게 막을지를 통제한다. `find_grafana_panel`·`render_grafana_panel` 같은 로컬 툴도 같은 인터페이스 뒤에 합쳐 제공한다.

## 결정 1: 프롬프트 세 층

| 층 | 설정 주체 | 저장 | 역할 |
| --- | --- | --- | --- |
| 베이스 프롬프트 | 관리자/SRE | 플러그인 설정 또는 내장 파일 | 도구 호출 순서, 대시보드 생성·수정·삭제 같은 위험 작업 안전 규칙, 빈 결과 폴백, 잘린 결과는 집계 쿼리로 재조회, 응답 형식과 근거 제시 |
| 데이터소스 프래그먼트 | 관리자/SRE | 플러그인 설정 YAML | 우선 사용할 Mimir·Loki·Tempo UID, 서비스명 라벨 후보, Loki 필드 처리 관습 |
| 사용자 프롬프트 | 각 Grafana 사용자 | Redis | 담당 서비스, 선호 응답 형식, 자주 보는 대시보드 |

프래그먼트가 특히 중요했다. 에이전트가 매번 "어떤 데이터소스지? 라벨은 뭐지?"부터 탐색하면 라운드가 낭비된다. 사용자 프롬프트는 베이스를 **덮어쓰지 않고** 위에 덧붙는다.

## 결정 2: 오케스트레이터를 백엔드 단일 책임으로

프런트엔드가 시스템 프롬프트를 조립하면 사용자가 정책을 우회할 수 있다. 프런트는 사용자 메시지만 보내고 합성은 백엔드가 한다. 루프의 안전장치는 전부 코드다.

- **라운드 상한**: 기본 최대 10라운드
- **중복 호출 차단**: 같은 도구·같은 인자는 callHash로 막음
- **도구별 재시도 제한**: 기본 2회
- **개별 결과 크기 제한**: 잘라 내고 잘렸다는 마커를 남김
- **전체 히스토리 제한**: 누적 결과가 커지면 오래된 툴 결과부터 플레이스홀더로 치환하되 `tool_call_id` 짝은 유지
- **노 데이터 힌트**: 비면 포기하지 않고 라벨 후보·시간 범위·데이터소스를 바꿔 재시도하도록 유도

"LLM이 잘 판단해 주겠지"에 기대지 않기 위한 코드 레벨 가드레일이다.

## 결정 3: 비용은 백엔드에서

사용자별 일일 토큰 한도, 분당 요청 수, 초과 시 429, 응답 후 OpenAI가 돌려준 실제 토큰을 사용자별 일일 버킷에 누적(사후 반영), Asia/Seoul 자정 리셋. Redis 장애가 SRELens 전체 장애가 되지 않도록 했다.

## 세 시나리오

**에러 스파이크를 요청 패턴까지.** "09:50~10:05 beta 환경 오류 급증 원인을 분석해 줘"에 메트릭·로그·트레이스를 함께 봐서 "CopyMedia 요청 급증, 다수가 존재하지 않는 대상 복사 → 404와 409 비즈니스 에러 대량 발생, 인프라 장애가 아니라 요청 패턴 문제"까지 연결했다.

**포이즌 필 재시도 폭풍.** 스트림 처리 서비스에서 같은 메시지가 다운스트림 400으로 계속 재시도됐다. 기존엔 메트릭 → 스트림 로그 → 다운스트림 로그 → Tempo 재시도 체인 → Kafka 오프셋을 오가야 했다. 같은 질문을 프롬프트 개선 단계별로 반복했더니, 기본 프롬프트에서는 트레이스 검색이 재시도 한도에 걸려 실패, 프래그먼트 개선 전에는 Tempo는 되지만 Loki에서 잘못된 데이터소스·필터로 0건, 개선 후에는 둘 다 정확한 쿼리에 도달했다. 그 환경의 Loki는 에러 레벨이 본문 JSON이 아니라 구조화 메타데이터에 있었기 때문이다. 결론은 "업스트림 메시지의 필수 필드가 비어 발생한 포이즌 필". 교훈: **프래그먼트는 프롬프트가 아니라 SRE 운영 지식의 압축본이다.**

**로그가 없을 때 "모른다".** 트레이스에는 1~2초 타임아웃과 500이 있는데 로그가 아직 Loki에 수집되기 전. SRELens는 "확보된 근거는 Tempo 트레이스뿐, 유력한 원인은 다운스트림 지연/오류, 로그 근거는 없음"이라고 답했다. 없는 데이터를 지어내지 않았다.

## 도전과 해결

- **엉뚱한 라벨**: 프래그먼트에 라벨 후보와 주의 사항, 베이스에 폴백 순서(다른 라벨 시도, 시간 범위 넓히기).
- **너무 큰 응답**: 코드가 결과를 자르고 마커를 남기며, 프롬프트는 마커를 봤을 때 `count_over_time`·`topk`·`sum by` 같은 집계를 먼저 쓰도록 정한다. 코드는 신호를, 프롬프트는 행동을.
- **긴 루프**: max rounds + retry limit + duplicate block. LLM을 믿지 않는다는 뜻이 아니라 운영 도구의 예측 가능성.
- **LLM 응답도 신뢰할 수 없는 입력**: Markdown·코드·표·Mermaid를 렌더링하는 프런트엔드도 백엔드와 같은 수준으로 조심했다.

## UX

SSE로 텍스트뿐 아니라 tool_call·image·link·done·error 이벤트를 나눠 보내고, 도구를 호출하는 동안 도구 이름을 UI에 보여 "멈춘 건지 분석 중인지"를 추측하지 않게 한다. Stop 버튼으로 중단해도 받은 답변은 남는다. `find_grafana_panel` → `render_grafana_panel`로 PNG를 채팅에 가져온다. 대화 기록은 30일 미사용 시 자동 정리(TTL 갱신)되지만 사용자 프롬프트는 직접 지우기 전까지 유지된다. Grafana 로그인이 GitHub OAuth라 GitHub 계정 기준으로 기록·한도가 적용된다.

## 배운 것과 계획

LLM을 붙이는 것보다 제어권 설계가 중요하다. 운영 지식을 프롬프트 가능한 형태로 바꾸는 것이 품질을 좌우한다. 없는 근거를 없다고 말하는 것도 기능이다. 계획은 근거 링크와 Grafana Explore에서 재실행 가능한 재현 쿼리 제공, Kafka 랙·타임아웃 스파이크·포이즌 필 같은 반복 패턴의 템플릿화, 사용량·비용·실패율·도구 호출 패턴 대시보드다.

## 읽고 남는 질문

- 라운드 10, 재시도 2 같은 기본값이 실제 분석에서 얼마나 자주 상한에 닿는지, 그때 결론 품질이 어떻게 떨어지는지가 있으면 튜닝 근거가 된다.
- 프래그먼트 YAML은 환경이 바뀌면(데이터소스 추가, 라벨 규칙 변경) 낡는다. 누가 언제 갱신하는지, 낡았을 때 어떻게 알아채는지가 이 설계의 장기 리스크다.
- 같은 팀의 SRE Observer(알림 트리거 자동 RCA)와 SRELens(사람이 질문하는 대화형 분석)가 프래그먼트·가드레일을 공유하는지, 아니면 별도인지가 궁금하다.

## 한 줄로 가져가기

관측성 LLM 도구의 품질은 모델이 아니라 세 가지에서 나온다. 누가 바꿀 수 있는지가 정해진 프롬프트 층, 코드로 박아 둔 루프 가드레일, 그리고 SRE의 머릿속 라벨 지식을 YAML로 꺼내 놓은 프래그먼트. 그 위에서라야 "모른다"가 기능이 된다.
