## 한 줄 요약

팀마다 대시보드·스크립트·위키로 제각각 관리하던 사내 클라우드 Verda(VM, LB, DNS, 쿠버네티스)와 모니터링 IMON(알림 그룹·규칙·모니터)을 OpenTofu + Terragrunt로 옮겼다. 이미 돌고 있던 VM 약 300대, LB 약 160개, DNS 레코드 약 350개를 손으로 import할 수 없으니 리소스별 import 스크립트와 정규화 단계를 만들어 서비스 하나에 시범 적용한 뒤 나머지에 확산했고, 지금은 약 1,500개 리소스가 코드로 선언돼 7개 서비스의 변경이 전부 PR → plan → 리뷰 → apply → 매일 drift check를 거친다. 전파는 "코드 쓰세요"가 아니라 SRE가 먼저 import해서 보여 주기, 대시보드 화면에서 HCL을 뽑아 주는 Chrome 확장, 담당 SRE를 통한 Opentalk였다. 다음 단계는 OpenTofu 저장소를 MCP로 연결한 Slack 봇이 자연어 요청이나 알림을 받아 Terragrunt 코드를 쓰고 PR을 여는 것이다.

## 왜 IaC였나

여러 팀이 각자의 방식으로 인프라를 관리했다. 대상이 몇 개일 때는 문제가 아니지만 규모가 커지면 부담이 누적된다. 저자들의 기준은 소프트웨어 배포와의 비교다. 아무도 SSH로 서버에 파일을 올리지 않고 Git에 푸시하면 CI/CD가 빌드·리뷰·배포하는데, 인프라는 아직 콘솔에서 클릭하고 위키에 적는다. GitOps는 그 간극을 메운다. 원하는 상태를 Git에 선언하고, 변경은 반드시 PR로, 이력은 전부 Git에. "리뷰 없이는 변경도 없고, 흔적 없는 변경도 없는 환경"이 목표였다.

## 도구: OpenTofu와 Terragrunt

OpenTofu는 Terraform의 오픈소스 포크로 HCL 문법과 프로바이더 호환을 유지하면서 오픈소스 라이선스로 쓸 수 있어 학습 비용이 낮다. 먼저 VM, LB, 알림 같은 반복 구성을 모듈로 분리해 팀들이 값만 넘겨 쓰게 했다. 그래도 환경별 모듈 호출, 백엔드·프로바이더 설정의 반복은 남았고, 이를 Terragrunt로 풀었다. 공통 설정은 상위 `root.hcl`에 한 번, 각 환경에는 달라지는 `inputs`만. 모듈화로 리소스 정의 중복을, Terragrunt로 환경 중복을 줄인다.

## 이사 1단계: import 스크립트와 정규화

가장 큰 허들은 이미 운영 중인 리소스를 코드 관리 체계로 가져오는 일이다. OpenTofu에 import가 있지만 수백 개를 수동으로 하기는 비현실적이다. 두 가지에 신경 썼다.

**코드·state·실제 리소스 일치.** state 파일은 "코드에 선언한 리소스"와 "클라우드에 있는 리소스"를 잇는 정보다. import 후에도 네트워크 ID나 이미지 ID처럼 같은 것을 가리키지만 표현이 달라 plan에 계속 변경으로 뜨는 경우가 있었다. 그대로 두면 plan을 믿을 수 없으니 import 뒤 상태와 입력값을 정리하는 **정규화** 단계를 추가했다.

**리소스별 전략.** VM은 개별 인스턴스 단위면 되지만 LB는 리스너·풀이 함께 움직이고, DNS는 존과 레코드 관계를, 쿠버네티스는 클러스터와 노드 풀 단위를, IMON은 팀 → 알림 그룹 → 알림 규칙 → 모니터 계층을 유지해야 한다. 흐름은 통일했다.

1. 현재 리소스 조회
2. IaC 관리 대상과 제외 대상 구분
3. 코드 구조에 맞게 변환해 Terragrunt 파일 생성
4. 실제 리소스를 OpenTofu state에 연결
5. plan으로 불필요한 변경이 없는지 검증

### 만난 문제들

| 문제 | 대응 |
| --- | --- |
| 사람이 만든 VM과 쿠버네티스가 자동 생성한 VM이 OpenStack에 혼재 | 네이밍 패턴과 메타데이터로 쿠버네티스 VM은 제외. 이 필터가 없었으면 운영 클러스터에 영향 |
| IMON 알림이 4단계 계층 | 실제 계층과 비슷한 디렉터리 구조로 표현해 폴더만 봐도 소속이 보이게 |
| LB 이름에 클라우드는 `-`와 `_` 모두 허용, 프로바이더 백엔드는 `_` 불허 | 프로바이더의 validation 로직을 고쳐 업스트림에 기여 |
| 리전마다 flavor_id, image_id, network_id UUID가 달라 plan에 불필요한 변경 | 모듈에 매핑 로직 추가. 사용자는 읽기 쉬운 이름을 쓰고 모듈이 리전별 ID로 변환 |

## 이사 2단계와 전파

1단계의 import·정규화 스크립트, 필터 규칙, 모듈 보정 로직이 다른 서비스로 확산하는 자산이 됐다. 변경 흐름(PR을 열면 plan 자동 생성, 리뷰·승인 후 적용)을 표준화했지만 모두가 HCL을 바로 쓰는 건 아니라서 전파 방식을 따로 고민했다.

- **좋은 예시가 최고의 문서**: 복잡한 import는 SRE가 먼저 하고 "여러분 서비스의 VM은 코드로 이렇게 생겼습니다"를 보여 줬다.
- **Chrome 확장**: 모니터링 사용자 대부분은 브라우저에서만 일한다. IMON2 대시보드에서 알림 규칙 페이지를 열면 확장 프로그램이 DOM에서 설정값을 읽어 HCL을 자동 생성한다. 사용자가 이미 머무는 곳에서 코드를 만나게 한 것.
- **Opentalk**: 모든 팀에 한꺼번에 설명하는 대신 각 서비스 담당 SRE에게 먼저 공유해, 그 인프라를 잘 아는 SRE가 팀 상황에 맞게 안내.
- **블로그**: 이 글 자체가 "왜 이렇게 만들었는지"를 코드 밖에 남기는 전파 수단.

## 달라진 것

모든 변경에 작성자, 시간, 이유, 리뷰어가 남는다. 콘솔에서 혼자 클릭할 때는 불가능했던 피드백이 PR에서 오간다. "custom_tag가 빠졌습니다, DB ACL 설정에 필요합니다", "BMT 결과를 보니 메모리를 많이 쓰는 패턴이라 이 flavor 말고 Memory Intensive로 바꾸는 게 어떨까요". 잘못된 설정이 인프라에 닿기 전에 걸러진다.

| 단계 | 동작 |
| --- | --- |
| Plan | PR이 열리면 자동 실행, 결과가 PR 코멘트로 |
| Review | 팀이 diff 리뷰 |
| Apply | 머지 시 자동 배포 |
| Drift Check | 매일 자동 스캔, 코드와 실제의 차이를 Slack 알림 |

서비스별·환경별(Verda, Flava, IMON)로 워크플로가 분리돼 있고, 상태 잠금 복구용 `force-unlock` 워크플로도 있어 서버에 직접 접속할 필요가 없다. Drift는 누군가 콘솔에서 직접 고치면 생기는 코드와 실제의 불일치인데, 매일 잡아내니 문화를 정착시키는 안전장치가 된다. 의도적으로 코드와 다르게 둘 리소스는 `.driftignore`에 등록해 예외로 관리한다.

모니터링 임계치는 PR 하나로 여러 알림을 한꺼번에 바꾸고 이유가 커밋 메시지로 남아 "이 값 누가 왜 바꿨지"를 추적할 일이 없어졌다. 새 팀원에게는 위키와 구두 설명 대신 저장소를 보여 주면 된다. 그리고 셀프서비스가 시작됐다. A 서비스 개발 팀은 직접 Terragrunt 코드를 쓰고 PR을 올리며 SRE는 리뷰어로만 참여한다.

## 다음: 코드는 AI도 읽는다

"A 서비스 두 대 더", "B 서비스에 LB 추가" 같은 반복 요청은 패턴이 정해져 있다. OpenTofu 저장소를 MCP로 연결하고 Slack에서 자연어로 인프라를 바꾸는 봇을 만들었다. 에이전트가 기존 코드 패턴을 참고해 Terragrunt 코드를 생성하고 PR을 열고, plan 결과는 Slack으로, 사람이 리뷰·승인하면 배포. 직접 코드를 쓰든 봇을 거치든 같은 GitOps 파이프라인을 탄다.

알림을 트리거로 쓰는 시나리오도 제시한다.

| 흐름 | 기존 (수동) | IaC + AI 에이전트 |
| --- | --- | --- |
| 알림 수신 | 온콜이 Slack 확인 | 에이전트가 자동 수신 |
| 상황 파악 | 콘솔에서 VM 수·스펙 확인 | 에이전트가 IaC로 즉시 파악 |
| 대응 | SRE에 요청하거나 직접 콘솔에서 추가 | 스케일 아웃 코드 생성 후 PR 오픈 |
| 리뷰 | 사후에 "누가 왜 추가했지" | PR에 이유·알림·plan이 모두 기록 |
| 소요 시간 | 알림부터 반영까지 수십 분 | PR 생성까지 수 분, 승인 즉시 반영 |

## 도입을 고민하는 사람에게

작은 변경도 절차를 거친다. "VM 하나 스펙 올려 주세요"가 클릭 두세 번에서 코드 수정 → PR → 리뷰 → 머지 → 적용이 된다. 그리고 IaC는 기술이 아니라 문화의 문제다. 한 명이라도 콘솔에서 고치면 drift가 생긴다. 규모가 작으면 import가 쉬워 빨리 시작할 수 있고, 크면 이력 관리와 장애 위험을 줄일 수 있으니 어느 쪽이든 시작해 보라는 권유다. 이 여정은 Verda와 IMON의 Terraform 프로바이더를 만든 SRE 9팀 덕분에 가능했다고 덧붙인다.

| 항목 | 값 |
| --- | --- |
| 코드로 선언된 리소스 | 약 1,500개 |
| PR·CI/CD를 거치는 서비스 | 7개 |
| 옮긴 기존 리소스 | VM 약 300대, LB 약 160개, DNS 레코드 약 350개 |
| Drift Check 주기 | 매일 |

## 읽고 남는 질문

- Drift Check가 차이를 발견하면 누가 어느 쪽으로 맞추는지(코드를 실제에 맞추는 import인지, 실제를 코드로 되돌리는 apply인지)에 대한 규칙이 궁금하다. 긴급 대응으로 콘솔에서 바꾼 경우가 특히 그렇다.
- AI 봇이 PR을 열 때 plan 결과가 destroy를 포함하면 어떻게 막는지. 사람 리뷰가 있다지만 "승인 즉시 반영"이라면 리뷰어가 plan을 실제로 읽는지가 안전의 전부가 된다.
- 쿠버네티스 VM을 제외한 것처럼 IaC 밖에 남긴 리소스가 얼마나 되는지, 그것들은 누가 관리하는지. 1,500개는 관리 대상이지 전체가 아니다.
- Chrome 확장이 DOM을 읽는 방식은 대시보드 UI가 바뀌면 깨진다. IMON2에 API가 있다면 왜 DOM을 택했는지(권한? API 부재?).

## 한 줄로 가져가기

IaC 도입의 절반은 import 스크립트와 정규화이고 나머지 절반은 사람이 클릭하던 자리에서 코드를 만나게 하는 전파 설계다. 그리고 인프라가 전부 코드가 되는 순간, 그 코드를 읽고 쓰는 주체에 AI가 자연스럽게 포함된다.
