## 한 줄 요약

보안 업무에 AI를 넣을 때 논의는 "완전 자율 에이전트"와 "위험하니 하지 말자"로 갈리기 쉽다. LINE Plus 보안팀은 그 사이에서 **판단을 대신하지 않고 판단 준비를 돕는 것**부터 시작해 넓혀 가는 3단계(판단 보조 → 에이전트 협업 → 정형 영역 자동화)를 택했다. SAGE는 세 진입점(Jira 보안 상담 어시스턴트, Slack 보안 운영 안내 어시스턴트, 담당자용 웹 워크벤치)이 같은 지식 자산과 오케스트레이션(Langflow + GPT + Langfuse + MCP + OpenSearch 벡터)을 공유하는 플랫폼이다. 설계의 요체는 답변 정책이다. "가능합니다/불가능합니다" 같은 확정 판단과 "접수했습니다" 같은 담당자 흉내를 **명시적으로 금지**하고, 티켓 복잡도를 먼저 가늠해 간단한 건 의도적으로 짧게 답하며, 인용은 검증된 것만, 근거가 충돌하면 금지 → 조건부 → 추가 확인 → 특이사항 없음 순으로 엄격한 쪽을 택한다. 그리고 운영 팀이 반복 패턴을 운영 언어로 쓰면 개발 팀이 정책의 한 섹션만 고치는 주간 피드백 루프를 돌린다.

## 배경: "이 데이터를 외부 서비스에 올려도 되나요?"

이 한 질문에 답하려면 정보 등급·전송 경로(외부·국외·위탁)·사용 도구(생성 AI·SaaS)에 따라 다른 규정 조항을 보고, 같은 종류의 과거 상담이 어떻게 종결됐는지 찾고, 운영 팀만 아는 "요즘 자주 반려되는 사유"를 확인해야 한다. 그런데 규정은 Confluence에, 상담 이력은 Jira에, 처리 노하우는 Slack과 담당자 머릿속에 있다. 목표는 공식 판단을 생성하는 것이 아니라 **1차 자료 정리와 근거 확보를 자동화**해 담당자 숙련도에 따른 품질·시간 편차를 줄이고, 의뢰자와 담당자 모두에게 "무엇을 봐야 하는지"를 빨리 알려 주는 것이다.

## 구조: 세 진입점, 하나의 플랫폼

| 항목 | 상담 어시스턴트(Jira) | 운영 안내 어시스턴트(Slack) | 분석 워크벤치(웹) |
| --- | --- | --- | --- |
| 트리거 | 티켓 생성·댓글 | 채널 메시지 | 담당자 직접 실행 |
| 주 사용자 | 의뢰자 + 보안 컨설팅 담당자 | 임직원 + 보안 운영 담당자 | 보안 담당자(ISM 등) |
| 답변 위치 | 티켓 자동 댓글 | Slack 스레드 | 실행자 화면만 |
| 사람 검토 | 자동 댓글 후 담당자 검토 | 자동 게시 후 필요 시 검토 | 담당자 직접 실행·검토 |
| **답변 책임 경계** | 담당자용 참고 제안(공식 판단 아님) | 사용자용 참고 안내(공식 판단 아님) | 담당자 검토용 분석 |

원문이 "가장 중요한 행"이라 한 것이 답변 책임 경계다. 스택은 Langflow(로우코드 워크플로 구성·실행), GPT 계열(의도 분류·추론·생성, 워크플로마다 모델 크기와 reasoning effort를 다르게), Langfuse(트레이스, 주간 리포트 데이터 소스), MCP(Jira·Confluence 읽기/쓰기와 규정 원문 실시간 조회를 도구로), OpenSearch 벡터 스토어(과거 상담·노하우 임베딩), FastAPI + htmx(워크벤치). 사내 컴포넌트 이름, 지시문 원문, 운영 수치는 보안상 일반화했다고 명시한다.

## 보안 상담 어시스턴트: 티켓의 1~4단계를 대신 끝내 두기

티켓은 본문이 길고, 댓글에 정정 이력이 끼어 있고, 참고 링크가 곳곳에 있다. 담당자(ISM)는 답하기 전에 ① 본문·댓글 다시 읽기 ② 비슷한 과거 상담 찾기 ③ 관련 규정 떠올리기 ④ 더 필요한 정보 정리 ⑤ 근거와 전문 지식을 합쳐 판단을 거친다. 어시스턴트는 손이 많이 가는 **1~4단계를 자동으로 끝내 두는 것**이 목적이고 ⑤는 사람 몫이다. 하나의 거대 에이전트가 아니라 단계별 에이전트가 이어진 멀티 에이전트 플로이며, 근거 수집에는 조건부로 호출되는 보조 워크플로 넷이 있다. 규정 검토(외부 송신·국외 이전·위탁 축이 하나라도 걸리면), 유사 과거 상담 검색(사례 비교가 실제로 판단을 줄여 줄 때만), 정보 등급 판정(등급 다툼이 핵심 쟁점일 때만), 조항 인용 보강(마무리 단계에서 필요할 때만).

**답변 정책.** 댓글은 답변이 아니라 참고 제안이다. 블록 구조는 먼저 볼 점 / 리스크 / 판단 관점 / 누락 정보 / 담당자 액션 / 참고 근거로 고정한다. 어떤 티켓이든 같은 자리에서 같은 정보를 찾게 하고, 모델이 창의적으로 양을 늘리는 것을 막기 위해서다. 금지 사항은 셋. "가능합니다/불가능합니다" 확정 판단, "접수했습니다/처리하겠습니다/검토했습니다" 같은 담당자처럼 보이는 표현, 임의 추측에 기반한 규정 해석.

**복잡도에 따른 답변 형태.** 티켓마다 복잡도를 먼저 가늠하고(사람이 직관으로 매기지 않음) simple은 먼저 볼 점과 액션 한두 건만, medium은 리스크·판단 관점·누락 정보까지, complex는 사전 조건·추가 상담 트리거·참고 문서 후보·유사 사례까지. 두 약속이 붙는다. **간단한 상담에는 의도적으로 짧게 답한다. 애매한 케이스는 낮은 복잡도로 잡는다.** 인용은 "문서 어디의 어떤 문장"이 보이도록 검증된 것만 노출하고, 근거가 충돌하면 더 엄격한 쪽을 우선한다.

가상 시나리오(대시보드 데이터를 매일 사내 분석 DB에 적재하는 시스템 연동 신청)를 medium으로 보고 정리한 예시가 있는데, "연결해도 된다/안 된다"를 단정하지 않고 통신 경로·암호화·보관 기간·접근 기록·외부 AI 투입 여부 같은 확인 항목과 규정 원문 링크를 준다.

피드백 통로는 유용했던 블록, 부족했던 블록, 인용 정확성, 누락된 판단 축, 자유 의견 다섯 항목이고, 같은 패턴이 반복 지적되면 정책 규칙으로 옮긴다.

## 보안 운영 안내 어시스턴트: 짧은 질문에 안전한 첫 안내

단말 보안·인증·외부 저장장치·VPN 문의가 모이는 공개 채널은 응답 시간이 곧 경험인데 담당자가 즉시 못 답하는 시간대가 있다. 역할은 "담당자가 답하기 전에 사용자가 안전하게 다음 행동을 시작할 수 있는 1차 안내". 검색 에이전트(운영 노하우·과거 상담 임베딩에서 미리 봐 둘 점, 정답 패턴, 지금 해도 안전한 조치를 모음)와 답변 에이전트(그 패킷을 들고 규정·가이드로 2차 검증 후 작성) 둘로 나눠, 노하우가 빨리 쌓여도 곧바로 단정형 답변에 들어가지 않게 했다.

정책의 핵심은 **표면 증상에 속지 않기**다. 키워드 라우팅 대신 단말 보안·인증 상태 같은 실제 원인을 분리한 뒤 라우팅하고, 광범위한 점검 리스트 대신 이 케이스에 맞는 다음 행동 하나를 준다. 답변은 인사·본문·(선택)참고 문서·주의 문구("AI 참고 안내이며 공식 판단이나 승인이 아님")의 네 부분, 문의 언어와 같은 언어로만.

가장 중요한 결정으로 원문이 꼽는 것은 "개발 팀이 프롬프트를 한 번 잘 정리하면 끝"이라는 가정을 버린 것이다. 운영 팀이 반복 패턴을 운영 언어로 쓴다. "외부 저장장치 신청 거부 문의는 사유 확인 전에 호스트명·시리얼의 오기재부터 의심한다", "VPN 실패라도 특정 단말 도구 상태가 단서면 헬프데스크로 보내지 말고 재설치 안내를 먼저", "인증 단말 변경/분실은 다른 신청 폼으로". 개발 팀은 **정책 전체가 아니라 한 섹션만** 고친다. 주간 루프는 ① 시스템이 모든 답변과 👍/👎/무반응·담당자 호출 클릭을 적재 ② 주 1회 관측 건수·카테고리 분포·부정 피드백별 입력·출력·근거를 마크다운 리포트로 자동 생성 ③ 운영 팀이 부정 사례마다 문제점·이상적 답변안·개선 가이드 3단 코멘트 작성 ④ 개발 팀이 규칙 갱신.

## 분석 워크벤치

트리거가 사람인 담당자 주도형 도구다. 기밀성 구분 판정(정보 등급 후보 제안), 유사 사례 검색, 보안 규정·프로세스 안내 등 네 워크플로가 있고 일부는 전 임직원으로 확대 중이다.

## 읽고 남는 질문

- 운영 수치를 의도적으로 뺐다고 했지만, 상담 어시스턴트 도입 후 담당자의 1차 응답 시간이나 추가 확인 라운드 수가 어떻게 변했는지가 "판단 준비를 돕는다"의 효과 증명이다. 2편에 기대한다.
- 복잡도 판정을 "사람이 직관으로 매기지 않는다"고 했는데 그러면 모델이 매기는 것일 텐데, 판정이 틀려 complex를 simple로 짧게 답한 경우의 위험과 그 오판률이 궁금하다.
- 확정 표현 금지는 프롬프트 지시로 보이는데, 출력 후 검증(금지 표현 필터, 인용 존재 확인)이 코드로 있는지가 신뢰의 관건이다. 앞서 본 SRE Observer의 가드레일처럼 앱 레벨 검증이 있는지.

## 한 줄로 가져가기

보안에 AI를 넣는 첫 단계는 "무엇을 하게 할까"가 아니라 "무엇을 못 하게 할까"다. 확정 판단을 금지하고, 답변 책임 경계를 표로 못 박고, 간단한 건 짧게, 애매한 건 낮게, 그리고 규칙을 쓰는 사람을 개발자가 아니라 운영자로 두면 사람의 판단이 남는 자동화가 된다.
