## 한 줄 요약

AI로 개발할 때 결과 품질은 코드 생성 능력보다 **얼마나 정확한 맥락 위에서 작업하는가**에 달렸는데, MSA에서는 그 맥락이 저장소·문서·Slack에 흩어져 있고 무엇이 최신인지도 모른다. 이 팀은 Karpathy의 LLM Wiki 개념을 코드 중심으로 구현했다. 코드에서 정책·데이터·흐름·예외를 역추출해 **raw**(원본 근거, 변경 이력 누적)에 보존하고, LLM이 그것을 읽어 사람과 AI가 함께 보는 **knowledge**(현시점 유효한 것만) 문서로 정리하며, PR이 병합될 때마다 변경분만 뽑아 갱신하고(ingest), 주기적으로 어긋난 곳을 잡는다(lint). 사람은 스펙 PR 리뷰만 한다. 그 위에서 요구사항 → 사전 영향도 분석 → 스펙 구체화 → 구현 → 사후 영향도 분석의 스펙 주도 개발을 돌린다.

## 배경: 왜 매번 주입하지 않고 SSOT를 만드는가

요청을 개발 가능한 스펙으로 만들려면 조건·예외·데이터 기준·영향 범위를 정하고 기존 정책·인터페이스와 충돌하지 않는지 봐야 한다. 그 근거가 여러 서비스와 문서에 흩어져 있고 최신 기준 판단도 어렵다. 그래서 흩어진 정보를 AI에 매번 주입하는 대신 **코드를 근거로 하는 SSOT**를 만들었다.

LLM Wiki는 질문마다 원본을 다시 읽는 대신 LLM이 원본을 한 번 읽어 지속 관리되는 위키로 정리해 두고 이후 질문은 위키에서 답하게 하자는 개념이고, 핵심은 **위키 관리 주체가 사람이 아니라 LLM**이라는 것이다.

## 구조: 코드 → raw → knowledge

코드는 "무엇이 동작하는지"의 가장 강한 근거지만 "왜 그렇게 결정됐는지"는 없다. 그 배경은 주석·Confluence·Slack·회의 메모에 흩어져 있다. raw는 코드에서 뽑은 현재 동작 기준 스펙을 원본 맥락과 함께 보존하는 층이고, knowledge는 raw를 LLM이 읽어 정리한, 사람이 평소 읽고 AI가 스펙 정리 때 참조하는 문서다.

흐름은 두 단계다. **baseline 생성**(소스 전체에서 역추출 → raw → knowledge)과 **최신화**(PR 병합마다 변경분 수집 → raw에는 덮어쓰지 않고 이력으로 누적 → knowledge에는 최신만). 여기에 주기적 검증이 붙는다. 장치는 셋: 스킬(추출), 워크플로우(ingest/lint), GitHub Actions(자동 실행).

## 스킬: 코드에서 스펙을 뽑는다

**baseline 스킬**은 소스 어디에서 무엇을 뽑는지가 정해져 있다.

| 소스 | 추출 대상 |
| --- | --- |
| DTO·Entity | 필드명·타입·필수 여부·허용값 |
| Validator·예외 처리 | 허용·불허 조건, 예외 상황 |
| Service·UseCase | 처리 단계·분기·입출력 |
| YAML·Config | 처리 한도, 환경별 차이 |
| 노출 API·메시지 | 다른 서비스와의 연결 |
| 코드 주석 | 정책 값·예외 분기의 이유 |

클래스·메서드 구조를 옮기는 것이 아니라 **요구사항 분석에 필요한 정책·데이터·흐름·예외로 바꿔 적는다.** 예외는 API 엔드포인트, Kafka 토픽, DB 컬렉션, enum 값 같은 식별자로, 이것만은 그대로 둔다. 추출 결과는 스스로 검토하고, 그래도 코드만으로 판단이 안 서는 지점(값이 왜 그렇게 정해졌는지, 예외 분기가 의도인지)은 사람이 답한다.

**PR 스킬**은 PR 하나가 무엇을 바꿨는지에만 집중해 기존 raw와 대조하고 "이전엔 이랬는데 이번에 이렇게"로 정리한다. 산출물은 변경 스펙(ingest의 원본), 분석 리포트(근거·참조 파일·반영 대상), 리뷰 피드백 정리(AI가 작업한 PR에 사람이 남긴 코멘트 중 개발 가이드에 반영할 것) 셋이다.

## 워크플로우: ingest와 lint

**ingest**는 raw를 knowledge에 반영하되 그대로 옮기지 않는다. raw는 잘게 쌓이고 knowledge는 주제 단위로 정리된다. 중요한 결정은 **knowledge 문서 하나가 사람과 AI를 동시에 만족**시켜야 한다는 것이다. 사람용·AI용을 따로 만들면 한쪽이 낡는다. 같은 Markdown 앞에 frontmatter(doc_type, tags, sources, last_updated)와 TLDR을 두어 AI가 어떤 문서인지·최신인지 빠르게 판단하게 하고, 같은 파일을 HTML로 변환해 정적 사이트(Knowledge Wiki)로 배포한다. 탐색은 도메인별 index.md(링크 + TLDR)로, raw 기준 검색은 별칭·검색 의도·서비스 간 연결을 담은 검색 색인으로.

**lint**는 다섯 영역을 검사한다. 링크·정합성(고아 페이지, 끊긴 참조, 모순), **식별자 무결성**(raw의 식별자와 knowledge가 어긋남), 최신성(raw 변경 미반영), 문서 규칙(메타데이터 누락, 태그 위반, index 요약과 본문 불일치), 산출물 동기화(HTML·색인 미갱신). 가장 중요한 것은 식별자 무결성이다. 발견된 문제는 ingest 재실행으로 고치고, raw는 원본이므로 직접 수정하지 않는다.

**GitHub Actions.** 소스 PR 병합(트리거) → 변경 감지 후 스펙 추출 → [spec sync] PR 생성 → **사람이 스펙 PR 리뷰·병합** → ingest 실행 → 주기적 lint.

## 활용: 스펙 주도 개발

이슈 티켓이 오면 SSOT를 근거로 **사전 영향도 분석**(직접 수정 대상, 영향 모듈, 충돌 가능한 정책, 확정 전 확인 사항)을 티켓 코멘트로 남긴다. 그 결과로 스펙을 확정하고 개발 가이드·컨벤션을 참조해 구현한다. PR에는 전체 스펙이 아니라 코드로 확인할 수 없는 **ADR만** 첨부한다. PR이 생기면 실제 변경 소스 기준으로 **사후 영향도 분석**을 한다. 그리고 MSA에서는 기능 하나가 여러 서비스에 걸치므로 각 서비스의 역할·입출력·의존·정책을 엮어 파이프라인 전체를 한눈에 보는 Knowledge Wiki를 사람이 함께 본다.

## 남은 수동 단계

전부 자동은 아니다. baseline에서 코드만으로 판단 안 되는 지점은 사람이 답해야 하고, PR마다의 스펙 변경도 아직 사람이 리뷰해 확정한다. 스펙 리뷰는 신뢰가 쌓이면 자동화할 계획이고, SSOT 기반으로 개발하면 스펙과 ADR이 코드와 함께 남아 baseline의 빈틈도 사라질 것으로 본다. Slack 봇·에이전트 연동도 계획이다.

## 읽고 남는 질문

- 서비스 수, 문서 수, PR당 스펙 추출에 드는 시간과 비용, 그리고 사람이 스펙 PR을 반려한 비율 같은 운영 수치가 없다. "신뢰가 쌓이면 자동화"의 기준이 이 수치일 텐데.
- raw는 덮어쓰지 않고 이력을 누적한다면 시간이 갈수록 커진다. knowledge가 "현시점 유효한 것만"을 유지하기 위해 오래된 raw를 어떻게 무시하는지(last_updated 기준인지, 명시적 supersede인지)가 궁금하다.
- 코드 주석에서 "왜"를 뽑는다고 했는데, 주석이 없는 결정(대부분)은 baseline 때 사람이 답한 것이 raw에 어떤 형식으로 남는지. 그것이 코드 변경으로 무효화될 때 lint가 잡을 수 있는지.

## 한 줄로 가져가기

AI에게 줄 맥락은 매번 모으는 것이 아니라 코드에서 뽑아 위키로 굳히고 코드가 바뀔 때 위키가 따라가게 만드는 것이다. 그 구조의 핵심은 raw와 knowledge를 나누고, 식별자만은 그대로 두고, 사람은 스펙 PR의 리뷰어로만 남기는 것이다.
