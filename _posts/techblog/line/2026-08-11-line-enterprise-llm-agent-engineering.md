## 한 줄 요약

사내 클라우드 Flava의 AI 어시스턴트(FAA)는 도구 260개와 수백 페이지 문서를 다루며 문의의 약 96.1%에 답한다(별도 평가 모델이 "실질적 답변을 줬는가"를 판정한 수치, 정확도와는 별개). 그 수치는 화려한 기술이 아니라 **세 번의 소거**로 얻었다. 파인 튜닝 대신 RAG(연구에서 지식 주입 정확도 약 11%, 자체 실험에서도 학습 질문을 조금만 바꾸면 틀림), 청킹 대신 **검색 후 자르기**(문서를 통째로 임베딩해 제품군 안에서 검색한 뒤, 헤더로 나누고 경량 LLM이 질문에 맞는 섹션만 고름), 계획-실행이나 멀티 에이전트 대신 **ReAct**(좋은 도구와 충분한 맥락이 있으면 모델이 스스로 순서를 만든다). 미답변의 약 50%는 참조할 문서 자체가 없는 경우라, 남은 과제는 모델이 아니라 교과서 보강이다.

## 배경: 시리즈의 위치

1편은 컨텍스트 엔지니어링, 즉 260개 도구와 문서 중 LLM에 필요한 것만 골라 주는 '점진적 공개'였다. 2편은 "무엇을 전달할 것인가" 다음의 질문, 모델 파인 튜닝과 에이전틱 워크플로 영역의 세 갈림길이다. 3편은 프롬프트 엔지니어링을 예고한다. FAA는 릴리스 후 사용자 질문 패턴과 답변 결과를 추적하는 '인텔리전스 리포트'를 자체 구축해 모니터링한다.

## 소거 1: 파인 튜닝을 제외하다

"AI가 사내 문서를 다 학습했나요?"에 답은 "아니오"다. 두 근거가 있다. UC Berkeley·Google Research의 *From Style to Facts*(Zhao et al., 2025)는 Gemini 모델 700개로 위키 형식 데이터로 지식을 주입한 뒤 QA로 평가했더니 정확도가 **약 11%**였다. 그리고 직접 'Flava란 무엇인가' 같은 절대 안 변하는 기본 지식 40개로 학습시켜 보니, 학습 질문을 그대로 던지면 맞고 조금만 다르게 물으면 틀렸다. 대규모 텍스트로 형성된 기존 지식을 수십 개로 덮을 수 없었다. 400개, 4,000개로 늘리면 되지 않느냐는 반문에는 도메인 전문가가 질문을 설계하고 정답을 쓰고 교차 검수해야 하며, 문서가 바뀔 때마다 학습 데이터도 갱신해야 하는 유지보수 비용으로 답한다. 의료·법률처럼 성과가 있는 도메인도 있지만 여기서는 오픈북(RAG)이 합리적이다.

## 소거 2: 청킹하지 않는 RAG

보통 RAG는 문서를 잘게 쪼갠다. "오브젝트 스토리지 최대 용량은?"에 그 내용만 담긴 200토큰 청크가 있으면 유사도가 높고, 5,000토큰 가이드 속 한 줄이면 벡터가 여러 주제로 희석되기 때문이다. 대가는 문맥 상실이다. "이 경우에는 아래 설정을"이 경계에서 잘리면 '이 경우'와 '아래 설정'을 잃는다. overlap, contextual retrieval, late chunking 같은 기법은 결국 "자른 뒤 생긴 문제를 수습하는 노력"이다.

FAA가 역발상을 택할 수 있었던 것은 문서 특성 덕이다. 각 문서가 **하나의 제품(VM, Redis…)의 하나의 주제(생성, 삭제, 설정…)만** 다루고, 대부분 A4 몇 페이지다. 잘 정리된 문서를 억지로 쪼개면 완결된 문맥을 파괴한다. 법률 문서처럼 수십 페이지에 맥락이 이어지면 청킹이 필수지만 여기는 아니다.

**검색 후 자르기(post-split)** 흐름은 이렇다. "VM을 만들고 삭제하는 방법 알려줘" →

1. **검색**: 문서를 통째로 임베딩. 질문의 대상 제품을 파악해 그 제품 문서군 안에서만 검색.
2. **정제 1단계**: 검색된 마크다운 문서를 헤더(`##`) 기준 의미 단위로 분할.
3. **정제 2단계**: 조각의 헤더 목록을 경량 LLM에 보여 주고 "질문과 관련 있는 인덱스를 골라줘" → `[1, 3]`.
4. 메인 LLM에는 [1] VM 생성 방법, [3] VM 삭제 방법 두 조각만 전달. 5개 중 2개.

"LLM을 한 번 더 부르면 느리지 않나"에는 LLM 비용이 프리필과 디코딩으로 나뉘고 이 호출은 출력이 인덱스 몇 개뿐이라 싸다는 답이다. 핵심은 **자르는 시점**이다. pre-split은 어떤 질문이 올지 모르는 상태에서 기계적으로 자르지만, post-split은 질문을 아는 상태에서 자른다.

## 소거 3: 복잡한 워크플로 대신 ReAct

**계획 후 실행(plan-and-execute)**은 질문을 하위 태스크로 쪼개 계획을 세우고 순차 실행한다. **ReAct**는 한 걸음 걷고 결과를 보고 다음 걸음을 정한다. 초기에 계획 후 실행을 구현해 봤지만 계획 수립과 재계획 로직으로 복잡도가 크게 늘어난 반면 답변 품질 개선은 체감하기 어려웠다. 점진적 공개로 260개 도구를 정리하고 post-split로 정제된 컨텍스트를 주니, 에이전트는 복잡한 트러블슈팅에서도 도구를 순서대로 호출하며 스스로 답을 찾았다. 코딩 에이전트에서도 계획과 실행을 엄격히 나누기보다 매 단계 추론-행동을 반복하는 루프를 택하는 추세라고 덧붙인다(Claude Code 참조).

'VM 전문가', 'Kubernetes 전문가'로 나누는 **멀티 에이전트**도 검토했지만 택하지 않았다. 결국 한 일은 프레임워크 도입이 아니라 **기본에 머무르는 것**이었다.

## 결과와 남은 과제

세 갈림길에서 공통으로 택한 방향은 단순함이다. 복잡한 학습 대신 문서 참조, 사전 청킹 대신 질문을 아는 상태의 후처리, 복잡한 워크플로 대신 단순한 루프. "기술을 더하는 것이 아니라 덜어내는 것." 미답변 원인 분석에서 약 50%가 참조할 문서가 없는 **Doc Gap**이었고 나머지는 일시적 API 실패나 범위 밖이었다. 문서가 있는 영역에서는 잘 답한다는 뜻이고, 남은 과제는 AI의 뇌를 개조하는 것이 아니라 교과서를 보강하는 것이다.

## 읽고 남는 질문

- 응답률 96.1%는 "답을 했는가"이고 정확도는 별개라고 명시했다. 그렇다면 정확도(사용자 만족, 정답률)는 얼마인지가 이 소거법의 진짜 성적표인데 없다. 3편이나 리포트 후속에 기대한다.
- post-split의 2단계 LLM 필터가 관련 섹션을 놓치는(false negative) 비율이 궁금하다. 헤더만 보고 고르므로 헤더가 내용을 잘 대표하지 않는 문서에서는 취약할 텐데, 문서 작성 가이드로 보완하는지.
- "문서가 하나의 제품·하나의 주제"라는 전제가 깨지는 문서(예: 여러 제품에 걸친 마이그레이션 가이드)는 어떻게 다루는지. 그런 문서만 청킹하는 하이브리드인지 아니면 문서를 쪼개 쓰게 강제하는지.

## 한 줄로 가져가기

엔터프라이즈 RAG의 품질은 유행 기술을 얼마나 붙였느냐가 아니라 데이터의 특성을 보고 무엇을 빼도 되는지 판단하는 데서 나온다. 문서가 짧고 주제가 명확하면 통째로 넣고 질문을 안 뒤에 자르고, 도구와 맥락이 좋으면 모델이 계획을 세우게 두면 된다.
