## 한 줄 요약

두 글을 이어 읽으면 SLI/SLO의 "적용"과 "확산"이 한 흐름으로 보인다. 도입 3편은 LINE 앱의 메시지·채널·인증에 적용한 방법론이다. 사용자 관점에서 **CUJ**(핵심 사용자 여정)를 고르고, CUJ마다 측정 위치·대표 API·성공 기준(예: 99.9퍼센타일 응답 500ms 미만, 성공률 99.999%)을 정의해 SLI를 만들고, 28일 동안 99.9%(총 40,320분 중 40,280분)처럼 **지킬 수 있는** SLO를 잡고, 초록·주황·빨강으로 단순화한 대시보드를 만든다. 활용 1편은 그 과정을 서너 번 반복하며 발견한 공통 패턴을 다섯 단계 **프레임워크**(Confluence 템플릿)로 굳히고, SLI/SLO 알림을 웹훅으로 모아 서비스 상태를 자동으로 보여 주는 사내 도구 **LINE Status**를 한 달 만에 만든 이야기다. 상태 이름은 SLI/SLO가 아니라 "메시지 전송", "읽음 표시"처럼 사용자가 아는 기능 단위로 붙였다.

## 도입 3편: 마인드셋과 네 단계

SLI/SLO는 지표를 정하는 일이 아니라 **"서비스를 어떤 관점으로 이해할 것인가"를 다시 정의하는 일**이다. 두 가지 마인드셋이 필요하다. 서비스를 탐구해 사용자 여정 목록을 만들고 핵심을 고르는 것, 그리고 개인이나 한 팀이 아니라 모든 이해관계자가 함께 목표를 세우고 동의해 책임을 나눠 갖는 것.

**1. CUJ 분석.** "가장 많이 쓰는 기능은?", "반드시 제공해야 하는 기능은?"을 물어 핵심만 선별한다. LINE 가입, 메시지 송수신, 인증·암호화, LINE Login·프로필 같은 것이 후보다. 모든 기능이 중요하지만 이 단계의 핵심은 **가장 핵심만 고르는 것**, 그리고 사용자 관점에서 정의하는 것이다.

**2. SLI 구현.** CUJ마다 어디서 측정할지(게이트웨이·프런트·백엔드 중 가장 정확한 위치), 어떤 API로 측정할지(복잡한 계산이 필요 없도록 대표 API 하나), 성공·실패 기준이 무엇인지를 정한다. 보통 응답 시간(몇 퍼센타일이 몇 ms 이내)과 성공률 둘이다. 예: "메시지 전송은 99.9퍼센타일 응답 500ms 미만, 전체 요청의 99.999%가 성공."

**3. SLO 타깃.** "28일 동안 99.9%, 즉 40,320분 중 40,280분 동안 SLI를 달성한다." 핵심은 **현실적인 목표**다. 너무 높으면 그만큼 비용이 들고, 너무 낮으면 사용자 경험이 나빠진다.

**4. 시각화.** SLO와 오류 예산 요약 대시보드 + CUJ별 상세 대시보드. 정보를 많이 담기보다 초록(안정 달성)·주황(경고)·빨강(실패)으로 단순화해 한눈에.

**활용.** "느려졌다" 대신 "응답 시간이 SLI 기준 400ms를 초과해 사용자가 불편을 겪고 있다"처럼 정량적으로 말한다. 오류 예산이 80% 이상 남았으면 신규 기능에 공격적으로, 10%만 남았으면 안정성에 리소스를 넣는 **리소스 분배 기준**이 된다. 온콜에는 오류 예산 상태 변화 알림을 붙였고 정기 미팅에서 SLO를 점검한다.

## 활용 1편: 프레임워크

여러 서비스에 반복 적용하다 보니 서비스 특성과 무관한 공통 패턴이 보였다. 그것을 다섯 단계로 정리했다.

| 단계 | 내용 |
| --- | --- |
| CUJ 선정·SLI 정의 | 본질적 사용자 경험 파악, 핵심 CUJ, 측정 가능하고 의미 있는 SLI |
| 계측·메트릭 설계 | CUJ에 맞는 메트릭 신규 개발 권장, Prometheus/OpenTelemetry 표준 네이밍 |
| 대시보드·기록 규칙 | Grafana 대시보드, recording rules로 복잡한 PromQL 사전 처리 |
| SLO·알림 | **28일 롤링 윈도 99.9%(다운 40분 허용)에서 시작 권장**, 초기엔 유연하게 두다 안정화 후 확정, Runbook |
| 오류 예산 운영·거버넌스 | 릴리스 속도와 안정성 균형, 월간·분기 리뷰, 필요 시 재조정 |

Confluence 템플릿으로 제공하고 각 팀이 복제해 채운다. 특정 팀이나 역할에 의존하지 않고 확산하기 위한 장치다.

## LINE Status

SLI/SLO를 여러 서비스에 넣고 나니 담당하지 않는 서비스의 상태도 궁금해졌다. 이미 `api.line-status.info`가 있었지만 외부 API 사용자용이고 이슈 시 수동 갱신이었다. 내부 구성원이 **공통 기준**으로 컴포넌트별 상태를 보고, SLI/SLO 알림과 장애 데이터로 **자동 갱신**되는 도구를 만들기로 했다.

상태를 무엇으로 표현할지 논의가 있었다. 온콜 알람을 그대로? 오류 예산 기반? 기준은 개별 장애 여부가 아니라 CUJ 관점의 **user happiness**였다. 각 서비스의 SLI/SLO 알림을 웹훅으로 받는 백엔드를 두고 DB에 이벤트를 쌓아 현재 상태와 이력을 관리한다. 상태 이름은 SLI/SLO 용어가 아니라 "메시지 전송", "읽음 표시" 같은 기능 단위다. 개발은 약 한 달, 프런트엔드와 거리가 있는 SRE가 바이브 코딩으로 UI를 만들었다. 메인 페이지는 AI 한 줄 요약, 서비스 카드별 CUJ 나열, 초록·노랑·빨강. 상세 페이지는 최근 이벤트 순 정렬과 타임라인, 이달 이력. 히스토리 페이지는 이벤트별 서비스 영향 범위와 월 단위 이력.

프레임워크로 SLI/SLO를 도입하면 LINE Status에 등록해 조직 전체가 같은 기준으로 상태를 본다. 목표는 SLI/SLO를 "서비스 상태를 기술하는 조직의 공통 언어"로 만드는 것이다.

## 읽고 남는 질문

- 두 글 모두 실제 SLO 달성률이나 오류 예산 소진 사례, LINE Status 도입 후 장애 인지 시간 변화 같은 수치가 없다. 프레임워크가 몇 개 서비스에 적용됐는지도.
- 활용 1편에서 오류 예산 기반 상태 표현을 검토했다가 CUJ 기준으로 갔다는데, 최종적으로 상태 전환(초록 → 노랑 → 빨강)의 구체적 규칙이 무엇인지(알림 severity? 예산 소진율?)가 궁금하다.
- "메트릭 신규 개발 권장"은 기존 메트릭 재활용보다 비용이 크다. 그 판단의 근거(기존 메트릭이 CUJ를 왜곡한 사례)가 있으면 설득력이 더했을 것이다.

## 한 줄로 가져가기

SLI/SLO의 어려움은 수식이 아니라 "누구의 관점으로 무엇을 핵심이라 부를 것인가"에 있고, 그것을 여러 팀에 퍼뜨리려면 방법론을 템플릿으로, 결과를 기능 이름이 붙은 상태판으로 만들어 SRE가 아닌 사람도 같은 말을 쓰게 해야 한다.
