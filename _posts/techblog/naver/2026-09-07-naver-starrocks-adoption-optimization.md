## 한 줄 요약

데이터를 먼저 변환해서 넣던 시대(ETL)에서 일단 넣고 DB 안에서 변환하는 시대(ELT)로 바뀌면서, 분석용 DB는 "큰 테이블 하나를 빨리 훑는 것"보다 "잘게 나뉜 테이블들을 JOIN하는 것"을 잘해야 하게 됐다. ClickHouse는 전자에 강하고 StarRocks는 후자에 강하다. StarRocks의 성능은 결국 정렬 키·파티션 키·버킷 키를 쿼리 패턴에 맞게 고르는 데서 나오고, 원문은 그 여섯 가지 최적화 원칙을 정리한다.

## 배경: ETL에서 ELT로

ETL은 컴퓨팅이 비싸던 시절의 개념이다. 데이터를 옮기기 전에 정리해서 작게 만들어야 했다. 지금은 일단 다 넣어 두고 DB 안에서 변환하는 것이 성능과 확장성에서 유리하다. 그래서 Iceberg처럼 스키마가 나중에 바뀌어도 되는 오픈 테이블 포맷이 나왔고, DB 안에서 변환을 감당할 고성능 OLAP 엔진이 필요해졌다.

원문이 짚는 두 번째 변화는 **데이터 거버넌스**다. 예전에는 모든 컬럼을 한 플랫 테이블에 붙여 쿼리했다. 큐브를 만들 때도 컬럼을 추가하는 식이었다. 그런데 데이터가 잘게 분리되어 유통되는 환경이 되면서 JOIN으로 붙이는 방식의 장점이 커졌다.

## ClickHouse vs StarRocks

둘 다 LSM 트리 기반이고 MPP(대규모 병렬 처리) 쿼리 엔진이며 물리 장비와 컨테이너 모두 지원한다. 차이는 여기다.

| 항목 | ClickHouse | StarRocks |
| --- | --- | --- |
| 데이터 변환 | 테이블 엔진·materialized view (Transform After Load) | generated column·materialized view (일부 Transform Before Load 가능) |
| MV 갱신 | 원본에 INSERT될 때 트리거(준실시간) | 명령으로 갱신, 자동화용 스케줄러 내장 |
| 스토리지 | 로컬 LSM | 로컬 LSM + 분산 스토리지(연산/저장 분리 가능) |
| JOIN | 제한적, 대규모 테이블 조합에 한계 | 강함 |
| GROUP BY | StarRocks에 조금 뒤짐 | 데이터가 많을수록 격차 커짐(자체 테스트) |

StarRocks가 주목받는 이유를 정리하면 고성능 JOIN(플랫 테이블에서 벗어남), 단일 테이블 쿼리도 ClickHouse보다 빠름(자체 테스트), 오토 스케일링과 연산/저장 분리, 스케줄러형 materialized view, Iceberg 연동 최적화(HDFS 데이터를 빠르게 읽는 조합), 외부 데이터를 로컬처럼 쓰는 캐시다. WeChat, Trip.com, Airbnb 등이 쓴다.

## 구조: FE와 BE/CN

StarRocks는 프런트엔드(FE)와 백엔드로 나뉜다.

- **FE**: 메타데이터 관리, CBO(비용 기반 옵티마이저), compaction 스케줄링. 리더 하나가 메타데이터를 쓰고 나머지 FE는 Raft로 동기화한다. 리더 한 노드에 자원이 몰리므로 JVM 메모리를 넉넉히 줘야 한다.
- **BE**: 네이티브 스토리지 관리와 연산.
- **CN**: 연산/저장 분리 환경에서 연산만.

클러스터는 두 가지 구성이 있다. **Shared-nothing**에서는 BE가 로컬 스토리지와 연산을 직접 하고 CN이 Iceberg 같은 외부 카탈로그를 처리한다. **Shared-data**에서는 데이터가 분산 스토리지에 있고 BE는 캐시 역할이다. 로컬 스토리지와 Iceberg를 둘 다 쓰면 BE와 CN이 모두 필요하다.

## 핵심: LSM 트리에서는 정렬 키가 전부다

LSM 트리는 들어온 데이터를 정렬 키로 정렬해 작은 파일(SST)로 저장하고, 계속 병합(compaction)해 큰 정렬 파일로 만든다. 그러면 WHERE 조건이 정렬 기준과 같을 때 대상 데이터를 빨리 찾는다. **같지 않으면 별 효과가 없다.** 그래서 정렬 키 선택이 결정적이다.

StarRocks는 정렬된 데이터 위에 일정 간격으로 "값:위치" 인덱스를 만든다. 인덱스에는 제한이 있다.

- 조합 전체 최대 36바이트
- 최대 3개 컬럼
- 문자열 타입(CHAR/VARCHAR/STRING)은 한 번만, 그리고 마지막에만. 첫 번째에 두면 그 컬럼에서 정렬 조합이 멈춘다.

즉 문자열을 앞에 두면 인덱스가 거기서 끊긴다. UID + TS + Location처럼 고정 길이 컬럼을 앞에 두는 것이 원문 예시다.

데이터는 **파티셔닝**과 **버킷팅**으로 노드에 분산된다. 파티셔닝은 LSM 세그먼트의 정렬 경계를 정하는 것이라 파티션이 다르면 세그먼트가 완전히 분리된다. date처럼 늘 같이 처리되는 데이터의 경계가 되는 컬럼이 맞다. 버킷팅은 병렬 처리를 위한 것이니 데이터가 모든 노드에 고르게 퍼지는 키를 골라야 하고, 그것을 모니터링해야 한다.

## 여섯 가지 최적화 원칙

1. **스토리지 타입에 맞는 전략.** Shared-nothing 네이티브면 BE가 샤딩을 전담하니 고른 분산과 쿼리 조건에 맞는 정렬. Shared-data면 분산 스토리지의 처리량과 hot data 캐시를 쓰고, compaction으로 순차 I/O를 만들어 작은 I/O와 메타데이터 오버헤드를 줄임. Iceberg/Hive 외부 카탈로그면 Iceberg 파티션·Write Order로 프루닝, 캐시와 CBO 확장.
2. **자주 쓰는 컬럼 기준으로 세 키 설정.** 파티션 키는 프루닝이 되도록 일·주·월 단위로, 버킷 키는 노드 간 연산량이 균등하도록, 정렬 키는 쿼리에 불필요한 데이터를 잘라내도록.
3. **데이터 스큐 확인.** 버킷 키가 나쁘면 특정 노드에 몰린다. 테이블 → 파티션 → 태블릿(버킷 키로 나뉜 저장 단위) 순으로 조회해 태블릿별 크기와 행 수를 보면 `DISTRIBUTED BY` 키가 고른지 알 수 있다.
4. **Iceberg 추가 최적화.** hidden partition과 Parquet predicate로 필요한 데이터만 읽기. 정렬과 Z-Ordering을 많이 일어나게 하기. 외부 데이터를 BE에 직접 캐시하는 적극적 캐싱(HDFS의 Parquet 파일을 BE에 넣고 쿼리하는 것도 가능).
5. **대량 쓰기에는 적절한 파티션 단위.** 파티션 수는 FE가 다룰 메타데이터에 비례하고 FE 메모리를 먹는다. 장기간 대량 쓰기라면 파티션을 너무 잘게 나누면 안 된다.
6. **materialized view 적극 활용.** 중간 결과 저장뿐 아니라 기본 테이블의 캐시처럼 동작해 기본 테이블 쿼리도 빨라진다(윈도 함수 등은 안 됨). 주의 두 가지: MV 정의에 predicate(WHERE)를 넣으면 옵티마이저가 컬럼 정보를 못 얻어 쿼리 오류가 난다. 그리고 predicate 없는 INNER JOIN은 카테시안 곱으로 디스크를 채울 수 있다.

모니터링은 공식 Grafana 템플릿(클러스터·compaction·BE/FE 상태)을 권하고, slow query는 AuditLoader로 본다.

## 부록에서 챙길 것

CBO는 통계를 수집해 JOIN 순서 등 실행 계획을 최적화한다. 네이티브 테이블은 데이터가 바뀌면 자동 수집되지만 **Iceberg는 수동 트리거가 필요하다.** 외부 카탈로그를 쓰면 통계 갱신을 잊기 쉽다는 뜻이다.

마무리에서 원문은 DB가 클라우드에 맞춰 진화 중이고, 물리 장비 구조를 Kubernetes로 옮기는 게 아니라 Kubernetes에서 새로 개발되고 있다고 짚는다. StarRocks도 동적 스케일링과 오브젝트 스토리지를 지원하며, Operator로 설치한 뒤 업그레이드 장애 대응 방안을 미리 세워야 한다고 조언한다.

## 읽고 남는 질문

- "실제 분석 워크로드 기반 자체 테스트에서 ClickHouse보다 빠름"이라고 하는데 수치가 없다. 어떤 쿼리, 어떤 데이터 크기에서 얼마나 차이 났는지가 있으면 도입 판단에 훨씬 도움이 됐을 것이다.
- 정렬 키 36바이트·3컬럼 제한은 꽤 빡빡하다. 고카디널리티 문자열이 주 필터 조건인 테이블(예: URL, 사용자 에이전트)은 어떻게 설계하는지 궁금하다.
- Shared-data 구조에서 BE가 캐시 역할이면 캐시 미스 시 지연이 얼마나 튀는지, 그리고 네이버는 어느 구조를 택했는지가 명시돼 있지 않다.

## 한 줄로 가져가기

OLAP 엔진의 성능은 엔진 이름이 아니라 정렬 키가 WHERE와 맞느냐, 파티션이 프루닝되느냐, 버킷이 고르냐 세 가지에서 나오며, StarRocks는 거기에 JOIN을 더한 것이다.
