## 한 줄 요약

네이버의 로그 시스템 NELO는 수천 대의 Elasticsearch로 수 페타바이트를 저장하다 비용과 확장 한계에 부딪혔다. 검색 로그를 보니 **쿼리의 95%가 당일, 99%가 일주일 이내** 데이터였다. 그래서 Elasticsearch에는 14일만 두고, 장기 로그는 오브젝트 스토리지에 Iceberg 테이블 포맷으로 저장하는 Alaska를 만들었다. 적재·최적화·카탈로그 세 컴포넌트를 Iceberg SDK로 직접 만들었고, 결과는 Elasticsearch 노드 2,000대 이상 감소, 보관 기간 90일 → 최대 5년, 연간 수십억 원 절감이다.

## 배경: 두 계층 Elasticsearch의 한계

기존 구조는 Kafka → Elasticsearch였고, Elasticsearch는 SSD의 Hot 계층(3일)과 HDD의 Warm 계층(최대 90일)으로 나뉘어 있었다. 데이터가 늘자 클러스터 하나의 한계 때문에 클러스터를 여러 개로 늘렸고, 모든 클러스터가 한계에 닿아 장애가 잦았다. 연간 수십억 원이 들었다. 법적 요구로 1년 이상 보관하는 예외도 있었다.

결정적 근거는 한 달치 검색 요청 분석이다. 2주 이상 지난 데이터를 찾는 쿼리는 0.5%였다. Elasticsearch는 저장과 계산을 같은 노드가 하니 거의 안 읽는 데이터를 거기 두는 것은 낭비다. 최신 Elasticsearch는 원격 스토리지도 지원하지만, 마스터 노드가 관리할 메타데이터 규모가 이미 한계라 적용할 수 없었다. 결론은 "저장과 계산을 분리하고, 특정 쿼리 엔진에 묶이지 않는 오픈 포맷을 쓴다". 시뮬레이션에서 Iceberg가 최소 50% 절감으로 나왔다.

## Iceberg를 고른 이유

요구 사항은 쓰기/읽기 동시, 쓰기 중 스키마 변경, 단일 테이블 페타바이트, **수십만 개 테이블**, 쿼리 엔진 비종속, 저장/계산 분리, 높은 압축률. 후보는 Iceberg·Delta Lake·Hudi였고, Iceberg 커뮤니티가 가장 활발했다. Databricks가 Iceberg를 만든 Tabular를 인수하면서 경쟁이 정리되고 Iceberg가 주도권을 잡은 것도 고려했다.

Iceberg는 세 층이다. **데이터**(Parquet + zstd, 오브젝트 스토리지), **메타데이터**(어떤 파일들이 한 테이블을 이루는지, 스키마. JSON/Avro, 역시 오브젝트 스토리지), **카탈로그**(최신 메타데이터의 위치 같은 최소 정보, 보통 DB). 파일뿐 아니라 파일들의 관계까지 관리하니 "데이터 포맷"이 아니라 "테이블 포맷"이라 부른다. ACID 트랜잭션, 스키마 진화, hidden partitioning이 된다.

## 구조: Elasticsearch를 대체하지 않는다

새 시스템은 Elasticsearch를 없애지 않는다. 실시간 모니터링용 짧은 로그는 Elasticsearch에, 장기 보관은 Alaska에 둔다. 같은 Kafka 토픽을 둘 다 읽는다. Warm 계층에서 꺼내 옮기지 않은 이유는 셋이다. 실시간 검색이 필요 없는 로그는 애초에 Elasticsearch를 거칠 필요가 없고, 중복 저장돼도 Iceberg 쪽이 매우 싸며, HDD 기반 Warm 계층에서 읽으면 부하가 크다.

컴포넌트는 적재 쪽 셋과 쿼리 쪽 셋이다.

- **Orca**: Kafka → Iceberg 적재
- **Polarbear**: 테이블 최적화와 라이프사이클
- **Puffin**: Iceberg REST 카탈로그
- **Trino** 쿼리 엔진, API 서버, 웹 UI

Kappa 아키텍처다. 실시간으로 쓰이는 테이블을 사용자가 그대로 읽는다. Lambda처럼 테이블을 여러 개 두고 변환하는 것은 로그 저장에는 과하다. Iceberg가 ACID를 지원하니 쓰는 중에 읽어도 정합성이 보장되고, 동기화 주기는 5분이다. 사내 오브젝트 스토리지 Nubes는 MinIO S3 게이트웨이로 연동한다.

## 왜 직접 만들었나

오픈 소스로 PoC를 했지만 못 썼다. 이 부분이 이 글에서 가장 실무적인 대목이다.

- **kafka-connect**: 기능은 되지만 대상 테이블이 수백 개만 돼도 OOM. 필요한 것은 수십만 개.
- **Flink**: 단일 테이블로만 쓴다. 테이블 fan-out이 없어 테이블 수만큼 Flink 앱을 띄워야 한다.
- **Trino/Spark/Hive로 최적화**: 되지만 그 규모면 비용이 크고, 세밀한 스케줄링·스로틀링이 어려워 오브젝트 스토리지에 과부하를 줄 수 있다.
- **카탈로그**: Hive metastore로 시작했으나 lock 버그로 경합 시 데드락. Iceberg 커뮤니티가 REST 카탈로그를 표준으로 삼고 다른 카탈로그 직접 사용을 중단할 계획임을 확인했다. REST 카탈로그는 스펙만 있고 공식 구현체가 없다. Polaris는 특정 벤더 종속 우려. 카탈로그를 사용자에게 열어 줄 계획도 있어 직접 만드는 것이 낫다고 봤다.

## 적재(Orca): 초당 수십만 건을 테이블 수십만 개로

Kafka 다중 컨슈머 → 메모리 큐 → 테이블별 Writer → Parquet 변환 후 메모리 버퍼 → Flush Manager가 주기적으로 스토리지에 쓰고 커밋. 설계 포인트는 다음과 같다.

- **fan-out**: 토픽의 로그가 tenant별 테이블로 나뉜다. 데이터가 처음 오는 시점에 Writer를 동적으로 만들고 flush 때 메모리를 놓는다.
- **메모리**: 5분 단위 flush. 특정 테이블에 몰리면 그 테이블만 먼저 파일로 내보내는 롤오버. 메모리가 급증하면 전체 강제 flush로 OOM 예방.
- **오프셋**: Kafka batch 단위로 커밋하면 파일이 너무 작아진다. 메모리에 충분히 쌓인 뒤 커밋하려면 자동 오프셋 커밋을 못 쓰고, Iceberg 커밋이 성공한 위치까지만 Kafka에 오프셋을 커밋한다. **at-least-once**다. 중복은 equality delete로 막을 수 있지만 운용 비용이 비싸 안 썼다. 로그는 유실이 문제지 중복은 대체로 문제가 아니고, 모든 로그에 유니크 ID가 있어 사용자가 쿼리로 제거할 수 있다.
- **스키마**: 새 필드는 String으로 자동 추가(사용자가 타입 지정 가능). 새 필드가 오면 그 테이블 메모리를 강제 flush → 스키마 갱신 → 다시 적재. 변환 불가(숫자 컬럼에 문자열, 대소문자만 다른 중복 필드)는 원본과 이유를 에러 필드에 넣고, 알 수 없는 실패는 DLQ로.
- **scale-out의 역설**: 적재 노드를 늘리면 같은 테이블에 여러 노드가 동시에 쓰고, 커밋 충돌이 늘며, 파일이 작게 쪼개져 처리량과 스토리지 모두 나빠진다. 그래서 **단일 노드 성능 최적화**에 힘을 썼고, Kafka 커스텀 파티셔너로 개선할 계획이다.

## 최적화(Polarbear): 작은 파일과의 싸움

5분마다 flush하니 노드 1개, 테이블 1개면 하루 최소 288개 파일이다. 테이블 10,000개면 하루 288만 개. 이대로 두면 메타데이터가 거대해지고 커밋과 쿼리가 느려지며 오브젝트 스토리지도 힘들다. 배치 잡은 다음과 같다.

- **Rewriting data**: 같은 시간 파티션의 파일을 매시간 병합, 목표 128MiB. 대부분 1시간 로그가 파일 하나가 된다. 모바일 앱 로그는 기기 사정(네트워크·배터리)으로 최대 3일 전 로그가 늦게 오므로(disorder data), 그런 테이블은 매시간 3일치 파티션을 모두 병합한다. 적재가 지연되면 병합 스케줄을 멈춘다. 이미 병합한 파티션에 다시 작은 파일이 생기는 것을 막기 위해서다.
- **Expire snapshot**: 커밋마다 스냅샷이 남으니 테이블당 최근 10개만 유지.
- **Retention**: 테이블별 보존 기간 지난 로그를 하루 한 번 삭제.
- **Delete table**: 요청 후 3일(복구 가능 기간) 뒤 삭제. SDK 삭제 뒤에도 가비지가 남을 수 있어 S3 API로 디렉터리 하위를 다시 지운다.
- **Delete orphan files**: 커밋 충돌로 생긴 가비지를 메타파일과 대조해 삭제. 작업 중 커밋된 새 파일을 지울 위험이 있어 **7일 이상 된 파일만** 대상.

리더 노드가 테이블 평균 크기 기준 빈 패킹으로 태스크를 배분하고, 그 결과를 Iceberg 시스템 테이블에 저장한다. 팔로워는 그 테이블을 읽어 자기 몫을 실행한다. 스케줄 상태가 테이블에 있으니 노드가 재시작해도 이어서 한다.

## 카탈로그(Puffin)와 쿼리

Puffin은 Iceberg SDK의 REST 카탈로그 핸들러를 Spring Boot로 감싼 것이고 백엔드는 MySQL이다. 카탈로그를 사용자에게 열어 access key 기반 인증, 테이블 단위 권한, read-only API만 허용으로 데이터 연동을 제공한다. 예전에는 Open API로 로그를 내려받아 분석했는데, 이제 자기 쿼리 엔진에서 바로 SQL을 돌릴 수 있다.

쿼리는 Trino지만 Trino에 의존하지 않게 설계해 Spark로 바꿀 수 있다. 쿼리는 둘로 나뉜다. **Main query**는 원본 테이블에 대해 비동기로 CTAS를 실행해 결과를 테이블로 저장한다. 인덱스가 없어 Elasticsearch보다 느리고 장기간 검색은 수 시간이 걸릴 수 있으니 브라우저를 열어 둘 수 없다. **Sub query**는 그 결과 테이블에 대한 동기 쿼리로 빠르게 탐색한다.

장기 데이터 쿼리 비율이 낮으니 Trino는 작게 운영하고, 대신 제약을 걸었다. 테이블당 Main query 동시 1개, Sub query 사용자당 15/min, ANTLR로 문법 제한(SELECT만, WITH/JOIN/UNION 금지, 중첩 금지, FROM에 테이블 하나), 플래닝으로 리소스를 예측해 초과 시 에러. 그 이상은 카탈로그 연동으로 사용자 자원을 쓰게 안내한다.

## 숫자

| 항목 | 결과 |
| --- | --- |
| Elasticsearch 보관 | 90일 → 14일 |
| Elasticsearch 노드 | 2,000대 이상 감소 |
| Elasticsearch 용량 | 수 PB → 수백 TB |
| 최대 보관 기간 | 90일 → 최대 5년 |
| 인프라 비용 | 연간 수십억 원 절감 예상 |
| 압축률 | Parquet + zstd로 원본 대비 평균 약 6% |
| 파일 병합 | 파일 수 평균 약 7.5% 수준으로 감소 |
| 콜드 데이터 | 전체의 70%가 거의 검색되지 않음 |

부수 효과로, 사용자들이 장기 데이터뿐 아니라 최신 데이터도 Lucene 쿼리로 힘들던 분석을 SQL로 하기 시작했다.

## 읽고 남는 질문

- at-least-once라 중복이 남는데, 사용자에게 "쿼리로 제거하라"고 안내하는 것이 집계 쿼리에서는 부담이 될 수 있다. 중복 비율이 실제로 얼마나 되는지가 궁금하다.
- 단일 노드 최적화로 버틴다고 했는데 초당 수십만 건의 상한이 어디인지, 커스텀 파티셔너로 테이블을 노드에 고정하면 fan-out과 부하 분산이 어떻게 달라지는지 후속이 있으면 좋겠다.
- 쿼리 문법을 SELECT 단일 테이블로 제한한 것은 비용 방어로 이해되지만, JOIN이 안 되면 "로그 분석"의 상당 부분이 카탈로그 연동으로 넘어간다. 그 경로의 사용 비율이 어떤지 알고 싶다.

## 한 줄로 가져가기

저장소를 고르기 전에 "누가 언제의 데이터를 읽는가"를 먼저 재라. 95%가 당일이라면 나머지는 검색 엔진이 아니라 값싼 테이블 포맷에 두면 되고, 그 대가는 작은 파일을 끊임없이 병합하는 운영이다.
