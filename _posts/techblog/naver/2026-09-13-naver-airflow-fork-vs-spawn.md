원문: [Python의 멀티프로세싱과 Airflow, 그리고 관련된 문제 해결기 1편](https://d2.naver.com/helloworld/4452165) — NAVER D2, 도정우, 2026-09-01

## 한 줄 요약

Airflow는 작업(task)마다 새 프로세스를 만드는데, 그 프로세스를 만드는 방법이 두 가지(fork, spawn)다. 원문은 둘을 같은 조건에서 재서 fork가 왜 압도적으로 유리한지 보여주고, 그 유리함이 Python에서는 시간이 지나면 사라진다는 것까지 짚는다. 2편의 예고편이지만 1편만으로도 "왜 프로세스가 무거운가"를 이해하는 데 충분하다.

## 무엇이 문제였나

Airflow는 정해진 시간에 여러 작업을 실행해 주는 도구다. 네이버의 데이터 입수 플랫폼이 이것으로 배치를 돌리고 있고, Airflow 3.0 도입을 검토하다 문제를 만났다. 1편은 그 문제의 배경이다.

Airflow가 작업을 실행할 때 지켜야 하는 조건이 둘 있다.

- **병렬성.** 여러 작업을 동시에 돌려야 한다. 그런데 Python에는 GIL이라는 자물쇠가 있어서, 한 프로세스 안에서는 스레드가 아무리 많아도 Python 코드는 한 번에 하나만 실행된다. CPU가 8개여도 1개만 쓰는 셈이다. 그래서 진짜 병렬은 스레드가 아니라 **프로세스**를 여러 개 띄워야 나온다.
- **격리성.** 사용자가 쓴 작업 코드가 Airflow 본체를 죽이면 안 된다. 그리고 Python은 한 번 import한 모듈을 전역에 붙잡고 있어서, 작업 코드가 바뀌어도 같은 프로세스 안에서는 다시 읽어 오기 어렵다. 작업이 끝나면 그 작업이 불러온 모듈도 같이 버려져야 한다.

두 조건을 한 번에 만족시키는 방법이 "작업 하나 = 프로세스 하나, 끝나면 폐기"다. 그러면 다음 질문이 생긴다. 그 프로세스를 **어떻게 만드느냐**.

## 핵심 아이디어: 복사냐, 새로 시작이냐

Python이 프로세스를 만드는 방법은 두 가지다.

- **fork**는 지금 실행 중인 프로세스를 그대로 복제한다. 복제본은 부모가 읽어 둔 모듈, 만들어 둔 객체, 열어 둔 파일을 전부 물려받고 fork한 지점부터 이어서 실행한다. 여기서 중요한 점은 **메모리를 실제로 복사하지는 않는다**는 것이다. 운영체제는 "어느 메모리가 어디 있는지"를 적은 표(페이지 테이블)만 복사하고, 실제 메모리는 부모와 자식이 공유한다. 둘 중 하나가 어떤 페이지에 **쓰기**를 하는 순간에야 그 페이지만 복사한다. 이것이 Copy-on-Write(COW)다. 비유하면 도서관 책을 복사하지 않고 같은 책을 같이 보다가, 누가 메모를 하려는 순간에만 그 페이지를 복사해 주는 방식이다.
- **spawn**은 Python 인터프리터를 처음부터 새로 띄운다. 부모의 메모리를 전혀 공유하지 않고, 필요한 모듈을 자식이 스스로 다시 import한다. 깨끗하지만 느리다.

## 숫자로 보는 차이

원문은 Airflow 공식 이미지 위에서(Python 3.11, CPU 4코어 제한) 부모가 `airflow` 모듈을 import한 뒤 자식 10개를 두 방식으로 만들고 쟀다.

| 항목 | fork | spawn |
| --- | ---: | ---: |
| 프로세스 생성까지 | 4.3ms | 206.6ms |
| 자식에서 `airflow` import | ≈0ms | 2,694.8ms |
| 자식 1개 메모리(PSS) | 9.4MB | 83.5MB |
| 부모 + 자식 10개 물리 메모리 합 | 120.8MB | 918.2MB |

생성이 50배 빠른 이유는 fork가 표만 복사하기 때문이다. import가 0인 이유는 부모가 이미 읽어 둔 모듈을 그대로 물려받아 다시 읽을 필요가 없기 때문이다. spawn은 프로세스마다 다시 import하는데, 단건으로 1초짜리 작업이 10개를 동시에 하니 2.7초가 됐다. CPU 4개를 나눠 쓴 결과다.

메모리 표를 읽을 때 세 지표를 구분해야 한다. RSS는 "이 프로세스가 올려 둔 메모리 전부"라 공유 페이지도 각자 자기 것으로 센다. PSS는 공유 페이지를 공유하는 프로세스 수로 나눠 안분한 값이라 실제 물리 사용량에 가깝다. USS는 그 프로세스만 쓰는 페이지다. fork 자식의 PSS 9.4MB는 "자기만 쓰는 1.9MB + 부모와 공유하는 82.8MB를 11개로 나눈 7.5MB"로 분해된다. spawn 자식은 PSS와 USS가 거의 같다. 공유하는 것이 없다는 뜻이다. 그래서 전체 합이 7.6배 벌어진다.

## Airflow는 실제로 어떻게 하는가

Airflow 3에서 작업은 supervisor라는 감독 프로세스에 감싸여 실행된다. supervisor는 작업 프로세스를 만들고, 타임아웃이면 죽이고, 좀비를 검사하고, 로그를 소켓으로 받아 파일에 쓰고, 작업이 DB에 직접 접근하지 못하게 API 게이트웨이 역할까지 한다. 작업 프로세스(단기)와 supervisor(장기) 둘 다 fork로 만든다. 전자는 생성 속도 때문이고, 후자는 메모리 때문이다.

## 공짜 점심이 끝나는 순간

원문의 마지막 절이 2편의 예고이자 1편의 핵심이다. fork는 두 가지 대가가 있다.

첫째, 부모의 것을 **전부** 물려받는다. DB 커넥션, 파일 디스크립터, 뮤텍스까지. 부모가 열어 둔 DB 커넥션을 자식이 같이 쓰면 디버깅하기 매우 어려운 문제가 생긴다.

둘째, **Python에서는 COW가 온전히 동작하지 않는다.** 원문이 실제 worker 프로세스의 메모리를 시간에 따라 두 번 잰 표가 이것을 보여준다. 생성 직후 worker의 RSS는 159MB인데 PSS는 35MB다. 대부분을 부모와 공유하고 있다. 그런데 작업을 몇 번 돌린 뒤 다시 재면 PSS가 102MB로 세 배가 됐다. 프로세스가 건드리는 페이지 총량은 그대로인데, 공유하던 페이지가 자기만의 복사본으로 바뀐 것이다. 쓰기가 없어도 복사가 일어난다. 왜 그런지는 2편이 다루지만, 짐작할 수 있는 단서가 있다. Python 객체는 참조 횟수(reference count)를 객체 안에 갖고 있어서, 읽기만 해도 그 숫자가 바뀐다. 읽는 것이 곧 쓰는 것이 되면 COW는 페이지를 복사한다.

## 읽고 남는 질문

- fork의 메모리 이점이 시간이 지나면 사라진다면, 오래 사는 worker 프로세스에서는 결국 spawn과 비슷한 메모리를 쓰게 되는 것 아닌가. 그렇다면 fork의 남는 이점은 생성 속도뿐인가.
- 부모의 DB 커넥션을 물려받는 문제는 "fork 전에 커넥션을 닫는다"나 "fork 직후 재연결한다"로 푸는 것이 관례인데, Airflow는 어떻게 하는지가 2편에서 나올 것 같다.
- 측정 환경이 CPU 4코어 제한 Pod라, spawn의 import 2.7초는 CPU 경합의 결과다. 코어가 넉넉하면 spawn의 불리함이 얼마나 줄어드는지도 궁금하다.

## 한 줄로 가져가기

프로세스를 "복사"하면 빠르고 싸지만 부모의 것을 전부 물려받고, Python에서는 읽기만 해도 복사가 일어나 그 싼 값이 오래가지 않는다.
