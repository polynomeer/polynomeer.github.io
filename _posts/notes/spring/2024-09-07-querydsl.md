## Querydsl이 필요한 순간

조회 조건이 조금만 복잡해져도 메서드 이름 쿼리나 문자열 JPQL은 금방 읽기 어려워진다. Querydsl은 이 문제를 타입 안전한 쿼리 빌더로 해결한다. 다른 방법과의 비교는 [동적 쿼리 정리](/posts/dynamic-query/)에 있다.

## 장점

- 컴파일 타임에 필드 변경 오류를 발견할 수 있다.
- IDE 자동완성이 잘 된다.
- 조건 조합이 명확하다.
- Repository 구현을 읽기 좋게 유지할 수 있다.

## 기본 구조

Querydsl은 `JPAAnnotationProcessor`가 `@Entity` 타입마다 생성한 Q타입을 사용한다([Querydsl Reference 2.1](http://querydsl.com/static/querydsl/latest/reference/html/ch02.html)).

```java
QOrder order = QOrder.order;
```

이후 레퍼런스가 권하는 `JPAQueryFactory`로 조건을 조합한다.

```java
return queryFactory
    .selectFrom(order)
    .where(order.status.eq(OrderStatus.PAID))
    .fetch();
```

## 동적 조건 패턴

가장 많이 쓰는 방식은 `BooleanExpression`을 메서드로 분리하는 것이다.

```java
private BooleanExpression eqKeyword(String keyword) {
    return hasText(keyword) ? order.name.contains(keyword) : null;
}
```

`where(...)`는 null 조건을 건너뛴다("Skips null arguments", [Querydsl 5.0.0 소스](https://github.com/querydsl/querydsl/blob/QUERYDSL_5_0_0/querydsl-core/src/main/java/com/querydsl/core/FilteredClause.java)). 그래서 빈 검색 조건은 null을 돌려주는 것만으로 빠진다.

## 언제 특히 유용한가

- 검색 조건이 3개 이상으로 늘어날 때
- 조인과 정렬이 복잡할 때
- Repository 메서드 이름이 과도하게 길어질 때
- 커스텀 조회 전용 Repository가 필요할 때

## 주의할 점

- Querydsl을 도입해도 [인덱스](/posts/db-index/) 전략이 해결되는 것은 아니다.
- 복잡한 조회는 결국 [실행 계획](/posts/reading-execution-plans/)을 확인해야 한다.
- 카운트 쿼리와 본문 쿼리를 분리해야 할 때가 많다.

## 정리

Querydsl은 쿼리를 표현하는 방식을 바꿀 뿐 DB가 실행하는 방식은 그대로다. 조건 조합이 많아지는 시점부터 투자할 가치가 있다.
