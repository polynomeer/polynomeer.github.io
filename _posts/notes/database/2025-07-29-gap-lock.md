`Gap Lock`은 MySQL InnoDB를 공부하다 보면 꼭 한 번은 마주치는 개념이다.  
이름만 보면 “행을 잠그는 락”처럼 보이지만, 실제로는 **레코드 자체가 아니라 인덱스 레코드 사이의 빈 구간(gap)** 을 잠그는 락이다.

이 락을 이해하지 못하면 다음 상황에서 혼란이 생긴다.

- 분명 특정 행만 조회했는데 왜 다른 세션의 `INSERT`가 막히는가
- `SELECT ... FOR UPDATE`를 했을 뿐인데 왜 범위 전체가 잠기는가
- `Repeatable Read`에서 팬텀 리드를 어떻게 막는가
- 왜 인덱스 유무에 따라 락 범위가 크게 달라지는가

이번 글에서는 InnoDB 기준으로 `Gap Lock`이 무엇인지, 왜 필요한지, 언제 걸리는지, 그리고 실무에서 어떤 식으로 해석해야 하는지를 정리한다.

---

# 1. Gap Lock이란?

`Gap Lock`은 **인덱스 레코드와 레코드 사이의 공간**을 잠그는 락이다.

예를 들어 인덱스 값이 아래처럼 있다고 하자.

```text
10, 20, 30
```

이때 InnoDB 입장에서는 다음과 같은 “구간”이 존재한다.

- `(-∞, 10)`
- `(10, 20)`
- `(20, 30)`
- `(30, +∞)`

`Gap Lock`은 이 구간 자체를 잠근다.  
즉 `(10, 20)` 구간에 락이 걸리면, 다른 트랜잭션은 그 구간 안에 새로운 값을 삽입할 수 없다.

중요한 점은 다음이다.

- `Gap Lock`은 기존 행을 막기 위한 락이 아니다.
- **새로운 레코드가 끼어드는 것**을 막기 위한 락이다.
- 따라서 주된 목적은 **팬텀 리드(phantom read) 방지**다.

---

# 2. 왜 필요한가?

트랜잭션 A가 어떤 범위 조건으로 조회한 뒤, 같은 트랜잭션 안에서 다시 같은 조건으로 조회한다고 생각해 보자.

```sql
SELECT * FROM orders
WHERE price BETWEEN 100 AND 200
FOR UPDATE;
```

첫 번째 조회 시점에는 3개의 행이 있었는데, 트랜잭션 B가 그 사이에 `price = 150`인 새 행을 삽입해 버리면 두 번째 조회 결과가 달라질 수 있다.

이게 바로 **팬텀 리드**다.

InnoDB는 이를 막기 위해 단순히 “현재 읽은 행만 잠그는 것”으로 끝내지 않고,  
**그 범위 사이에 새로운 값이 들어올 수 있는 인덱스 구간까지 잠근다.**

즉:

- `Record Lock`은 현재 존재하는 레코드를 잠그고
- `Gap Lock`은 그 사이의 빈 공간을 잠그며
- 둘을 조합한 `Next-Key Lock`이 InnoDB의 기본 범위 잠금 전략이 된다.

---

# 3. Record Lock, Gap Lock, Next-Key Lock 차이

이 세 개를 구분하지 않으면 개념이 섞인다.

## 3.1 Record Lock

기존 레코드 자체를 잠근다.

- 특정 행의 수정/삭제 충돌을 막는다.
- 이미 존재하는 데이터에 대한 경쟁 제어가 목적이다.

예:

```sql
SELECT * FROM users WHERE id = 10 FOR UPDATE;
```

`id = 10`이라는 레코드 자체를 잠그는 쪽에 가깝다.

## 3.2 Gap Lock

레코드 사이의 **빈 구간**을 잠근다.

- 새로운 삽입을 막는다.
- 범위 일관성을 보장하는 쪽이 목적이다.

## 3.3 Next-Key Lock

InnoDB에서 자주 보게 되는 기본 형태다.

- **Record Lock + Gap Lock**
- “현재 레코드”와 “그 앞의 gap”을 함께 잠근다고 이해하면 된다.

즉 InnoDB는 범위 조건에서 단순히 행 하나만 잠그는 것이 아니라,  
그 범위의 결과가 흔들리지 않도록 **행 + 구간**을 함께 잠근다.

---

# 4. 언제 Gap Lock이 걸리는가?

모든 조회에서 무조건 걸리는 것은 아니다.  
주로 다음 조건에서 등장한다.

## 4.1 `SELECT ... FOR UPDATE` / `LOCK IN SHARE MODE`

잠금 읽기(locking read)를 수행할 때 범위 조건이 있으면 `Gap Lock` 또는 `Next-Key Lock`이 걸릴 수 있다.

예:

```sql
SELECT * FROM accounts
WHERE balance BETWEEN 1000 AND 2000
FOR UPDATE;
```

이 경우 InnoDB는 해당 범위의 기존 행뿐 아니라, 그 범위 안에 **새로운 balance 값이 삽입되는 것**도 막으려 한다.

## 4.2 `UPDATE`, `DELETE`

범위 조건을 가진 `UPDATE`나 `DELETE`도 내부적으로는 해당 범위를 탐색하며 잠금을 건다.

예:

```sql
DELETE FROM reservations
WHERE start_time >= '2025-07-01'
  AND start_time < '2025-08-01';
```

이때도 관련 인덱스 구간에 대해 범위 잠금이 형성될 수 있다.

## 4.3 `Repeatable Read`

MySQL InnoDB의 기본 격리 수준은 `Repeatable Read`다.  
이 수준에서 팬텀 리드를 방지하기 위해 `Gap Lock`이 적극적으로 활용된다.

반대로 `Read Committed`에서는 이 동작이 줄어드는 경우가 많다.  
그래서 같은 SQL이라도 격리 수준에 따라 락 범위 체감이 달라질 수 있다.

---

# 5. 언제 안 걸리거나, 생각보다 좁게 걸리는가?

`Gap Lock`은 범위 탐색과 인덱스 구조에 크게 의존한다.

## 5.1 유니크 인덱스를 통한 정확한 단건 조회

유니크 인덱스를 사용해서 정확히 한 건을 찾는 경우에는 보통 gap까지 잠글 필요가 없다.

예:

```sql
SELECT * FROM users
WHERE email = 'a@example.com'
FOR UPDATE;
```

`email`이 unique index라면, 보통은 특정 레코드 잠금 중심으로 끝난다.

하지만:

- 범위 조건이거나
- 정확히 일치하지 않는 탐색이거나
- 적절한 인덱스를 못 타는 경우

잠금 범위가 다시 넓어진다.

## 5.2 인덱스가 없으면

이 경우가 실무에서 특히 위험하다.

적절한 인덱스가 없으면 InnoDB는 더 넓은 범위를 스캔하면서 더 넓은 락을 형성할 수 있다.

즉, `Gap Lock`을 공부할 때는 단순히 “락이 걸린다”가 아니라  
**어떤 인덱스를 타고 어떤 범위를 읽는가**를 같이 봐야 한다.

---

# 6. 예시로 이해하기

테이블:

```sql
CREATE TABLE products (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  price INT NOT NULL,
  KEY idx_price (price)
);
```

현재 데이터:

```text
100, 200, 300
```

## 트랜잭션 A

```sql
START TRANSACTION;

SELECT * FROM products
WHERE price BETWEEN 100 AND 300
FOR UPDATE;
```

## 트랜잭션 B

```sql
INSERT INTO products(price) VALUES (150);
```

트랜잭션 B의 `INSERT`는 막힐 수 있다.  
이유는 트랜잭션 A가 `100 ~ 300` 범위의 읽기 결과가 변하지 않도록 그 사이의 gap을 잠그기 때문이다.

반면 아래처럼 범위 밖에 삽입하면 통과할 수 있다.

```sql
INSERT INTO products(price) VALUES (1000);
```

이건 잠긴 범위 밖이기 때문이다.

---

# 7. Gap Lock이 실무에서 문제처럼 느껴지는 이유

개념적으로는 팬텀 리드를 막기 위한 좋은 장치지만, 운영에서는 다음과 같은 문제로 체감된다.

## 7.1 예상보다 넓은 삽입 대기

“나는 특정 행만 읽었다고 생각했는데 왜 insert가 막히지?”라는 상황이 자주 나온다.

원인은 보통:

- 범위 조건을 사용했거나
- 인덱스가 비효율적이거나
- 실제 실행계획이 더 넓은 범위를 스캔했기 때문이다.

## 7.2 락 경합 증가

트래픽이 높은 서비스에서 범위 잠금이 자주 걸리면:

- insert 지연
- lock wait timeout
- deadlock

같은 현상이 늘어난다.

## 7.3 “쿼리는 맞는데 구조가 틀린” 상황

SQL 자체는 맞아도 인덱스 설계가 잘못되면 락 범위가 과도하게 넓어질 수 있다.  
그래서 `Gap Lock` 문제는 애플리케이션 코드보다 **스키마/인덱스 설계 문제**인 경우도 많다.

---

# 8. 실무에서 어떻게 다뤄야 하는가?

## 8.1 범위 잠금이 필요한지 먼저 판단하기

모든 상황에서 팬텀 리드를 강하게 막을 필요는 없다.

예를 들어:

- 단순 조회 화면
- 통계성 읽기
- 약간의 시점 차이를 허용할 수 있는 기능

이라면 굳이 `FOR UPDATE`를 걸지 않는 편이 낫다.

반대로:

- 예약 중복 방지
- 재고 차감
- 중복 없는 순번 할당
- 특정 조건 집합의 일관성 보장

같은 문제는 범위 잠금이 필요할 수 있다.

즉 `Gap Lock`은 “무조건 피해야 하는 것”이 아니라  
**정합성을 위해 의도적으로 감수할 수 있는 비용인지**를 판단해야 한다.

## 8.2 인덱스를 정확히 설계하기

`Gap Lock`의 범위는 인덱스를 타고 탐색한 구간에 의해 결정된다.

따라서:

- 범위 조건에 맞는 인덱스를 만들고
- 가능한 한 탐색 범위를 좁히고
- 불필요한 풀스캔이나 넓은 range scan을 줄여야 한다.

이건 성능 최적화이기도 하지만, 동시에 **락 범위 최적화**이기도 하다.

## 8.3 트랜잭션을 짧게 유지하기

`Gap Lock`이 오래 유지되면 다른 세션의 insert가 오래 막힌다.

그래서 다음은 피하는 게 좋다.

- 트랜잭션 안에서 외부 API 호출
- 사용자 입력 대기
- 긴 비즈니스 로직 처리
- 대량 처리 루프

잠금은 짧고 굵게 잡아야 한다.

## 8.4 격리 수준을 맹목적으로 높이지 않기

`Repeatable Read`는 정합성 면에서 좋지만, 그만큼 `Gap Lock` 체감도 커질 수 있다.

업무 특성상 충분하다면:

- `Read Committed`
- 낙관적 락
- 유니크 제약 + 재시도

같은 대안이 더 적합할 수도 있다.

# 9. 자주 하는 오해

## 9.1 Gap Lock은 “행 락의 종류”다?

정확히는 아니다.

- Record Lock은 레코드
- Gap Lock은 레코드 사이의 구간

을 잠근다.

## 9.2 Gap Lock은 무조건 성능을 망친다?

그렇지는 않다.

정합성이 필요한 구간에서는 오히려 필요한 메커니즘이다.  
문제는 **필요 이상으로 넓게 걸릴 때**다.

## 9.3 인덱스만 있으면 무조건 괜찮다?

아니다.

인덱스가 있어도:

- 조건이 범위형이면 gap이 생기고
- 실행계획이 넓은 구간을 읽으면
- 그만큼 넓은 범위 잠금이 걸릴 수 있다.

중요한 것은 “인덱스 존재 여부”보다 **실제로 어떤 탐색 경로를 타는가**다.

---

# 10. 정리

`Gap Lock`은 InnoDB가 팬텀 리드를 막고 범위 일관성을 보장하기 위해 사용하는 핵심 메커니즘이다.

핵심만 다시 정리하면:

- `Gap Lock`은 레코드가 아니라 **인덱스 사이의 빈 공간**을 잠근다.
- 목적은 **새로운 삽입을 막아 범위 결과를 안정적으로 유지하는 것**이다.
- 주로 `Repeatable Read`, `SELECT ... FOR UPDATE`, 범위형 `UPDATE/DELETE`에서 중요하게 등장한다.
- 인덱스와 실행계획에 따라 락 범위가 크게 달라진다.
- 실무에서는 “왜 insert가 막히는가?”를 이해하려면 SQL만이 아니라 **인덱스와 격리 수준**까지 함께 봐야 한다.

결국 `Gap Lock`은 “DB가 괜히 과하게 잠그는 기능”이 아니라,  
**범위 정합성을 위해 설계된 비용 있는 메커니즘**이다.

그래서 중요한 것은 없애는 것이 아니라,

- 정말 필요한 구간에만 사용하고
- 인덱스로 범위를 줄이고
- 트랜잭션을 짧게 유지하고
- 대체 가능한 경우는 다른 방법으로 설계하는 것

이다.
