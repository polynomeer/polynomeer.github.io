SLASH 24에서 "Compose를 토스팀에 안착시키기까지"를 발표했던 연사의 후속편이다. 그때 남겨 둔 질문("증권처럼 초 단위로 바뀌는 화면에서 리컴포지션을 어떻게 다루는가")에 대한 답이 이 발표다. 종목 상세 화면을 네이티브 Compose로 다시 만들면서, 가격이 바뀔 때마다 화면 전체가 다시 그려지던 문제를 세 단계로 줄였고, Material의 BottomSheetScaffold를 쓸 수 없어 Layout과 anchoredDraggable로 바텀 시트를 직접 만든 이야기가 이어진다. 내용은 발표 영상과 자동 생성 자막을 근거로 했고, 표현은 내 말로 바꿨다.

## 배경: 왜 UX를 바꾸고, 왜 네이티브로

증권은 토스 앱 하단 다섯 탭 중 하나였다. 제품이 늘고 표현할 정보가 많아지면서 화면이 복잡해졌고, 탭 하나로 모든 제품을 담기 어려웠다. 하단 탭을 확장해 새 탭을 만드는 UX가 나왔고, 더 넓은 지면으로 제품을 표현할 수 있게 됐다.

종목 상세에는 두 가지 어려움이 있었다. 매매 중에 차트와 호가·내 주식 탭을 동시에 보기 어려웠고, 다른 종목을 보려면 홈으로 돌아가 다시 골라야 했다. 그래서 상단 탭을 **바텀 시트**로 옮겨 탭을 누르면 시트가 올라오게 하고, 시트를 절반만 열면 차트와 탭을 동시에 보게 했으며, **스와이프**로 다른 종목을 탐색하게 했다. 이 두 변경은 네이티브로 구현하는 편이 수월하고 로딩도 웹보다 빠르다고 판단해 네이티브로 갔다.

Compose를 고른 이유는 둘이다. 증권에는 커스텀 UI가 많은데, View 버전의 TDS로는 랭킹 컴포넌트처럼 리스트 왼쪽에 요소 두 개를 넣는 것도 커스텀 뷰를 따로 만들어야 했고 재사용을 고려해 설계하기 어려웠다. Compose의 TDS는 슬롯 형태라 left 슬롯에 두 요소를 넣으면 끝이다(슬롯 이야기는 [작년 발표](/posts/slash24-compose-adoption/)에 있다). 둘째는 증권의 특수성이다. API와 소켓 등 여러 소스에서 데이터가 오는데, 이를 collect해 뷰에 세팅하는 코드가 많아질수록 관리 비용이 커진다. Compose는 데이터를 뷰에 바로 전달하니 실수할 여지가 적다.

## 문제 1: 가격이 바뀌면 화면 전체가 다시 그려진다

리컴포지션은 Compose가 변경이 필요한 부분을 감지해 다시 구성하는 과정이다. 많이 일어나면 성능이 나빠진다. 개발 초기에 실제로 스크롤 중 프레임 드랍이 있었고 CPU 사용량이 올라 배터리가 빨리 닳았다. 증권 앱은 1초에 수많은 데이터가 오므로 리컴포지션이 많을 수밖에 없고, 그만큼 신경 써야 했다.

리컴포지션이 일어나는 원인은 둘이다. **State가 바뀌면** Compose가 자동으로 추적해 리컴포지션한다. 이때 주의할 점은 연산 결과와 무관하게 **State를 읽는 순간**에 발생한다는 것이다. `price > 5`라는 식에서 결과가 바뀌지 않아도 `price` 값이 바뀔 때마다 리컴포지션된다. 둘째, **컴포저블에 전달되는 파라미터가 바뀌면** 발생한다. 파라미터가 전부 같으면 스킵하는데, 모든 파라미터가 안정적(stable)이어야 스킵된다. 안정성 이야기는 시간 관계상 테크 블로그로 미뤘다.

### 1단계: 필요한 데이터만 전달한다

종목 상세는 가격이 바뀔 때마다 UI state를 새로 만들어 화면에 넘기고 있었다. Screen state 안에 stock main, price, bottom sheet, chart 등이 들어 있고, 컴포저블이 이를 collect해 각 요소에 UI state를 통째로 전달했다. 그러자 실제로는 헤더만 바뀌는데 차트와 바텀 시트까지 전부 리컴포지션됐다. 원인은 **가격을 쓰지 않는 곳까지 UI state의 변경을 감지**한 것이다. 통째로 넘기니 스킵 판정에서 같은 UI를 그리는데도 바뀌었다고 판단했다.

수정은 헤더에는 가격만, 차트와 바텀 영역에는 각자 필요한 데이터만 전달하는 것이다. 차트와 바텀 시트의 스킵을 유도한다.

### 2단계: State를 읽는 위치를 내린다

그래도 Screen 수준에서 전체 리컴포지션이 남았다. 너무 넓은 범위에서 State를 읽었기 때문이다. State는 읽는 시점에 리컴포지션을 일으키므로, 실제 변경을 추적해야 하는 위치에서 읽어야 한다. 가격을 **Flow 형태로** 내려보내고 헤더 안에서 Flow를 State로 바꿔 읽게 했다. 최종적으로 변경 지점인 헤더와 차트만 다시 그려진다.

발표자는 이 방식을 모든 화면에 적용할 필요는 없다고 선을 그었다. 증권처럼 데이터 변화가 아주 잦은 화면에서만 신경 쓰면 되고, 일반 화면에서는 이 정도까지는 필요 없다.

## 문제 2: BottomSheetScaffold를 쓸 수 없었다

바텀 시트 인터랙션은 Material의 BottomSheetScaffold로 만들려 했다. 쓰지 못했다. 제공되는 `BottomSheetState`가 open class가 아니라 커스텀할 수 없었고, `SheetValue`도 원하는 기준으로 동작하지 않았다. 예를 들어 `Hidden`은 시트가 완전히 가려지는 것인데, 토스증권이 원한 hidden은 **일부만 가려지는** 상태였다.

그래서 **Layout으로 직접** 만들었다. Compose의 Layout은 사용자가 정한 정책으로 컴포저블을 배치하며 둘을 받는다. **content**는 그려질 컴포저블이고 layoutId 같은 정보로 어떤 것인지 구분한다. 화면을 헤더, 콘텐트, 핸들, 시트 콘텐트로 나눴다. **MeasurePolicy**는 콘텐트들의 크기와 위치를 정하는 로직으로, measurable(각 콘텐트의 크기를 정할 정보)과 constraints(레이아웃에 전달된 크기 제약)를 받아 measure하면 placeable이 나오고, layout 단계에서 place한다. 콘텐트 크기는 바텀 시트 위치에 따라 달라지므로 constraints의 max 값을 조절했고, 시트 위치에 맞춰 핸들과 시트 콘텐트를 배치했다.

드래그는 `Modifier.anchoredDraggable`로 구현했다. 지정한 위치까지 드래그가 자동으로 붙는 동작을 쉽게 만드는 modifier다. 앵커는 상단에 붙음·가운데 멈춤·하단, 세 개를 Top·Middle·Bottom으로 정의하고, `onSizeChanged` 시점에 크기에 맞춰 앵커 위치를 계산해 draggable state에 넣었다. MeasurePolicy의 layout 단계에서 그 state의 offset을 읽어 위치를 정한다.

## 문제 3: 애니메이션이 프레임마다 리컴포지션을 일으킨다

바텀 시트 진행도에 따라 상단 헤더의 글씨 크기가 바뀌는 애니메이션이 있다. 처음엔 `ResizeText` 컴포저블에 시작·목표 크기와 진행도 State를 넘겨 구현했다. 잘 동작하는 듯했지만 **프레임마다 리컴포지션**이 났다. 진행도를 읽는 위치가 컴포지션 시점이었기 때문이다.

이를 풀려면 Compose가 그리는 세 단계를 알아야 한다.

| 단계 | 하는 일 | 관련 API |
| --- | --- | --- |
| Composition | 컴포저블 함수를 실행해 UI 트리를 만든다. 리컴포지션이 여기 속한다 | |
| Layout | UI 트리를 배치한다 | `Modifier.graphicsLayer`, `offset` |
| Drawing | 캔버스에 그린다 | `drawBehind`, `drawWithContent` |

글씨 크기 변경은 Layout과 Drawing 단계에서만 바뀌면 되는데, 진행도를 컴포저블 함수 안(Composition)에서 읽었으니 리컴포지션이 났다. 그 코드를 `graphicsLayer` 블록, 즉 Layout 스코프로 옮겼다. Composition 단계에서 State를 읽지 않으니 리컴포지션이 없고 Layout 단계에서만 변경을 감지해 크기를 바꾼다. 더 싼 비용으로 그리게 됐다. 모든 상황에 이렇게 할 필요는 없지만 애니메이션을 만들 때 적용하면 성능 이득이 크다.

## 리뷰

**세 문제의 답이 하나로 모인다. State를 어디서 읽는가.** 1단계는 파라미터를 잘게 나눠 스킵을 유도하고, 2단계는 State를 읽는 위치를 트리 아래로 내리고, 3단계는 읽는 위치를 Composition 단계 밖(Layout)으로 옮긴다. 셋 다 "이 값이 바뀔 때 다시 실행돼야 하는 코드의 범위"를 좁히는 일이다. 작년 발표에서 사용자 설문의 지배적 불만이 "리컴포지션 줄이기가 너무 어렵다"였는데, 그 어려움의 실체를 실제 화면으로 보여 줬다.

**선언형 UI의 편의가 고빈도 갱신에서는 비용이 된다.** "데이터를 뷰에 바로 전달하니 실수가 적다"는 것이 Compose를 고른 이유였다. 그런데 그 편의를 그대로 쓰면(UI state를 통째로 전달) 가격 하나에 화면 전체가 다시 그려진다. 증권 앱에서는 선언형의 편의를 일부 포기하고(Flow를 내려 헤더에서 State로 바꾸는 식으로) 데이터 흐름을 손으로 설계해야 했다. 발표자가 "일반 화면에서는 필요 없다"고 두 번 못 박은 것은 이 비용을 아무 데나 지불하지 말라는 뜻이다.

**Material 컴포넌트가 막히면 Layout으로 내려간다.** BottomSheetScaffold가 open class가 아니라는 이유로 커스텀을 포기하지 않고 MeasurePolicy와 anchoredDraggable로 직접 만들었다. 작년 발표의 슬롯 컴포넌트가 "Material Button의 설계를 이해하고 따라 한 것"이었다면, 이번엔 Material이 못 하는 것을 그 아래 층에서 만든 것이다.

## 남는 질문

- 가격이 초당 수십 번 오면 헤더의 리컴포지션 자체도 초당 수십 번이다. 헤더만 남겼다고 해도 그 빈도가 프레임 예산 안에 들어오는지, 아니면 Flow 단계에서 conflate·sample로 빈도를 줄였는지.
- Flow를 컴포저블 트리 아래로 내려보내는 방식은 ViewModel의 단일 UI state 원칙과 충돌한다. 어디까지 Flow로 내리고 어디부터 State로 고정하는지의 규칙을 팀이 갖고 있는지.
- 스와이프로 종목을 넘기면 옆 종목의 화면이 미리 구성되는지(pager 프리로드), 그때 옆 종목의 소켓 구독도 미리 시작되는지. 리컴포지션 최적화가 보이지 않는 페이지에서도 유효한지.
- 안정성(stability)은 "테크 블로그로"라고 미뤘는데, 실제로 파라미터 스킵이 안 되던 클래스(List, 외부 모듈 타입)를 어떻게 안정화했는지가 이 발표의 빠진 조각이다.
