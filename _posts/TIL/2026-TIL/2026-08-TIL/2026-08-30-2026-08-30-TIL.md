지난 월요일(8/24)부터 새 저장소를 한꺼번에 열었다. CTF 운영 플랫폼 flag-grid, 개발자 Q&A 플랫폼 quno, 시스템 설계 훈련 플랫폼 sys-drill이 같은 날 시작했고, 그날 밤과 다음 날 밤에는 옛 게임을 Unity로 다시 만드는 neon-diary와 원본 데이터를 분석하는 tokyo-yahwa가 생겼다. flag-grid, neon-diary, tokyo-yahwa는 Codex로, quno와 sys-drill은 Claude Code로 진행했다. 저장소마다 `AGENTS.md`나 `CLAUDE.md`부터 두고, 기획 문서를 작업 계획서로 옮긴 다음 구현에 들어갔다. 한 주 커밋 수가 많아서 전부 적지는 않고 굵은 줄기만 남긴다.

## 이번 주 한 작업

### flag-grid: CTF 백엔드와 FBCTF 방향의 화면

첫날 백엔드 골격이 거의 다 나왔다. 대회, 팀, 제출, 점수 원장과 리더보드, 세션 인증, 힌트 열람과 감점, 대회 상태 전이, 운영자 감사 로그, 리더보드 동결, 공지, 문제 공개 전이까지 하루에 들어갔다. 점수는 ADR-003에서 정한 대로 추가만 하는 원장(`score_events`)을 사실로 두고, 팀 점수는 조회용 집계로 다룬다.

8/25에는 첨부 파일을 업로드 세션과 다운로드 티켓 흐름으로 만들고, 저장소를 로컬과 S3 presigned URL 중에서 고를 수 있게 했다. 실시간 갱신은 SSE로 내보내고, 인스턴스가 여럿일 때를 위해 Redis fan-out 브로커를 선택적으로 붙였다. Redis가 없으면 메모리 브로커로 내려가는 경로도 테스트했다. 운영 런북, 스모크 시나리오, 릴리스 점검 게이트, Playwright 회귀 테스트도 같은 날 추가했다.

화면은 처음에 폼 위주의 관리 화면이었는데, ADR-013에서 FBCTF를 1차 레퍼런스로 삼기로 정했다. 단 원본을 복제하지 않고 지금의 도메인 모델과 API에 맞춰 독립 구현한다는 조건을 같이 적었다. 8/26과 오늘(8/30)은 대부분 이 포팅 작업이었다. 게임보드 모듈, 공개 페이지, 관리자 내비게이션을 FBCTF의 구조에 맞추고, 오늘 밤에는 공개 팀 등록 흐름과 로그인 뒤 팀 컨텍스트 복원을 고쳤다.

### neon-diary와 tokyo-yahwa: 원본 분석과 Unity 구현을 나눈 구조

두 저장소는 역할을 처음부터 나눴다. tokyo-yahwa는 원본 게임 패키지를 분석해 파일 형식 문서, 리소스 매니페스트, 핸드오프 문서를 만드는 상류 저장소다. 원본 파일은 Git에 넣지 않고 분석 도구와 결과물만 추적한다. 8/25 밤에 charinfo, pot, 맵 헤더 추출기를 만들고 dat 레코드 구조를 탐색했으며, 8/26에는 chr 프레임, pat 이미지, 비트맵 폰트 매니페스트를 정리했다.

neon-diary는 이 결과를 받아 Unity 6 URP 위에서 구현하는 쪽이다. 8/25에 부트스트랩 서비스, ScriptableObject 기반 데이터, additive 씬 전환, 세이브 스냅샷을 placeholder 데이터로 먼저 세웠다. 8/26에는 핸드오프 문서를 읽는 순서를 프롬프트 파일로 남겼다. 상류 결과를 먼저 믿고, 구현하다가 모순이 보일 때만 원본을 다시 연다는 규칙이다. 이후 한글 비트맵 폰트와 원본 배경을 런타임에 붙였다.

8/28부터 오늘까지는 검증 장치를 많이 넣었다. 스토리 진행 계약 검증, 세이브 후 복원을 왕복하는 smoke 경로, 런타임 검증 리포트, 가져온 디자인 에셋을 배치 모드로 검사하는 래퍼가 들어갔다.

### quno와 sys-drill: 단계별 계획서를 따라가는 진행

두 저장소는 계획서의 단계를 하나 끝낼 때마다 체크리스트를 갱신하는 방식으로 진행했다. quno는 Question 리비전과 Diff, 답변 채택, 태그 팔로우, Watch 기반 알림과 Outbox 소비 워커, PostgreSQL 전문 검색을 거쳐 Vote, Comment, Save, Follow User까지 왔다. 프론트엔드는 Next.js로 Phase 0~6을 진행했다.

sys-drill은 쿠폰 장애 시나리오에서 시작해 규칙 기반 평가와 Claude를 섞은 하이브리드 평가, Docker 샌드박스에서 돌리는 Build Mode(Rate Limiter, Circuit Breaker, Distributed Lock, Retry/Backoff, Event Bus)를 차례로 붙였다. 오늘은 Toxiproxy로 실제 네트워크 지연을 주입하는 단계와 OpenTelemetry 트레이싱 단계를 끝냈다.

iterview는 화면 재설계를 마무리하고 이번 주 후반 내내 UI 문구를 한국어로 옮겼다.

## 같은 팀의 정답 두 개가 동시에 들어오면

flag-grid에서 가장 기억에 남는 수정은 `fix(backend): normalize concurrent duplicate solves`였다. 같은 팀이 같은 문제의 정답을 거의 동시에 두 번 제출하는 경우다.

제출 처리 흐름은 이랬다.

1. `existsByCompetitionIdAndTeamIdAndChallengeId`로 이미 푼 문제인지 확인한다.
2. 아니면 제출 기록을 저장한다.
3. 정답이면 `challenge_solves`에 풀이 기록을 넣는다.

스키마에는 `(competition_id, team_id, challenge_id)` 유니크 제약이 이미 있어서 점수가 두 번 들어갈 일은 없었다. 문제는 응답이었다. 두 요청이 동시에 1번을 통과하면 둘 다 "아직 안 풀었다"고 판단하고, 늦게 INSERT한 쪽이 유니크 제약에 걸린다. 이 `DataIntegrityViolationException`을 아무도 잡지 않아서, 사용자 입장에서는 정상적인 중복 제출이 500 서버 오류로 보였다.

고친 방식은 단순하다. 풀이 기록 INSERT를 `saveAndFlush`로 바꾸고 `try`로 감싸서, 제약 위반을 "이미 풀었음" 409(`SUBMISSION-003`)로 바꿨다. 이 엔티티는 `IDENTITY` 전략이라 `save`만으로도 INSERT가 바로 나가지만, `saveAndFlush`로 써 두면 ID 전략이 바뀌어도 예외가 커밋 시점까지 밀리지 않고 `try` 안에서 난다.

핵심은 앞의 존재 확인이 동시성 방어가 아니라는 점이다. 확인과 INSERT 사이에는 틈이 있고, 그 틈은 애플리케이션 코드로 닫히지 않는다. 최종 판정은 DB 제약이 하고, 애플리케이션은 제약 위반을 도메인 오류로 번역하는 역할만 맡는다. 앞의 확인은 대부분의 중복을 싸게 걸러내는 최적화로 남겨 둔다.

테스트도 같이 넣었다. `CountDownLatch`로 두 스레드를 동시에 출발시키고, 응답 상태가 정확히 `[200, 409]`이고 리더보드 점수가 75점 한 번만 반영됐는지 본다. 같은 시각에 들어간 핫 문제 부하 스크립트도 "동일 팀 정답 버스트는 200 한 건, 나머지는 409"를 기대 결과로 적어 두었다.

## 느낀 점

화요일 저녁 18시 무렵, 다섯 저장소에 ADR을 소급해서 기록한 커밋이 30분 안에 연달아 남아 있다. quno에는 결정 13건, neon-diary에는 8건이 한 번에 들어갔다. 에이전트와 빠르게 진행하면 결정이 코드 속에 묻히기 쉬운데, 이렇게 한 번 꺼내 적어 두니 이후 커밋에서 "ADR-0014로 기록", "ADR-013에 따라"처럼 결정을 참조하며 진행하게 됐다.

neon-diary와 tokyo-yahwa를 나눈 것도 같은 맥락이었다. 분석과 구현을 한 저장소에서 섞으면 에이전트가 매번 원본을 다시 파헤칠 수 있다. 상류 저장소의 핸드오프 문서를 계약처럼 두니 구현 쪽 세션은 그 문서만 읽고 시작할 수 있었다.

동시 제출 건은 기능이 다 돌아가는 것처럼 보여도 동시에 두 번 누르는 경우는 따로 시험해야 드러난다는 걸 다시 확인한 일이었다. 단건 테스트로는 이 500이 나오지 않는다.
