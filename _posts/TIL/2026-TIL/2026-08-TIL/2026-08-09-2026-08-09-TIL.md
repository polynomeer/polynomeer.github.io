## 참여 트랜잭션의 실패와 commit 위치

이번 기간에 가장 오래 붙잡은 건 mini-transaction에 rollback-only 전파를 넣다가 만난 버그였다.

`REQUIRED`로 참여한 안쪽 메서드가 실패하면, 참여자는 커넥션을 실제로 롤백하지 않는다. 트랜잭션의 주인이 아니기 때문이다. 대신 공유하는 홀더에 rollback-only 표시만 남긴다. 바깥 메서드가 그 예외를 잡아 삼키고 정상 종료하더라도, 주인이 `commit()`을 호출하는 시점에 표시를 보고 실제로 롤백한 뒤 `UnexpectedRollbackException`을 던진다. 실제 Spring에서 확인한 결과는 이랬다.

| 상황 | 결과 |
| --- | --- |
| `REQUIRED` 참여자 실패, 바깥에서 catch | `UnexpectedRollbackException`, 전체 롤백 |
| `REQUIRES_NEW` 실패, 바깥에서 catch | 예외 없음, 안쪽 변경만 롤백 |
| `NESTED` 실패, 바깥에서 catch | 예외 없음, savepoint까지만 롤백 |

13주차 mini 구현은 참여자의 실패를 주인에게 전혀 알리지 않았다. 그런데도 테스트가 통과했던 건 바깥이 예외를 그대로 던지는 경우만 봤기 때문이다. 바깥이 예외를 삼키는 순간 조용히 커밋될 구조였다.

그래서 rollback-only 전파를 넣었더니 이번에는 다른 곳이 터졌다. 인터셉터를 단순화하면 이런 모양이었다.

```java
try {
    Object result = invocation.proceed();
    txManager.commit(status);   // 여기서 MiniUnexpectedRollbackException
    return result;
} catch (Throwable ex) {
    txManager.rollback(status); // 이미 닫힌 커넥션에 다시 rollback
    throw ex;
}
```

`commit()`이 예외를 던질 수 있게 되자 같은 `catch`가 그걸 실행 실패로 받아서, 이미 정리된 트랜잭션에 `rollback()`을 다시 호출했다. 결과는 "connection is closed" 오류였다. Spring의 `TransactionAspectSupport.invokeWithinTransaction()`을 다시 보니 `commitTransactionAfterReturning()`은 `proceed()`를 감싼 `try`/`catch`/`finally` 바깥에 있었다. 실행 실패와 커밋 실패를 다른 경로로 처리하려는 구조다. 같은 모양으로 `commit()`을 `try` 밖으로 옮겨서 해결했다.

`NESTED`와 `REQUIRES_NEW`의 차이도 이번에 정확히 알게 됐다. 둘 다 안쪽 실패가 바깥으로 번지지 않아서 결과만 보면 비슷하다. 하지만 `REQUIRES_NEW`는 기존 커넥션을 스레드에서 떼어 두고(suspend) 새 물리 커넥션을 쓴다. `NESTED`는 같은 커넥션 위에 savepoint를 하나 만들 뿐이다. 실험에서도 `NESTED`는 바깥과 같은 `Connection` identity가 나왔다.

## 느낀 점

얕은 축소 구현은 겉으로는 테스트를 통과한다. 정책을 하나씩 실제에 가깝게 추가할 때 숨어 있던 구조적 가정이 드러난다. 이번 버그도 rollback-only를 넣기 전까지는 보이지 않았다. Spring 소스에서 `commit` 호출이 왜 그 위치에 있는지는, 직접 틀리게 만들어 보고 나서야 이해가 됐다.

Dudecide를 문서부터 시작한 것도 비슷한 이유였다. 에이전트와 같이 작업하면 결정 근거가 대화에 묻히기 쉽다. 그래서 상태 머신과 투표 규칙을 먼저 문서로 고정하고, 구현은 그 문서를 기준으로 진행하게 했다. 스택을 하루 만에 바꾼 것도 ADR에 이유와 함께 남아 있어서 나중에 다시 볼 수 있다.
