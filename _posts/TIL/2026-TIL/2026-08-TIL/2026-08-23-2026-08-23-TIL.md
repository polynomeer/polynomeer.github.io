이번 2주는 다섯 달 가까이 멈춰 있던 Starkraft를 다시 연 기간이었다. 결정적(deterministic) RTS 시뮬레이션 코어는 3월에 거의 완성해 두었고, 이번에는 libGDX 클라이언트를 실제로 반복해서 플레이할 수 있는 상태로 만드는 데 집중했다. 그 사이 Dudecide 프론트엔드를 붙였고, spring-internals-lab은 캡스톤으로 마무리 단계에 들어갔다. 주 후반에는 iterview 화면을 전반적으로 다시 짰다.

## 이번 2주 동안 한 작업

### Starkraft: 1단계 안정화

8월 12일에 상용화 로드맵과 1단계 안정화 계획을 먼저 문서로 썼다. 1단계 목표는 폴리싱이 아니라 "반복되는 내부 플레이 세션에서 믿고 쓸 수 있는 클라이언트"다. 종료 조건으로는 일반 플레이 중 크래시가 없을 것, HUD가 월드를 가리지 않을 것, 핵심 명령이 일관되게 동작할 것, 클라이언트 I/O가 깨지지 않을 것을 적었다.

이후 커밋은 대부분 이 목록을 따라갔다.

- **입력 상태 정리:** 선택 없이 명령을 대기 상태로 만들 수 없게 막았다. 공격 모드에서 아군 클릭을 거부하고, 명령 대기 중에는 박스 선택과 미니맵 드래그를 막았다. HUD 위에서의 클릭이 월드로 새지 않게 했고, 오버레이가 떠 있을 때는 단축키와 포인터 제스처를 끊었다.
- **작은 화면 대응:** 하단 HUD, 명령 덱, 상단 바를 작은 화면에서 압축하고, 월드 뷰포트를 HUD 경계에 맞췄다.
- **렌더링 비용:** 명령 덱, 선택 HUD, HUD 프레임을 매 프레임 다시 만들지 않도록 캐시했다. 바뀌지 않은 라벨과 액터 상태는 갱신을 건너뛰고, 화면 밖 타일은 그리지 않게 했다.
- **표현 계층:** 하드코딩된 색을 프레젠테이션 테마 토큰으로 옮겼다. 큐에 쌓인 명령(Shift 체이닝)과 집결 명령을 화면에 표시하고, 비활성 명령에는 이유를 보여주게 했다.

8월 19일 밤에는 기획, 밸런스, 클라이언트 UX, 릴리스와 리플레이 검증, 운영과 디버깅 템플릿 같은 문서를 한꺼번에 추가하고 README에 문서 안내표를 만들었다.

### Dudecide: API 마무리와 Next.js 프론트엔드

8월 10일에는 백엔드를 마저 채웠다. 투표 생성과 마감, 초대와 멤버십, 결정 초안과 재검토 흐름, 리포트 갱신, 멱등성 키, outbox와 알림 스케줄러, 액터 기반 접근 제어가 들어갔다. 11일에는 프론트엔드 구현 계획을 쓰고 Next.js 앱을 만들어 스레드, 결정 보드, 투표, 검색, 작업 화면을 붙였다. 12일에는 실시간 동기화와 Vitest, 라우트 통합 테스트, Playwright 스모크 테스트를 추가했다. 13일에 로컬 스택을 처음 실제로 띄워 보니 CORS와 JSON 필드 이름이 프론트엔드와 맞지 않아서 둘 다 고쳤다.

### spring-internals-lab: 캡스톤과 내부 동작 실험

지난번에 다음 할 일로 적어 둔 두 가지를 진행했다. 지금까지 만든 축소 구현을 Mini Order Platform이라는 캡스톤으로 묶었다. Bean, AOP, 트랜잭션, MVC, 이벤트, Boot 순서로 여섯 단계에 걸쳐 쌓았다. mini-transaction에는 생략했던 `NESTED` 전파를 JDBC savepoint로 추가했다. 그 뒤로는 `@Cacheable`, `@Async`, `@Scheduled`, `@Lookup`, `FactoryBean`, `ObjectProvider`, `BeanPostProcessor` 등록 순서처럼 하나씩 따로 보면 좋을 주제들을 작은 실험 모듈로 하나씩 만들었다.

### monticker: 디자인 정리와 테스트 재정비

13~16일에는 웹 화면에 디자인 시스템을 적용하고 UI/UX 점검 결과를 반영했다. 접근성 이름이 없던 입력에 이름을 붙이고, 터치 영역을 넓히고, 임의 hex 색을 토큰으로 바꿨다. 19~20일에는 백엔드 모듈마다 Testcontainers 기반 `integrationTest` 소스셋을 만들고, 실제 API와 웹 서버를 상대로 하는 Playwright e2e를 CI에 붙였다.

여기서 버그가 하나 나왔다. `findTopByOrderByEventTimeDesc`는 `limit` 파라미터와 상관없이 항상 1건만 돌려주고 있었다. Spring Data 메서드 이름의 `Top` 뒤에 숫자가 없으면 결과가 1건으로 고정되고, 호출자가 넘긴 `Pageable` 크기보다 그게 우선한다. 목 기반 단위 테스트로는 보이지 않던 문제였고, 실제 Postgres로 리포지토리를 검증하는 통합 테스트를 새로 쓰면서 드러났다. 이름을 `findByOrderByEventTimeDesc`로 바꿔 `Pageable`이 크기를 정하게 했다.

## 프로세스 사이에서 파일로 상태를 주고받을 때

Starkraft 플레이 런처는 시뮬레이션과 클라이언트를 별도 프로세스로 띄운다. 둘은 파일로 통신한다.

- 클라이언트는 일시정지 여부와 배속을 control 파일에 쓴다. 시뮬레이션은 틱마다 이 파일을 읽는다.
- 시뮬레이션은 스냅샷을 NDJSON 파일에 한 줄씩 덧붙인다. 런처는 첫 스냅샷이 생길 때까지 기다렸다가 클라이언트를 붙인다.

8월 14일에 이 두 경로에서 같은 종류의 문제를 고쳤다. 읽는 쪽이 아직 쓰는 중인 파일을 보는 문제다.

control 파일은 `Files.writeString(path, ...)`으로 바로 덮어쓰고 있었다. 이 호출은 파일을 비운 다음 내용을 쓰기 때문에, 그 사이에 시뮬레이션이 읽으면 빈 파일이나 반쯤 쓰인 내용을 보게 된다. 같은 디렉터리에 임시 파일을 만들어 다 쓴 뒤 이름을 바꾸는 방식으로 고쳤다.

```kotlin
Files.writeString(temp, text)
try {
    Files.move(temp, path, REPLACE_EXISTING, ATOMIC_MOVE)
} catch (_: AtomicMoveNotSupportedException) {
    Files.move(temp, path, REPLACE_EXISTING)
}
```

같은 파일 시스템 안의 rename은 원자적이라, 읽는 쪽은 이전 내용이나 새 내용 중 하나만 보게 된다. 임시 파일을 대상과 같은 디렉터리에 만드는 이유도 여기에 있다. 다른 파일 시스템으로의 이동은 원자적으로 할 수 없다. 원자적 이동이 지원되지 않는 환경에서는 일반 이동으로 물러나게 했다.

스냅샷 쪽은 반대 방향이었다. 런처는 "파일이 있고 크기가 0보다 크면" 첫 스냅샷이 준비됐다고 판단했다. 그런데 NDJSON은 한 줄이 끝나야 레코드 하나가 완성된다. `{"recordType":"snapshot"`까지만 쓰인 순간에도 크기는 0보다 크다. 판단 기준을 "개행 문자가 하나라도 있는가"로 바꾸고, 반쪽 레코드를 먼저 쓰고 나중에 `}\n`을 덧붙이는 테스트로 확인했다.

두 수정 모두 이미 있던 쓰는 쪽과 읽는 쪽의 계약을 분명히 한 것이다. 덮어쓰는 파일은 rename으로 교체하고, 덧붙이는 파일은 줄 단위로만 읽는다.

## 느낀 점

1단계 계획에 "클라이언트 I/O가 깨지지 않을 것"을 종료 조건으로 적어 둔 덕분에 이런 문제를 따로 찾아보게 됐다. 평소 플레이에서는 거의 재현되지 않는 종류의 버그라, 목록에 없었다면 넘어갔을 것 같다.

monticker의 `Top` 버그도 비슷했다. 목으로 리포지토리를 대신하는 테스트는 메서드 이름이 실제로 어떤 쿼리가 되는지 검증하지 못한다. 실제 DB를 붙인 테스트를 처음 쓰자마자 나온 버그라서, 통합 테스트 소스셋을 따로 나눈 게 의미가 있었다.

Starkraft는 이번 기간 커밋 대부분이 화면과 입력이었다. 시뮬레이션 코어가 결정적으로 고정되어 있으니 클라이언트를 많이 바꿔도 규칙이 흔들릴 걱정은 적었다. 다만 HUD 커밋이 짧은 간격으로 수십 개 이어지면서 중간에 되돌리는 수정도 몇 개 생겼다.
