9월 19일부터 28일까지를 묶어서 정리한다. 커밋이 몰린 날은 21일이었다. 이날 proofu, monticker, code-drill, neon-diary, parity-pay에서 모두 커밋이 나왔다. 기능을 새로 넣기보다 이미 만든 것을 검증하고, 처음 보는 사람이 읽을 수 있게 정리한 작업이 많았다. 중간중간 지원 서류도 정리했다. 코드 작업은 대부분 Claude Code 세션에서 진행했고, neon-diary만 Codex로 진행했다.

## 이번 주에 한 작업

### proofu: 생성에서 제출, 내보내기까지

지난주에 시작한 proofu는 이력서 생성 흐름의 뒷부분을 채웠다.

- 20일: 승인된 주장에서 문서 블록 초안을 만드는 생성 기능을 넣었다. 모델은 허용된 참조만 인용할 수 있고, 생성된 버전에는 출처가 고정된다.
- 21일 오전: 승인된 버전만 제출 스냅샷으로 얼리게 했다. DOCX, Markdown, JSON, PDF 내보내기를 붙였다(ADR-0009). 렌더링한 파일에서 텍스트를 다시 추출해 원본과 맞는지 검증한 뒤에 저장한다.
- ATS 호환성 검사는 점수 없이 확인 항목만 보여 주게 했다. 문장 다듬기에는 의미를 바꾸는 수정을 거부하는 가드를 붙였다. 같은 날 오후에는 표기만 바뀐 날짜와 천 단위 숫자를 같은 값으로 보도록 고쳤고, 밤에는 원문에 있던 숫자를 빠뜨린 수정도 거부하게 했다.
- 21일 밤: 모델 제공자 오류를 과금, 인증, 요청 한도, 과부하로 구분했다. 운영자가 손을 대야 하는 오류에는 알림을 걸었다. 운영 프로파일에서는 가짜 AI 제공자를 쓸 수 없게 막았다.
- 22일: OIDC 로그인을 붙였다(ADR-0010). 그 위에 재인증이 필요한 계정 삭제, 전체 데이터 내보내기, 보존 기간 설정을 올렸다.
- 23~24일: 기술과 역량 모델, 관측성, CSP, axe-core로 자동 접근성 검사를 넣었다. 키셋 커서 버그도 고쳤다. Postgres의 `cast(ts as date)`는 세션 타임존을 쓰는데 커서는 UTC로 만들고 있었다. 그래서 한국 시간 0시부터 9시 사이에는 목록의 두 번째 페이지가 비어 있었다.
- 24일: 워커가 작업 도중 죽으면 `RUNNING`으로 남은 작업이 영영 다시 시도되지 않았다. 15분 lease가 지난 작업은 다시 큐에 넣게 했다. 모델 호출 한 번은 4분과 SDK 재시도 한 번으로 묶었다. 호출이 lease보다 길어지면 같은 작업이 두 번 돌 수 있기 때문이다.

### monticker: 보안 리뷰와 검증 강화

21일에 영역별로 나눠 코드 수준 보안 리뷰를 하고 문서로 남겼다. Critical로 분류한 것이 셋이었다.

- 어떤 배포 경로도 `prod` 프로파일을 켜지 않았다. 그래서 공개 저장소에 커밋된 개발용 JWT 비밀키와 암호화 키가 그대로 쓰일 상황이었다.
- 리프레시 토큰을 브라우저 저장소에 두고 있었다.
- 실계좌 주문 API에 입력 검증이 없었다.

같은 날 대부분을 고쳤다. 기본 비밀키로는 서버가 뜨지 않게 했고, 리프레시 토큰은 HttpOnly 쿠키로 옮겼다. 토큰 재사용을 감지하면 세션 계열 전체를 폐기하게 했고, 주문은 브로커로 보내기 전에 검증하게 바꿨다. 23일에는 감지된 이벤트로 페이퍼 주문을 내는 감시 규칙(ADR-051)을 넣었다. 현금 예약 락 전략 세 가지를 실제 Postgres에서 비교해 ADR-052로 남겼다. 첫 측정은 커넥션 풀 없이 돌려서 세 전략이 구분되지 않았고, 이 방법론 오류도 ADR에 같이 기록했다.

## 배운 점: 통과하는 테스트가 무엇을 잡는가

code-drill의 프로젝트형 문제에는 패키지마다 참조 구현과 대표 오답(mutants)이 있다. 원래 오답은 문제를 만들 때 숨은 테스트가 충분히 촘촘한지 확인하는 용도였다. 21일에는 이걸 사용자 쪽으로 돌렸다. 사용자가 더 쓴 테스트가 실제로 결함을 잡는지 재는 결함 검출(DEFECT_DETECTION) 역량이다.

규칙은 두 가지다.

1. 사용자의 테스트는 참조 구현에서 통과해야 한다. 틀린 동작을 기대하는 테스트는 테스트가 아니다.
2. 그 테스트를 오답 구현 위에서 돌렸을 때 오답의 절반 이상을 떨어뜨리면 성공이다.

첫 스모크에서 바로 구멍이 보였다. 사용자 테스트 파일에는 시작 저장소의 공개 테스트가 그대로 들어 있다. 그래서 사소한 테스트 하나만 더 써도, 공개 테스트가 원래 잡던 오답이 전부 사용자가 잡은 것으로 계산됐다. 없는 상품의 재고가 0이라는 테스트 하나로 오답 넷 중 둘을 잡은 것으로 나왔다.

고친 방법은 이렇다. 사용자 테스트로 떨어진 오답마다 공개 테스트만으로 한 번 더 돌린다. 그때도 떨어지면 `alreadyCaught`로 분류해 사용자의 몫에서 뺀다. 추가 실행은 잡힌 오답에만 하므로 비용도 크지 않다. 문제를 만들 때도 조건을 하나 더 붙였다. 공개 테스트가 못 잡는 오답이 최소 둘은 있어야 이 역량을 잴 수 있다는 것이다.

이건 뮤테이션 테스트의 기본 아이디어와 같다. 테스트가 통과했다는 사실만으로는 아무것도 알 수 없다. 일부러 틀린 구현을 넣어 봐야 그 테스트가 무엇을 잡는지 보인다. 그리고 점수를 매길 때는 기준선을 빼야 한다. 기존 테스트가 이미 하던 일까지 새 테스트의 성과로 세면 숫자는 좋아 보여도 아무것도 재지 못한다.

## 느낀 점

이번 주에 고친 것들은 대부분 "통과는 하는데 실제로는 아무것도 보장하지 않는" 경우였다. 테스트는 통과하는데 결함을 잡지 못했고, 설정 파일에는 운영 값이 있는데 어떤 배포 경로도 그 프로파일을 켜지 않았다. 측정은 돌아갔지만 커넥션 풀이 없어서 비교가 되지 않았다. 확인 방법을 하나 더 붙이면 이런 것들이 보였다. 오답 위에서 다시 돌리기, 배포 경로를 실제로 따라가기, 측정 조건을 다시 보기 같은 것들이다.

proofu에서 lease와 모델 호출 시간 상한을 같이 정한 것도 비슷했다. 실패한 작업을 다시 시도하게 만드는 순간, 첫 시도가 아직 끝나지 않은 경우까지 같이 생각해야 했다.
