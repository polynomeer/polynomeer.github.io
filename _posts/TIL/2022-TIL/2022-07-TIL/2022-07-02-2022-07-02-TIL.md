## Today I Learned

### Unit Testing

Spring Boot 애플리케이션의 테스트 작성법을 모아 읽었다. Spring 레퍼런스는 IoC를 제대로 쓰면 setter와 생성자로 객체를 직접 조립할 수 있어 단위 테스트와 통합 테스트가 모두 쉬워진다고 설명한다.

Spring Boot는 테스트 범위에 따라 어노테이션을 나눠 제공한다. Baeldung 글 기준으로 정리하면 다음과 같다.

- `@SpringBootTest`: 전체 애플리케이션 컨텍스트를 띄우는 통합 테스트. `webEnvironment` 속성으로 mock 서블릿 환경 등을 고른다.
- `@WebMvcTest`: Spring MVC 인프라만 자동 구성하고, 대부분 컨트롤러 하나만 띄운다. Spring 가이드도 서버를 띄우지 않고 웹 계층만 좁혀 테스트할 때 이 어노테이션을 쓴다.
- `@DataJpaTest`: 인메모리 H2, Hibernate, Spring Data, `DataSource`를 구성하고 SQL 로그를 켜서 영속성 계층만 테스트한다.
- `@MockBean`: 의존하는 빈(예: Service가 의존하는 Repository)을 mock으로 바꿔 넣는다. `@MockBean`과 `@SpyBean`은 Spring Boot 1.4에서 추가되었다.

### Upsert

Upsert는 insert와 update를 합친 말로, 데이터가 없으면 넣고 있으면 고치는 로직이다. 참고한 글은 MySQL 계열의 `INSERT ... ON DUPLICATE KEY UPDATE` 구문 예를 들고, 오라클에서는 `MERGE`를 제공한다고 덧붙인다.

### Upsert in JPA

크게 두 가지 방법이 있다. 첫 번째는 애플리케이션의 서비스 코드에서 findById로 찾은 다음 있으면 update, 없으면 insert 하는 것이다. 두 번째는 쿼리로 ON DUPLICATE KEY UPDATE 또는 REPLACE를 사용하는 것이다. 하지만 JPA에서 제공되는 것 같지는 않고, 또 쿼리에 의존하는 것 보다는 애플리케이션에서 처리하는게 나아보인다. 물론 성능은 쿼리에서 처리하는게 약간 더 빠르지 않을까 추측이 된다. (한 번의 쿼리로 실행이 가능하기 때문에)

Spring Data JPA의 `save()`가 이미 이 분기를 하고 있다. 새 엔티티면 `persist()`를, 아니면 `merge()`를 호출한다. 그래서 `@Id` 값을 애플리케이션에서 직접 채워 넣는 엔티티는 DB에 이미 있는 데이터로 간주되어, `save()`가 insert 전에 select를 한 번 실행한다. 조회 결과가 없어야 비로소 insert가 나간다. 이런 엔티티를 `saveAll()`로 대량 저장하면 건수만큼 select가 함께 실행된다.

또 Hibernate는 기본적으로 엔티티에 매핑된 모든 컬럼을 대상으로 INSERT와 UPDATE 문을 만든다. 바뀐 컬럼만 쓰고 싶으면 Hibernate의 `@DynamicInsert`, `@DynamicUpdate`를 붙인다.

### Ansible

Ansible은 오픈소스 IT 자동화 도구로, 인프라 설정을 코드로 작성해 여러 서버에 배포함으로써 같은 환경을 유지하게 해 준다. 설정은 YAML로 쓴다. 관리 대상 서버에 에이전트를 설치하고 대상이 설정을 당겨 가는(PULL) 다른 도구와 달리, Ansible은 에이전트 없이 SSH로 제어 노드에서 관리 노드로 밀어 넣는(PUSH) 방식으로 동작한다.
