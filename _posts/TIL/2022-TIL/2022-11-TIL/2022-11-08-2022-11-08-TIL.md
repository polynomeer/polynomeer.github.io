### Spring Actuator

Spring Boot Actuator는 운영 중인 애플리케이션의 상태를 확인하는 엔드포인트를 제공한다. `health`(상태), `info`, `metrics`, `env`, `loggers`(로그 레벨 조회·변경), `threaddump`, `heapdump` 등이 있다. 보안을 위해 HTTP로는 기본적으로 `health`만 노출되고, 나머지는 `management.endpoints.web.exposure.include`로 열어야 한다. JMX로는 `shutdown`을 뺀 대부분이 기본 노출된다([Spring Boot: Actuator](https://docs.spring.io/spring-boot/docs/2.7.x/reference/html/actuator.html)).

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus
  server:
    port: 9001   # 관리용 포트를 서비스 포트와 분리
```

`env`나 `heapdump`는 설정값과 메모리 내용을 그대로 보여 주므로, 열어야 한다면 관리 포트를 내부망에만 두거나 Spring Security로 보호한다. Kubernetes 환경에서는 `health` 아래의 liveness, readiness 그룹이 프로브 대상으로 쓰인다.

### Transaction Isolation Levels

MySQL InnoDB는 SQL 표준의 네 가지 격리 수준을 모두 지원하고 기본값은 `REPEATABLE READ`다([MySQL 8.0: Transaction Isolation Levels](https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-isolation-levels.html#isolevel_repeatable-read)).

| 격리 수준 | 일반 SELECT가 보는 것 | 비고 |
| --- | --- | --- |
| READ UNCOMMITTED | 커밋되지 않은 변경까지 | dirty read 가능 |
| READ COMMITTED | 각 SELECT 시점에 커밋된 데이터 | 같은 트랜잭션에서도 SELECT마다 새 스냅샷 |
| REPEATABLE READ | 트랜잭션의 첫 읽기 시점 스냅샷 | 일반 SELECT끼리는 결과가 일관됨 |
| SERIALIZABLE | REPEATABLE READ와 같되 | autocommit이 꺼져 있으면 일반 SELECT를 `SELECT ... FOR SHARE`로 바꿈 |

문서에서 놓치기 쉬운 점은 잠금 읽기(`SELECT ... FOR UPDATE`, `UPDATE`, `DELETE`)는 스냅샷이 아니라 최신 데이터를 대상으로 한다는 것이다. REPEATABLE READ에서 범위 조건으로 잠금 읽기를 하면 갭 락이나 넥스트 키 락으로 그 범위에 대한 삽입을 막는다. 문서는 같은 REPEATABLE READ 트랜잭션 안에서 잠금 문장과 일반 SELECT를 섞지 말라고 권하는데, 둘이 서로 다른 상태의 테이블을 읽기 때문이다.

- https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-isolation-levels.html#isolevel_repeatable-read

### JPA Propagation and Isolation Level

Spring `@Transactional`의 `propagation`과 `isolation` 속성은 서로 다른 축이다. 전파 속성은 이미 트랜잭션이 있을 때 참여할지 새로 만들지를 정하고, 격리 수준은 DB 트랜잭션끼리 얼마나 서로를 보지 않을지를 정한다.

- `REQUIRED`(기본값): 기존 트랜잭션에 참여하고 없으면 새로 만든다. 같은 물리 트랜잭션에 참여한 안쪽 메서드가 롤백 전용으로 표시하면, 바깥에서 커밋할 때 `UnexpectedRollbackException`이 난다.
- `REQUIRES_NEW`: 항상 독립된 물리 트랜잭션을 연다. 바깥 트랜잭션이 커넥션을 쥔 채로 커넥션을 하나 더 쓰므로, 커넥션 풀이 동시 스레드 수에 비해 작으면 고갈될 수 있다.
- `NESTED`: 하나의 물리 트랜잭션 안에서 JDBC savepoint로 부분 롤백한다. JDBC 기반 트랜잭션 매니저에서만 동작한다.

중요한 점은 격리 수준, 타임아웃, readOnly 설정이 새 트랜잭션이 시작될 때만 적용된다는 것이다. `REQUIRED`로 기존 트랜잭션에 참여한 안쪽 메서드에 다른 격리 수준을 적어도 기본적으로는 조용히 무시되고 바깥 설정을 따른다. 이런 불일치를 거부하게 하려면 트랜잭션 매니저의 `validateExistingTransaction`을 켠다([Spring Framework: Transaction Propagation](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html)).

### JPA Optimistic lock vs Pessimistic lock

두 사용자가 같은 행을 읽고 각자 수정해서 저장하면, 나중에 저장한 쪽이 먼저 저장한 변경을 덮어쓰는 lost update가 생긴다. Vlad Mihalcea의 글은 이를 다루는 두 전략을 충돌을 "막을 것인가, 감지할 것인가"로 구분한다.

비관적 락은 충돌을 미리 막는다. 읽을 때 행에 락을 걸어 다른 트랜잭션이 수정하지 못하게 한다. JPA에서는 `@Lock(LockModeType.PESSIMISTIC_WRITE)`로 조회하면 `SELECT ... FOR UPDATE`가 나간다. 확실하지만 락을 기다리는 동안 처리량이 떨어지고, 여러 행을 다른 순서로 잠그면 데드락이 생길 수 있다.

낙관적 락은 충돌을 허용하고 커밋 시점에 감지한다. 엔티티에 `@Version` 필드를 두면 JPA가 UPDATE 조건에 버전을 넣고 값을 올린다. 그 사이 다른 트랜잭션이 먼저 수정해서 버전이 바뀌었으면 갱신된 행이 0개가 되고 `OptimisticLockException`이 난다. 버전 필드는 엔티티당 하나이고 `int`, `long`, `short`(및 래퍼 타입)나 `java.sql.Timestamp` 타입이어야 하며, 값은 애플리케이션이 직접 바꾸지 않는다([Baeldung: Optimistic Locking in JPA](https://www.baeldung.com/jpa-optimistic-locking)).

```java
@Entity
public class Stock {
    @Id @GeneratedValue
    private Long id;
    private int quantity;

    @Version
    private Long version;
}
// UPDATE stock SET quantity = ?, version = 6 WHERE id = ? AND version = 5
```

선택 기준은 충돌 빈도와 재시도 비용이다. 충돌이 드물고 재시도가 싸면 낙관적 락이, 충돌이 잦거나(인기 상품 재고 차감) 재시도가 비싸면 비관적 락이 낫다. 낙관적 락을 쓰면 예외를 잡아 재시도하거나 사용자에게 알리는 처리가 함께 필요하다.
