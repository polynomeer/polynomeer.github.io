### 커밋 날짜 바꾸기

Git 커밋에는 작성자 날짜(author date)와 커미터 날짜(committer date) 두 가지가 있다. [git-commit 문서](https://git-scm.com/docs/git-commit)에 따르면 `--date` 옵션은 작성자 날짜를 덮어쓴다. 커미터 날짜는 `GIT_COMMITTER_DATE` 환경 변수로 지정한다.

```bash
# 직전 커밋의 두 날짜를 모두 바꾼다
GIT_COMMITTER_DATE="2022-03-18T10:00:00" git commit --amend --no-edit --date="2022-03-18T10:00:00"
```

더 이전 커밋은 `git rebase -i`로 해당 커밋을 `edit`으로 표시하고 멈춘 지점에서 같은 방식으로 amend한 뒤 `git rebase --continue`를 한다. 날짜를 바꾸면 커밋 해시가 바뀌는 히스토리 재작성이므로, 이미 공유된 브랜치라면 강제 푸시가 필요하고 다른 사람의 작업과 충돌할 수 있다.

### 단위 테스트

링크된 글은 단위 테스트의 목표를 다룬다. 단위 테스트는 버그를 찾는 것만이 아니라 소프트웨어 프로젝트가 지속적으로 성장할 수 있게 하는 데 목적이 있다는 관점이다. 테스트가 없으면 코드가 늘수록 변경할 때 무엇이 깨질지 몰라 개발 속도가 떨어지는데, 좋은 테스트는 회귀를 막아 이 속도를 유지하게 해 준다. 반대로 구현 세부 사항에 묶인 테스트는 리팩토링할 때마다 깨져 오히려 유지 비용이 되므로, 테스트 자체의 가치와 비용도 따져야 한다.

### Android IVI

IVI(In-Vehicle Infotainment)는 차량의 내비게이션, 미디어, 통화, 차량 정보 표시 등을 담당하는 시스템이다. 안드로이드 기반 IVI는 두 갈래로 나뉜다. Android Auto는 스마트폰에서 실행되는 앱 화면을 차량 디스플레이에 투사하는 방식이고, Android Automotive OS는 차량 헤드 유닛에서 안드로이드가 직접 실행되는 운영체제다. 후자는 차량 하드웨어와 HAL로 연결되어 공조 장치나 차량 상태에도 접근할 수 있다.

### Singed URLs and Signed Cookies

서명된 URL과 서명된 쿠키는 둘 다 만료 시간과 허용 조건을 담은 정책에 개인 키로 서명해서, CloudFront가 서명이 유효한 요청만 통과시키게 하는 기능이다. [AWS 문서](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-choosing-signed-urls-cookies.html)는 선택 기준을 이렇게 제시한다.

| 서명된 URL | 서명된 쿠키 |
| --- | --- |
| 설치 파일처럼 개별 파일 하나에 대한 접근을 제한할 때 | HLS 동영상의 모든 조각 파일이나 구독자 영역 전체처럼 여러 파일에 접근을 허용할 때 |
| 쿠키를 지원하지 않는 클라이언트를 쓸 때 | 기존 URL을 바꾸고 싶지 않을 때 |

서버는 사용자를 인증한 뒤 서명된 URL을 발급하거나 `Set-Cookie`로 서명된 쿠키를 내려 준다. 링크된 Java 예제 문서는 서명에 쓸 키 쌍과 URL 생성 코드를 다룬다.

- https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-choosing-signed-urls-cookies.html
- https://jayendrapatil.com/tag/signed-urls-vs-signed-cookies/
- https://liveroomlk.medium.com/cloudfront-signed-urls-cookies-and-s3-presigned-urls-be850c34f9ce
- https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-signed-cookies.html
- https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/CFPrivateDistJavaDevelopment.html

### AWS 요금 계산

요금 계산기에서 사용할 아키텍처 구성의 스펙을 상세히 입력하고 계산하면 비용이 산정된다.

#### Best Practices for Unit Testing

링크된 글들이 공통으로 권하는 원칙은 다음과 같다.

- 테스트 하나는 한 가지 동작만 검증하고, 이름에 무엇을 검증하는지 드러낸다.
- given-when-then(또는 arrange-act-assert) 구조로 준비, 실행, 검증을 나눈다.
- 테스트끼리 상태를 공유하지 않아 실행 순서와 무관하게 통과해야 한다.
- 구현 세부 사항이 아니라 관찰 가능한 결과를 검증한다.
- 스프링 컨텍스트가 필요 없는 로직은 컨텍스트 없이 테스트해서 빠르게 유지한다.

#### Mocking for Testing

의존 객체를 mock으로 바꾸는 방법은 두 가지다. Mockito의 `@Mock`과 `@InjectMocks`는 스프링 없이 순수 단위 테스트에서 쓰고, `@MockBean`은 스프링 컨텍스트에 등록된 빈을 mock으로 교체한다. `@MockBean`이 다른 테스트 클래스마다 다르게 쓰이면 컨텍스트 캐시를 재사용하지 못해 테스트가 느려진다. 인증이 필요한 컨트롤러는 Spring Security Test의 `@WithMockUser`로 가짜 사용자를 넣어 테스트한다.

#### Integration Testing

통합 테스트는 여러 구성 요소를 실제로 연결한 상태에서 함께 동작하는지 검증한다. Spring Boot에서는 `@SpringBootTest`로 컨텍스트 전체를 띄우고, `webEnvironment = RANDOM_PORT`로 실제 서버를 열어 `TestRestTemplate`이나 `WebTestClient`로 요청을 보낸다. DB는 내장 H2 대신 운영과 같은 DB를 Testcontainers로 띄우면 SQL 방언 차이로 인한 문제를 미리 잡을 수 있다. 느리므로 핵심 흐름 위주로 작성한다.
