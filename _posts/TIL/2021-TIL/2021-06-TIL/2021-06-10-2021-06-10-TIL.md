# 2021-06-10-TIL

## S3에 이미지 업로드 및 스프링 연동

이미지 파일은 DB나 애플리케이션 서버 디스크 대신 S3 같은 객체 저장소에 두고, DB에는 파일의 URL(또는 키)만 저장하는 구성이 일반적이다. 서버를 여러 대로 늘려도 파일 위치가 하나로 유지되고, 정적 파일 전송을 S3(또는 앞단의 CDN)가 맡는다. Spring에서는 컨트롤러가 `MultipartFile`로 파일을 받고, AWS SDK의 S3 클라이언트로 `putObject`를 호출해 업로드한 뒤 객체 URL을 돌려준다. 접근 키를 코드나 저장소에 넣지 말고 환경 변수나 IAM 역할로 주입해야 한다.

- https://leveloper.tistory.com/46

## ON DELETE CASCADE vs 비즈니스 로직상에서 순차적 삭제

성능 면에서는 ON DELETE CASCADE가 훨씬 우세하다. 하지만 안정성 및 디버깅의 용이성 같은 점을 고려해보면 비즈니스 로직 상에서 처리하는 것이 좀 더 낫다. DB 테이블에 CASCADE가 여기저기 걸려있으면 쿼리를 하나씩 추적하는것은 어렵다. 반면에, 비즈니스 로직 상에서 구현되어 있다면 디버깅을 보다 상세히 할 수 있다는 점에서 유리하다.

성능 차이가 나는 이유는 처리 위치에 있다. 외래 키의 `ON DELETE CASCADE`는 부모 행 하나를 지우는 문장 안에서 DB가 자식 행을 함께 지운다. 애플리케이션에서 지우면 자식들을 조회한 뒤 DELETE를 여러 번 보내야 한다. JPA의 `CascadeType.REMOVE`도 애플리케이션 쪽 처리라서, 자식 엔티티를 로딩해 한 건씩 삭제 쿼리를 보낸다. 반대로 DB 쪽 연쇄 삭제는 애플리케이션이 모르게 일어나므로, 영속성 컨텍스트에 남아 있는 엔티티와 DB 상태가 어긋날 수 있고 삭제 이벤트를 남기거나 감사 로그를 쓰기도 어렵다. 링크된 토론들도 이 두 관점(성능과 단순함 대 명시성과 통제)을 두고 의견이 나뉜다.

- [https://stackoverflow.com/questions/19997325/sql-on-delete-cascade-vs-delete-on-business-logic](https://stackoverflow.com/questions/19997325/sql-on-delete-cascade-vs-delete-on-business-logic)
- [https://dba.stackexchange.com/questions/254605/is-it-a-good-or-bad-idea-to-use-on-update-cascade-on-delete-cascade-for-foreig](https://dba.stackexchange.com/questions/254605/is-it-a-good-or-bad-idea-to-use-on-update-cascade-on-delete-cascade-for-foreig)

## Dirty Checking

save메소드로 엔티티를 저장하지 않더라도, 엔티티의 변화를 감지하여 자동으로 update쿼리가 수행되는 것

JPA는 엔티티를 영속성 컨텍스트에 처음 올릴 때 그 상태의 스냅샷을 보관한다. 트랜잭션이 커밋되면서 플러시가 일어날 때 현재 엔티티와 스냅샷을 비교하고, 바뀐 엔티티에 대해 UPDATE 문을 만들어 보낸다. 그래서 트랜잭션 안에서 조회한 엔티티의 필드만 바꿔도 반영된다. 조건이 있다. 영속 상태의 엔티티여야 하고(준영속, 비영속 엔티티는 대상이 아니다), 트랜잭션 안에서 바뀌어야 한다. Hibernate는 기본적으로 모든 컬럼을 UPDATE 문에 넣고, 바뀐 컬럼만 넣으려면 `@DynamicUpdate`를 쓴다.

## Jacoco

JaCoCo는 Java 코드 커버리지 도구다. 테스트를 실행할 때 바이트코드에 측정 코드를 넣어 어떤 라인과 분기가 실행됐는지 기록하고, HTML이나 XML 리포트를 만든다. 우아한형제들 글은 Gradle의 `jacoco` 플러그인으로 리포트를 만들고, `jacocoTestCoverageVerification`에 최소 커버리지 규칙을 걸어 기준에 못 미치면 빌드를 실패시키는 설정을 다룬다.

## Mock MVC

`MockMvc`는 실제 서버를 띄우지 않고 Spring MVC의 요청 처리 흐름을 테스트하는 도구다. `perform(get("/questions/1"))`로 요청을 만들고, `andExpect(status().isOk())`, `andExpect(jsonPath("$.title").value(...))`로 응답을 검증하며, `andDo(print())`로 요청과 응답 내용을 출력한다.

## AI 키워드: Scaling Vision Transformers

2021년 6월 Google 연구진이 "Scaling Vision Transformers" 논문을 arXiv에 올렸다. 언어 모델에서 연구된 스케일링 법칙이 ViT에서도 성립하는지 보기 위해 모델과 데이터 크기를 늘리고 줄이며 오류율, 데이터, 계산량의 관계를 분석했다. 그 과정에서 20억 파라미터 ViT를 학습해 ImageNet top-1 정확도 90.45%를 기록했다고 보고한다.
