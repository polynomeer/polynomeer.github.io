# 2021-06-03-TIL

## @RequiredArgsConstructor
- https://webdevtechblog.com/requiredargsconstructor-%EB%A5%BC-%EC%9D%B4%EC%9A%A9%ED%95%9C-%EC%9D%98%EC%A1%B4%EC%84%B1-%EC%A3%BC%EC%9E%85-dependency-injection-4f1b0ac33561

Lombok의 `@RequiredArgsConstructor`는 초기화되지 않은 `final` 필드와, 선언 시점에 초기화되지 않은 `@NonNull` 필드마다 파라미터를 하나씩 받는 생성자를 만든다([Lombok 문서](https://projectlombok.org/features/constructor)).

```java
@Service
@RequiredArgsConstructor
public class RoomService {
    private final RoomRepository roomRepository;
    private final ReservationRepository reservationRepository;
}
```

빈에 생성자가 하나뿐이면 그 생성자에 `@Autowired`를 붙이지 않아도 된다([Spring 문서](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/autowired.html)). Spring 팀도 생성자 주입을 권장한다. 객체를 불변으로 만들 수 있고, 필수 의존성이 `null`이 아님을 보장하며, 항상 완전히 초기화된 상태로 객체가 넘어가기 때문이다([Spring 문서](https://docs.spring.io/spring-framework/reference/core/beans/dependencies/factory-collaborators.html)). 같은 문서는 생성자 인자가 지나치게 많으면 클래스의 책임이 너무 많다는 신호라고도 적는다. Lombok이 생성자를 대신 써 주면 이 신호가 눈에 덜 띄므로, 필드 수가 늘어날 때는 한 번 의식해서 볼 필요가 있다.

## Spring Boot + MyBatis 에서 쿼리 로깅
- https://smallgiant.tistory.com/59
- http://jmlim.github.io/spring/2018/12/26/spring-boot-logback-sql-pretty/
- https://lee-mandu.tistory.com/352?category=715433
- https://congsong.tistory.com/23

MyBatis는 매퍼 네임스페이스(매퍼 인터페이스의 패키지와 이름)를 로거 이름으로 쓴다. [MyBatis 로깅 문서](https://mybatis.org/mybatis-3/logging.html)에 따르면 SQL 문은 DEBUG 레벨, 결과 행은 TRACE 레벨로 찍힌다. 그래서 Spring Boot에서는 매퍼 패키지의 로그 레벨만 올리면 된다.

```properties
logging.level.com.example.room.mapper=DEBUG
```

결과가 큰 쿼리에서는 TRACE를 켜면 로그가 넘치므로 SQL만 보고 싶을 때는 DEBUG에서 멈춘다. 값이 채워진 SQL을 보기 좋게 정렬해서 보고 싶다면 log4jdbc 같은 JDBC 프록시 드라이버를 쓰는 방법도 있다.

## 스프링에서 HTTP에 대한 테스트 코드를 작성하기
- https://itmore.tistory.com/entry/MockMvc-%EC%83%81%EC%84%B8%EC%84%A4%EB%AA%85

MockMvc는 서버를 띄우지 않고 Spring MVC를 테스트하는 도구다. 실제 `DispatcherServlet`을 호출하되 서블릿 API는 `spring-test`의 목(mock) 구현을 쓴다([Spring 문서](https://docs.spring.io/spring-framework/reference/testing/mockmvc/overview.html)). 컨트롤러를 직접 생성해서 메서드를 부르는 단위 테스트는 요청 매핑, 데이터 바인딩, 메시지 변환, 검증, `@ExceptionHandler`를 확인할 수 없는데, MockMvc는 이것까지 함께 검증한다.

```java
mockMvc.perform(get("/rooms").param("location", "서울"))
        .andExpect(status().isOk())
        .andExpect(jsonPath("$[0].location").value("서울"));
```

## Spring Boot and OAuth2
- https://daddyprogrammer.org/post/1754/spring-boot-oauth2-resourceserver/

OAuth 2.0에서 리소스 서버는 Bearer 토큰으로 보호되는 API를 가진 쪽이다. 인증과 권한 관리는 인가 서버에 맡기고, 리소스 서버는 요청에 담긴 토큰만 검증한다. Spring Security는 두 가지 토큰 형식을 지원한다. 서명된 JWT는 리소스 서버가 스스로 검증할 수 있고, 불투명(opaque) 토큰은 인가 서버에 물어봐야 검증할 수 있다([Spring Security 문서](https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/index.html)). 토큰이 없는 요청에는 `WWW-Authenticate: Bearer` 헤더로 응답한다.

## JPA Transactional and Proxy
- https://cobbybb.tistory.com/17
- https://mommoo.tistory.com/92
- https://www.baeldung.com/spring-jpa-soft-delete

`@Transactional`은 Spring이 빈을 프록시로 감싸고, 프록시가 메서드 호출 앞뒤에서 트랜잭션을 시작하고 끝내는 방식으로 동작한다. 그래서 프록시를 거치지 않는 호출에는 적용되지 않는다. [Spring 문서](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)는 같은 객체 안의 메서드가 다른 `@Transactional` 메서드를 부르는 자기 호출(self-invocation)은 실제 트랜잭션으로 이어지지 않는다고 명시한다.

```java
public void register(Room room) {
    save(room); // this.save()라서 프록시를 거치지 않는다
}

@Transactional
public void save(Room room) { ... }
```

해결 방법은 트랜잭션이 필요한 메서드를 다른 빈으로 옮기거나, 바깥 메서드에 `@Transactional`을 거는 것이다. 문서는 자기 호출까지 트랜잭션으로 감싸야 한다면 프록시 대신 바이트코드를 직접 엮는 AspectJ 모드를 쓰라고 안내한다.

마지막 링크는 soft delete를 다룬다. 행을 실제로 지우지 않고 `deleted` 같은 플래그만 바꾸는 방식이다. Hibernate에서는 `@SQLDelete`로 삭제 SQL을 `UPDATE`로 바꾸고([Hibernate Javadoc](https://docs.hibernate.org/orm/5.4/javadocs/org/hibernate/annotations/SQLDelete.html)), `@Where`로 조회할 때마다 지워지지 않은 행만 고르는 조건을 붙인다([Hibernate Javadoc](https://docs.hibernate.org/orm/5.4/javadocs/org/hibernate/annotations/Where.html)).
