## Spring Data JDBC - Aggregates

- https://spring.io/blog/2018/09/24/spring-data-jdbc-references-and-aggregates

애그리거트는 항상 일관된 상태여야 하는 객체 묶음이고, 바깥에서는 애그리거트 루트만 참조할 수 있다. Spring Data JDBC는 이 개념을 그대로 저장 규칙으로 쓴다.

- 애그리거트 안의 객체는 루트와 함께 저장되고, 루트를 지우면 함께 지워진다.
- 리포지토리는 애그리거트 루트마다 하나만 둔다.
- 다른 애그리거트는 객체가 아니라 id로 참조한다. 글에서 든 예처럼 책을 지운다고 저자가 지워지면 안 되므로 `Book`은 `Author` 객체 대신 저자 id를 가진다.

## Spring Data JDBC - one to many

- https://prog.world/introduction-to-spring-data-jdbc-baeldung/
- https://javabydeveloper.com/spring-data-jdbc-one-to-many-example/
- https://spring.io/blog/2018/09/24/spring-data-jdbc-references-and-aggregates
- https://www.baeldung.com/spring-data-annotations

애그리거트 루트가 컬렉션을 가지면 일대다 관계가 된다. [매핑 문서](https://docs.spring.io/spring-data/relational/reference/jdbc/mapping.html)에 따르면 자식 테이블에는 부모를 가리키는 외래 키 컬럼이 필요하다. `List`나 `Map`이면 순서나 키를 담을 컬럼이 하나 더 필요하고, 기본 이름은 `_KEY` 접미사가 붙는다. 컬럼 이름이 다르면 `@MappedCollection(idColumn = ..., keyColumn = ...)`으로 맞춘다.

```java
class Category {
    @Id
    Long id;

    @MappedCollection(idColumn = "CATEGORY_ID")
    Set<Item> items;
}
```

저장 방식은 JPA와 많이 다르다. [엔티티 저장 문서](https://docs.spring.io/spring-data/relational/reference/jdbc/entity-persistence.html)에 따르면 새 루트가 아닐 때는 참조하는 엔티티를 모두 지우고, 루트를 갱신한 뒤, 참조 엔티티를 다시 넣는다. 이전 상태를 추적하지 않기 때문이다. 자식 하나만 바꿔도 전체가 다시 쓰이므로, 자식이 많은 컬렉션을 애그리거트 안에 둘지는 따로 판단해야 한다.

## AI 키워드: Megatron-LM

NVIDIA가 2021년 4월 9일 arXiv에 대규모 언어 모델을 GPU 수천 개로 학습하는 방법을 다룬 Megatron-LM 논문을 올렸다. 텐서 병렬화, 파이프라인 병렬화, 데이터 병렬화를 조합해서, 파라미터 1조 개 모델을 GPU 3,072개로 학습하는 실험을 보고한다. 모델 하나가 GPU 한 장의 메모리에 들어가지 않을 때 어떻게 쪼개는지가 이 분야의 핵심 문제다.
