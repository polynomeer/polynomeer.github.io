## Service 계층은 꼭 필요한가

### Service in JPA

Spring Data JPA로 리포지토리를 만들면 컨트롤러에서 리포지토리를 바로 불러도 동작한다. 그런데도 Service 인터페이스와 구현 클래스를 따로 두는 이유가 궁금해서 Stack Overflow의 "Spring data jpa repo, why need interface service and service implementation" 질문과 Spring Data JPA 가이드, Spring Boot 기본 애너테이션 정리 글을 찾아봤다.

### What is service layer role in Spring Boot

Alam Khan의 글은 DAO(리포지토리)는 DB 연결만 맡도록 가볍게 두고, 서비스 계층은 DAO와 클라이언트 사이를 오가는 데이터에 비즈니스 로직을 적용하는 자리라고 설명한다. 서비스 계층을 두는 이유로는 관심사 분리, 클라이언트가 DB에 직접 닿지 못하게 하는 보안, 그리고 결합도 감소를 든다. 예를 들어 컨트롤러 메서드 50개가 DAO 메서드 20개를 직접 부르면 DAO가 바뀔 때 50곳을 고쳐야 하지만, 그 사이에 서비스 메서드 20개를 두면 20곳만 고치면 된다는 것이다.

아래 강의 메모의 "Service도 굳이 별도로 분리할 필요가 없다"는 말과 같이 보면, 로직이 리포지토리 호출을 그대로 넘기는 수준이라면 서비스 계층은 생략할 수 있고, 여러 리포지토리를 묶거나 트랜잭션 경계가 필요할 때 의미가 생긴다고 정리할 수 있다.

### redirect, forward, 그냥 리턴

- `redirect:/user` HTTP 302 요청 후 처리하고 이동, 주체는 브라우저
- `forward:user` Servlet 서버가 user 컨트롤러를 호출한다. -> 안티패턴이다.
- `return "user";`  controller -> model -> view

301은 캐싱이 된다. 우리가 필요한 것은 302이다. 주체는 항상 브라우저가 해준다!

MDN 문서도 301 Moved Permanently를 리소스가 `Location` 헤더의 URL로 영구히 옮겨졌다는 뜻으로 설명하고, 이 응답은 캐시될 수 있다. 브라우저가 301을 기억해 두면 다음 요청부터는 서버에 묻지 않고 바로 새 주소로 가므로, 폼 제출 후 목록으로 보내는 것처럼 매번 서버를 거쳐야 하는 이동에는 임시 이동인 302가 맞다.

setter가 없으면 컨트롤러에 값이 안 들어온다. getter가 없으면 view에 값을 못 전달한다. 롬복을 쓰면 알아서 getters and setters를 만들어줘버려서 돌아가는 원리를 잘 모르게 된다.

ModelAndView는 사용하지 않는 것이 낫다. 실제로 ModelAndView에 String을 추가해서 동작한다. 이는 구식적인 방법

## 미션2

PUT 메서드를 hidden 필드에 추가하니 405에러 메서드를 처리할 수 없다는 에러 페이지가 뜬다. 그래서 application.properties에

```
spring.mvc.hiddenmethod.filter.enabled=true
```

이와 같은 설정을 추가해주거나, 다른 방법은 시도해보았지만 실패했다.

HTML 폼은 GET과 POST만 보낼 수 있어서, Spring은 `_method`라는 hidden 파라미터를 읽어 요청 메서드를 PUT이나 DELETE로 바꿔 주는 `HiddenHttpMethodFilter`를 제공한다. Spring Boot 2.2 릴리스 노트에 따르면 이 필터는 본문에 파라미터가 있을 때 요청 본문을 일찍 소비하는 문제 때문에 2.2부터 기본으로 꺼졌고, `spring.mvc.hiddenmethod.filter.enabled=true`로 다시 켤 수 있다. 405가 난 이유가 이것이다.

### Entity의 디폴트 생성자 접근 제한

- Question 엔티티에서 값을 전달하지 못하는 에러 발생

  Question에서 생성자를 통해서 엔티티를 생성하도록 이미 생성자가 정의되어 있다. 그런데 public으로 Question 생성자를 정의했더니, 값을 넘겨주지 못하고 null로 생성된 것을 확인했다. 그래서 protected로 생성자의 접근제한을 낮추었더니 우선순위가 변경되어서 기존에 멤버필드를 초기화해주는 생성자가 정상적으로 호출되어서 값이 잘 들어갔다.

Jakarta Persistence 명세는 엔티티 클래스에 인자 없는 생성자가 있어야 하고, 그 생성자는 public이나 protected여야 한다고 정한다. Hibernate는 리플렉션으로 이 기본 생성자를 호출해 엔티티를 만들기 때문에, 기본 생성자가 없으면 `No default constructor for entity` 예외가 난다. 기본 생성자는 JPA를 위한 것이므로 protected로 두어 애플리케이션 코드에서 빈 객체를 만들지 못하게 하는 것이 흔한 방식이다.

### ResponseStatusException

*ResponseStatusException* usage has few benefits:

- Firstly, exceptions of the same type can be processed separately and different status codes can be set on the response, reducing tight coupling
- Secondly, it avoids the creation of unnecessary additional exception classes
- Finally, it provides more control over exception handling, as the exceptions can be created programmatically

위 목록은 Baeldung 글에서 옮겨 온 것이다. 같은 글에 따르면 `ResponseStatusException`은 Spring 5에서 추가된 `RuntimeException`으로, 예외 클래스에 `@ResponseStatus`를 붙이는 방식의 대안이다. `@ResponseStatus`는 그 예외 타입이 항상 같은 상태 코드와 메시지를 내도록 묶어 버리지만, `ResponseStatusException`은 던지는 자리에서 상태 코드와 사유를 정할 수 있다.

```java
throw new ResponseStatusException(HttpStatus.NOT_FOUND, "Actor Not Found");
```

### 엔티티에 메서드를 추가했더니 404

```java
public boolean matchPassword(User user) {
    return password.equals(user.password);
}
```

엔티티에 이것 하나 추가했다고 갑자기 404에러가 뜬다. 즉, 뷰를 받아오지 못한다. 무엇이 문제일까?

한 번씩 서버가 완전히 종료되지 않았거나 완전히 실행되지 않았을 때 접속하려고 하면 DB 데이터를 초기화하고 받아오지 못하는 것 같다.

## 개발자 언어 사전

- 안티 패턴: 코드 상에서 오류 날 가능성이 큰 문제가 있는 코드이다.
- 삽질: 보통 환경구축이나 디버깅 등 뭐가 안 되는지 잘 모를 때 그것을 알아내기 위해서 부단한 노력을 하는 것을 가리킨다.
