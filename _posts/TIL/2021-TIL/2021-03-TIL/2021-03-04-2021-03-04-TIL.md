서버 구성을 한 대에서 시작해 몇 대로 늘려 가는지 수업에서 들은 내용을 정리했다.

서버는 어떻게 생겼는가?

## SPA 아키텍처

User -> [Web Server -> WAS(Application Server) -> DB]

(Web Server: Apache, WAS: Tomcat)

- 정적인 컨텐츠 : HTML, CSS, JS, img, media -> Apache가 빠르다, 보안에 유리, 요새는 nginx를 사용(비동기 이벤트 기반), apache는 멀티스레드 기반, 트래픽 조절, 보안 역할
- 동적인 컨텐츠 : 글쓰기 등
- DB : 스프링 기본 H2, MySQL, Firebase

성능의 지표 : performance throughput 단위 시간당 동시 접속자 수

nginx의 구조는 AOSA(The Architecture of Open Source Applications) 2권의 nginx 장에서 확인했다. nginx는 동시 연결 1만 개를 다루는 C10K 문제를 풀기 위해 만들어졌고, 이벤트 기반이라 연결마다 프로세스나 스레드를 새로 띄우는 Apache 방식을 따르지 않는다. 대신 리눅스의 `epoll`, BSD의 `kqueue` 같은 운영체제의 이벤트 통지 메커니즘을 사용한다.

## 서버 4대 - 1: 배스천 서버

개발자는 ssh로 붙어서 관리, 배스천 서버를 따로 두어서 거기에 접속해서 나머지 서버에 접근한다.

web을 배스천으로 사용, 터널링을 통해서 여러 개를 거쳐서 가지만 바로 접근하는 것처럼 사용 가능

배스천 호스트(bastion host)는 공격을 견디도록 특별히 구성한 네트워크상의 컴퓨터로, 성채의 능보(bastion)에서 이름을 따왔다. 보통 하나의 애플리케이션이나 프로세스만 올리고 나머지 서비스는 제거하거나 제한한다.

## 서버 4대 - 2: 로드밸런서와 DB 분산

Web Was -> Web Was -> DB1 DB2 이 중간에 로드밸런서가 트래픽을 분산시켜준다.

cf) 쿠버네티스와는 관계가 없다. 이런 걸 통째로 관리해주는 개념

관계형 DB는 수평확장이 안 되어서 분산이 안 된다.

sol1) DB 파티셔닝 샤딩 -> 어렵다

sol2) Read Replica sync 비용이 커서 많아봐야 10대 정도

DB1은 읽기 전용으로 사용한다. (대부분은 읽기가 많다) DB2는 저장용

AWS RDS 문서는 읽기 전용 복제본(read replica)을 DB 인스턴스의 읽기 전용 사본으로 설명한다. 애플리케이션의 읽기 쿼리를 복제본으로 보내 기본 인스턴스의 부하를 줄이고, 읽기가 많은 워크로드에서 단일 인스턴스의 한계를 넘어 확장할 수 있다. 기본 인스턴스의 변경은 복제본에 비동기로 복사된다.
