### EOF

EOF(end-of-file)는 데이터 소스에서 더 읽을 데이터가 없는 상태를 말한다. 파일 끝에 특별한 문자가 저장되어 있는 것이 아니라 읽기 함수가 돌려주는 신호다. C 표준 라이브러리에서는 `getchar` 같은 함수가 음수인 `EOF` 매크로 값(보통 -1)을 반환해 이를 알리고, 자바의 `InputStream.read()`도 -1을 반환한다. 터미널 입력에서는 Unix 계열의 Ctrl+D처럼 정해진 키 입력을 EOF로 해석한다. JSON 파서가 "입력이 예상보다 일찍 끝났다"는 오류를 내는 것도 같은 개념으로, 빈 요청 본문이나 잘린 JSON을 읽을 때 생긴다.

- https://www.computerhope.com/jargon/e/eof.htm

### @JsonIgnoreProperties

Jackson 애너테이션으로, 직렬화할 때 특정 프로퍼티를 빼거나 역직렬화할 때 특정 JSON 프로퍼티를 무시한다. `@JsonIgnoreProperties({"internalId", "secretKey"})`처럼 이름을 나열하거나, `@JsonIgnoreProperties(ignoreUnknown = true)`로 클래스에 대응하는 setter나 생성자가 없는 모든 프로퍼티를 예외 없이 무시하게 할 수 있다. Javadoc에 따르면 `ignoreUnknown`은 역직렬화에만 영향을 준다. 외부 API 응답처럼 필드가 늘어날 수 있는 JSON을 받을 때 `UnrecognizedPropertyException`을 피하려고 쓴다. 전역으로는 `ObjectMapper`의 `FAIL_ON_UNKNOWN_PROPERTIES`를 끄는 방법도 있다.

### Assertion Frameworks: AssertJ vs JUnit

JUnit의 `assertEquals(expected, actual)`는 인자 순서를 헷갈리기 쉽고, 검증 종류마다 다른 정적 메서드를 찾아야 한다. AssertJ는 `assertThat(actual).isEqualTo(expected)`처럼 실제 값에서 출발하는 메서드 체인이라 IDE 자동완성으로 그 타입에 맞는 검증을 고를 수 있다. AssertJ는 JUnit 단언문을 AssertJ로 바꾸는 변환 스크립트도 제공하고, 두 방식이 한 프로젝트에 공존해도 된다고 안내한다. Google의 Truth도 비슷한 체인 방식인데, Truth 문서는 AssertJ가 없던 시절에 시작했기 때문에 따로 만들었다고 설명하고, Hamcrest는 매처 조합이 유연한 대신 제네릭이 복잡하고 실패 메시지가 읽기 어렵다고 비교한다.

### Pure Functions in Java

### DTO Inner Class

Oracle Java Tutorial의 용어로 static이 아닌 중첩 클래스는 inner class, static으로 선언한 것은 static nested class다. inner class는 바깥 클래스 인스턴스에 묶여 있어서 바깥 인스턴스 없이 만들 수 없고, 바깥 객체의 참조를 숨은 필드로 가진다. 그래서 요청과 응답 DTO를 한 클래스 안에 모을 때는 static nested class로 선언해야 Jackson이 바깥 인스턴스 없이 생성할 수 있다. 하나의 DTO를 여러 요청과 응답에 재사용할지, 용도마다 따로 둘지는 Stack Overflow 질문처럼 명시성과 클래스 개수 사이의 절충이다.

### @ControllerAdvice vs @RestControllerAdvice

`@RestControllerAdvice`는 Javadoc 설명대로 `@ControllerAdvice`와 `@ResponseBody`를 합친 단축 애너테이션이다. `@RestController`가 `@Controller`와 `@ResponseBody`의 조합인 것과 같은 관계다. 따라서 `@RestControllerAdvice` 안의 `@ExceptionHandler`가 반환한 객체는 뷰 이름이 아니라 응답 본문으로 직렬화된다. REST API라면 `@RestControllerAdvice`를 쓰면 된다.

### @ExceptionHandler and @ControllerAdvice

`@ExceptionHandler`는 처리할 예외 타입을 지정한 메서드이고, 컨트롤러 안에 두면 그 컨트롤러의 예외만 처리한다. `@ControllerAdvice` 클래스에 두면 여러 컨트롤러에 공통으로 적용된다. 컨트롤러마다 같은 핸들러를 반복하지 않아도 되고 예외 처리 정책을 한곳에서 관리할 수 있다는 것이 `@ControllerAdvice`의 장점이다. 컨트롤러 안의 핸들러가 전역 핸들러보다 먼저 적용된다.

### Dynamic vs Static vs SPA

Academind 글은 웹사이트를 HTML이 만들어지는 위치로 나눈다.

- Dynamic: 요청마다 서버가 서버 사이드 언어와 템플릿 엔진으로 HTML을 만든다. 사용자별 데이터를 담기 쉽다.
- SPA: 서버는 미리 만든 HTML 한 장만 주고, 그 안의 JavaScript가 브라우저에서 화면을 바꾼다. 데이터는 API로 받아 온다.
- Static: 정적 사이트 생성기로 미리 만든 HTML 파일을 그대로 서빙한다. 빠르고 호스팅이 싸지만 요청마다 다른 내용을 만들 수는 없다.

- https://academind.com/tutorials/dynamic-vs-static-vs-spa
- https://betterprogramming.pub/web-development-in-2021-dynamic-vs-static-vs-single-page-architecture-399d0c3defe6

### @Async in Spring

`@EnableAsync`를 켜고 메서드에 `@Async`를 붙이면 호출이 별도 스레드에서 실행된다. 반환값이 필요하면 `Future`나 `CompletableFuture`로 받는다. `@Async`가 동작하지 않는 흔한 이유는 프록시 방식이기 때문이다. Spring 문서는 기본 프록시 모드에서는 프록시를 거치는 호출만 가로챌 수 있고, 같은 클래스 안의 내부 호출은 가로챌 수 없다고 설명한다. 그래서 같은 빈 안에서 `this.asyncMethod()`로 부르면 그냥 동기로 실행된다. `@PostConstruct` 같은 생명주기 콜백과도 함께 쓸 수 없다.

### Spring Data JPA and R2DBC

JPA는 JDBC 위에서 동작하는 블로킹 API라서 WebFlux 같은 리액티브 스택에서 쓰면 이벤트 루프 스레드를 막는다. Stack Overflow 질문 제목처럼 JPA는 리액티브 저장소를 지원하지 않는다. Spring Data는 2016년 글에서 `ReactiveCrudRepository`처럼 리액티브 타입을 반환하는 저장소 모델을 소개했고, 관계형 DB에서는 리액티브 드라이버 규격인 R2DBC가 이 역할을 맡는다. 한 애플리케이션에서 JPA와 R2DBC를 함께 쓰는 것도 가능하지만, 트랜잭션 매니저와 설정이 둘로 나뉘는 점을 감수해야 한다. Kotlin에서는 코루틴으로 리액티브 코드를 동기 코드처럼 쓸 수 있다.

### Tomcat vs Jetty

둘 다 자바 서블릿 컨테이너다. Tomcat은 Apache 라이선스의 Apache 프로젝트로 Jakarta Servlet, Jakarta Server Pages 등 핵심 명세를 구현하고, Spring Boot가 기본 내장 서버로 쓴다. Jetty는 Eclipse 재단 프로젝트로, 비교 글은 부팅 시간과 메모리 사용량을 줄이는 데 우선순위를 두고 다른 시스템에 내장하기 쉽다는 점을 강점으로 든다. Spring Boot에서는 `spring-boot-starter-web`에서 Tomcat을 제외하고 `spring-boot-starter-jetty`를 추가해 바꿀 수 있다.

- https://cloudinfrastructureservices.co.uk/tomcat-vs-jetty-whats-the-difference/
