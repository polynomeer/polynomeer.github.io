### Checked Exception vs Unchecked Exception

자바 예외는 컴파일러가 처리를 강제하는지에 따라 둘로 나뉜다. checked exception은 `Exception`을 상속하지만 `RuntimeException` 계열은 아닌 예외로, 메서드 안에서 `catch`로 잡거나 `throws`로 선언해야 컴파일된다. unchecked exception은 `RuntimeException`, `Error`와 그 하위 클래스이고, 이 "잡거나 선언하라(catch or specify)"는 요구에서 빠진다.

Oracle Java Tutorial은 메서드가 던질 수 있는 checked exception을 파라미터, 반환값과 같은 공개 인터페이스의 일부로 본다. 반면 0으로 나누기, null 참조 접근, 잘못된 인덱스 같은 런타임 예외는 프로그래밍 오류에서 생기므로 호출자가 복구하리라 기대하기 어렵고, 그래서 선언을 강제하지 않는다. 튜토리얼이 내리는 기준은 간단하다. 호출자가 복구할 수 있으면 checked, 할 수 없으면 unchecked로 만든다. 예외 선언이 귀찮다는 이유만으로 `RuntimeException`을 상속하지 말라는 경고도 같이 붙어 있다.

스프링을 쓸 때는 한 가지를 더 기억해야 한다. `@Transactional`은 기본적으로 `RuntimeException`과 `Error`에서만 롤백하고, checked exception이 던져지면 롤백하지 않는다. checked exception에서도 롤백하려면 `rollbackFor` 같은 롤백 규칙을 지정해야 한다.

### Custom Exception vs Runtime Exception

사용자 정의 예외를 만들지, `IllegalArgumentException`, `IllegalStateException` 같은 표준 예외를 그대로 쓸지에 대한 논쟁이다. Tecoble 글은 양쪽 주장을 정리한다. 표준 예외 쪽은 메시지만으로도 의미가 전달되고, 익숙한 예외가 더 읽기 쉬우며, 예외 클래스가 지나치게 늘어나면 관리 비용이 생긴다고 본다. 사용자 정의 예외 쪽은 `PostNotFoundException`처럼 이름만으로 상황을 알 수 있고, 생성자에서 크기나 인덱스 같은 상세 정보를 일관되게 담을 수 있으며, 같은 예외가 여러 곳에서 던져질 때 관련 정보를 한 클래스에 모을 수 있다는 점을 든다.

.NET 문서의 예외 모범 사례도 비슷한 기준을 둔다. 미리 정의된 예외가 맞지 않을 때만 새 예외 클래스를 도입하라는 것이다. 스프링 애플리케이션에서는 사용자 정의 예외를 보통 `RuntimeException` 하위로 만들고, 에러 코드를 필드로 넣어 전역 핸들러에서 한 번에 응답으로 바꾸는 경우가 많다.

### Exception Handling in Spring

스프링 MVC에서 컨트롤러 밖으로 나간 예외를 HTTP 응답으로 바꾸는 방법은 크게 셋이다. Spring 블로그의 "Exception Handling in Spring MVC" 글이 이를 정리한다. 직접 만든 예외 클래스에 `@ResponseStatus`를 붙여 상태 코드를 정하거나, 컨트롤러 안에 `@ExceptionHandler` 메서드를 두어 같은 컨트롤러에서 난 예외를 처리하거나, `@ControllerAdvice` 클래스에 핸들러를 모아 전역으로 처리한다. 그 아래에는 이 모든 것을 구현하는 `HandlerExceptionResolver`가 있다. 처리되지 않은 예외는 기본적으로 500 응답이 된다.

### Request Parameter in Spring

요청 파라미터가 많을 때 `@RequestParam`을 여러 개 나열하는 대신 모델 클래스 하나로 받는 방법이다. 스프링 문서에 따르면 `@ModelAttribute`는 생략할 수 있고, 단순 값 타입이 아니면서 다른 리졸버가 처리하지 않는 파라미터는 기본적으로 모델 속성으로 취급된다. 이때 객체는 생성자 바인딩이나 setter(프로퍼티) 바인딩으로 채워지고, 바인딩 오류가 나면 기본적으로 `MethodArgumentNotValidException`이 발생한다.

### Jib vs Dockerfile

Jib은 Google이 만든 오픈소스 컨테이너 이미지 빌더로, Maven과 Gradle 플러그인 형태로 동작한다. Google Cloud 블로그의 비교 글에 따르면 Jib은 의존성, 리소스, 컴파일된 애플리케이션을 별도 레이어로 나눠서 코드만 바뀌면 마지막 레이어만 다시 올리면 되고, 이미지를 외부 레지스트리에 바로 올린다면 로컬에 Docker가 없어도 빌드할 수 있다. Dockerfile은 어떤 언어든 쓸 수 있고 모든 단계를 직접 통제할 수 있는 대신, 레이어 구성과 캐시 최적화를 스스로 챙겨야 한다. 같은 글은 Buildpacks도 함께 비교하는데, 설정 없이 동작하지만 이미지가 크고 레이어가 최적이 아니라고 평가한다.

Google Cloud의 한국어 Jib 시작 가이드 링크는 지금은 404를 반환한다.

### FFmpeg Wrapper Library in Java

자바에서 FFmpeg를 쓰는 가장 흔한 방법은 설치된 `ffmpeg` 실행 파일을 프로세스로 호출하는 것이다. `bramp/ffmpeg-cli-wrapper`는 이 방식을 감싼 라이브러리로, `ffmpeg`와 `ffprobe` 경로를 지정하고 빌더 API로 명령줄 옵션을 조립한다. 결국 CLI를 실행하는 구조이므로 서버에 FFmpeg 바이너리가 설치되어 있어야 한다. 함께 저장한 `jibbex/jib-FFmpeg`는 이름과 달리 자바 라이브러리가 아니라 Node.js와 Electron으로 만든 FFmpeg GUI이고, 2022년에 보관(archive) 처리되었다.
