## Today I Learned

### Package by Layer vs Package by Feature

패키지를 나누는 두 가지 기준이다. package by layer는 `controller`, `service`, `repository`처럼 기술 계층별로 묶고, package by feature는 `order`, `member`처럼 기능(도메인)별로 묶은 뒤 그 안에 계층을 둔다. 계층별 구조는 처음 보기에 익숙하지만 기능 하나를 고치려면 여러 패키지를 오가야 하고, 클래스가 거의 다 `public`이 되어 패키지가 경계 역할을 못 한다. 기능별 구조는 관련 코드가 한곳에 모이고, 기능 밖으로 공개할 것만 `public`으로 두어 접근을 좁힐 수 있다.

### Multi Module Monolithic

하나의 저장소, 하나의 빌드 안에서 코드를 여러 모듈로 나누는 구조다. Gradle에서는 `settings.gradle`에 `include`로 하위 프로젝트를 등록하고, 다른 모듈을 쓰려면 `implementation(project(":모듈명"))`처럼 프로젝트 의존성을 선언한다. Spring 가이드 "Creating a Multi Module Project"는 실행 가능한 애플리케이션 모듈과, 애플리케이션이 아닌 라이브러리 jar 모듈을 나누는 가장 기본적인 예제를 보여 준다.

나누는 이유는 의존 방향을 빌드 수준에서 강제하고, API 서버, 배치, 어드민처럼 따로 배포하는 애플리케이션이 도메인 코드를 공유하게 하기 위해서다. 우아한형제들 기술블로그의 "멀티 모듈 설계 이야기"는 반대로 흔한 실패를 짚는다. 공통 코드를 `common` 모듈 하나에 몰아 넣으면 모든 애플리케이션이 그 모듈에 의존하게 되고, 수정 영향 범위가 시스템 전체로 퍼지며, 웹, JPA, Redis 같은 의존성이 필요 없는 모듈까지 끌려 들어간다는 것이다. 모듈은 역할과 의존성 기준으로 나누고, 하위 모듈의 공개 범위를 엄격히 관리해야 한다는 결론이다. Pulkit Gupta의 글은 이렇게 모듈로 나눈 모놀리스를 이후 마이크로서비스로 쪼갤 때 챙길 항목들을 정리한다.

### Hexagonal Architecture

Alistair Cockburn이 제안한 Ports and Adapters 패턴의 다른 이름이다. 그가 밝힌 의도는 애플리케이션이 사용자, 다른 프로그램, 자동화 테스트, 배치 스크립트 중 무엇에 의해서든 똑같이 구동될 수 있고, 실제 운영 장치나 데이터베이스와 떨어진 상태로 개발하고 테스트할 수 있게 하는 것이다. 애플리케이션 코어는 포트(인터페이스)만 정의하고, 웹 컨트롤러나 JPA 저장소 같은 기술 세부 사항은 그 포트에 끼우는 어댑터로 바깥에 둔다.

### DTO in Inner Static Class

요청과 응답마다 DTO 클래스를 따로 만들면 파일이 금방 많아진다. 그래서 `MemberDto.Request`, `MemberDto.Response`처럼 관련 DTO를 한 클래스 안의 static nested class로 모으는 방식이 쓰인다. 참고한 글 중 하나는 도메인 클래스 안에 DTO를 넣는 예까지 보여 주지만, 그러면 도메인이 표현 계층의 형식을 알게 되므로 별도 DTO 클래스 안에 모으는 편이 의존 방향상 깔끔하다. `static`이어야 바깥 클래스 인스턴스 없이 생성할 수 있고, Jackson 같은 라이브러리가 역직렬화할 때도 문제가 없다.

### DTO

Martin Fowler의 정의로 DTO(Data Transfer Object)는 메서드 호출 횟수를 줄이기 위해 프로세스 사이에서 데이터를 실어 나르는 객체다. 원격 호출은 비싸니 한 번에 많은 데이터를 담아 보내자는 것이 출발점이고, 직렬화 방식을 DTO 안에 가둔다는 장점도 있다. VO(Value Object)는 다른 개념이다. 식별자가 아니라 값으로 동등성을 판단하는 객체이고, Fowler는 별칭 문제를 피하려면 값 객체를 불변으로 만들라고 한다. Tecoble 글은 둘이 혼동되는 이유로 『Core J2EE Patterns』 초판이 데이터 전송 객체를 VO라고 불렀다가 2판에서 TO로 고친 일을 든다.

### Pagination in JPA

Spring Data JPA의 `JpaRepository`는 `PagingAndSortingRepository`를 상속하므로, 저장소 메서드가 `Pageable`을 받고 `Page<T>`를 돌려주게 하면 페이지 번호, 크기, 정렬이 쿼리에 반영된다. `Page`는 전체 개수를 함께 알려 주기 때문에 count 쿼리가 추가로 실행된다는 점을 알아 둔다.

### Java Executable

`java.lang.reflect.Executable`은 Java 8에서 생긴 추상 클래스로, `Method`와 `Constructor`의 공통 기능(파라미터 타입, 예외 타입, 애너테이션 조회 등)을 모은 상위 클래스다. 리플렉션 코드에서 메서드와 생성자를 같은 방식으로 다룰 때 쓴다.

- https://docs.oracle.com/javase/8/docs/api/java/lang/reflect/Executable.html

### Module Access Modifier

Java 9 모듈 시스템에 "모듈 안에서만 보이는" 접근 제어자가 있는지에 대한 질문이다. 답은 없다는 것이다. 모듈의 공개 범위는 `module-info.java`의 `exports`로 패키지 단위로만 정해진다. 타입이 `public`이어도 그 패키지를 export하지 않으면 모듈 밖에서 접근할 수 없지만, 메서드나 필드 하나만 모듈 범위로 숨기는 수단은 없다.

### How to Check Date Overlap in SQL

두 기간 A, B가 겹치는지는 "겹치지 않는 경우"를 뒤집으면 간단해진다. A가 B보다 완전히 앞이거나(`EndA < StartB`) 완전히 뒤면(`StartA > EndB`) 겹치지 않으므로, 겹치는 조건은 `StartA <= EndB AND EndA >= StartB`다. 경계가 맞닿는 경우를 겹침으로 볼지에 따라 `<=`와 `<`를 고른다.

```sql
SELECT *
FROM reservation r
WHERE r.start_date <= :end_date
  AND r.end_date >= :start_date;
```

### QueryDSL vs JOOQ

둘 다 자바 코드로 타입 안전한 쿼리를 쓰게 해 주지만 출발점이 다르다. QueryDSL은 JPA 엔티티에서 `Q` 클래스를 생성해 그 경로로 쿼리를 쓰고, jOOQ는 이미 있는 DB 스키마에서 자바 코드를 생성해 SQL에 가까운 DSL로 쿼리를 쓴다. 참고한 글은 jOOQ가 MySQL, MariaDB 같은 오픈소스 DB에는 무료이고 상용 DB에는 유료 에디션이 필요하다고 정리한다.

- https://mycup.tistory.com/333

### MySQL Count vs Exists

"조건에 맞는 행이 하나라도 있는가"만 알고 싶을 때 `COUNT(*)`를 쓰면 안 되는 이유다. jOOQ 블로그의 설명처럼 `COUNT(*)`는 정확한 행 수를 구해야 하므로 끝까지 세지만, `EXISTS`는 첫 번째 일치하는 행을 찾는 즉시 멈출 수 있다. MySQL 문서에 따르면 `EXISTS` 서브쿼리의 `SELECT` 목록은 무시되므로 `SELECT *`든 `SELECT 1`이든 차이가 없다.

- https://www.itprotoday.com/sql-server/exists-vs-count
- https://dev.mysql.com/doc/refman/5.7/en/exists-and-not-exists-subqueries.html
