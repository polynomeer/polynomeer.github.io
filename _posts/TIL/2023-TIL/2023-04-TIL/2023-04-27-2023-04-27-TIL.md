### Sealed Class in Java

Java 15에서 sealed 클래스의 개념을 소개하였다. Java sealed 클래스 및 인터페이스는 해당 클래스와 인터페이스로부터 extend 또는 implement 하는 것을 제한한다.

다시 말해, sealed 클래스나 인터페이스는 아무나 상속하거나 구현할 수 없고, 직접 허용한 클래스만 하위 타입이 될 수 있다. 이는 클래스나 인터페이스로 하여금 서브타입을 좀 더 제어할 수 있게 해준다.

정확한 이력은 JEP 409에 나와 있다. sealed 클래스는 JEP 360으로 JDK 15에 프리뷰 기능으로 처음 들어왔고, JEP 397로 JDK 16에서 한 번 더 프리뷰를 거친 뒤, JDK 17에서 정식 기능이 됐다([JEP 409: Sealed Classes](https://openjdk.org/jeps/409)). 그러니 프리뷰 옵션 없이 쓰려면 Java 17 이상이 필요하다.

허용할 하위 클래스는 `permits` 절로 적는다. 그리고 허용된 하위 클래스는 반드시 `final`, `sealed`, `non-sealed` 중 하나를 선언해서, 계층을 거기서 닫을지, 다시 제한할지, 열어 둘지를 밝혀야 한다.

```java
sealed interface Shape permits Circle, Square, Rectangle {}

final class Circle implements Shape { double radius; }
final class Square implements Shape { double side; }
non-sealed class Rectangle implements Shape { double w, h; }
```

왜 필요한가. 일반 인터페이스는 누구나 구현할 수 있어서, `Shape`를 받는 코드가 가능한 모든 경우를 알 수 없다. sealed로 하위 타입을 닫아 두면 "도형은 이 세 가지뿐"이라는 도메인 지식이 타입에 드러난다. 반대로 `final`은 상속을 아예 막아서 "정해진 몇 가지 중 하나"라는 계층 자체를 만들 수 없다. sealed는 완전히 열린 상속과 완전히 닫힌 `final` 사이의 선택지다.

Kotlin에도 같은 개념이 있다. Kotlin 문서는 sealed 클래스의 모든 직접 하위 클래스가 컴파일 시점에 알려져 있다고 설명하고, 하위 클래스는 같은 모듈과 같은 패키지 안에 있어야 한다. 덕분에 `when` 식에서 모든 하위 타입을 다루면 `else` 분기가 필요 없다([Kotlin: Sealed classes and interfaces](https://kotlinlang.org/docs/sealed-classes.html)).

```kotlin
sealed interface Result
data class Success(val data: String) : Result
data class Failure(val error: Throwable) : Result

fun render(r: Result) = when (r) {
    is Success -> r.data
    is Failure -> "error: ${r.error.message}"
}
```
