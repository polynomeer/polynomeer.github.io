### Go Module

모듈은 함께 버전이 매겨지는 패키지의 묶음이다. 루트의 `go.mod`에 모듈 경로, Go 버전, 의존성(`require`)을 적고, `go.sum`에는 내려받은 의존성의 체크섬이 기록되어 빌드 재현성과 무결성을 보장한다. 자주 쓰는 명령은 다음과 같다.

```sh
go mod init example.com/hello   # go.mod 생성
go get example.com/pkg@v1.2.3   # 의존성 추가 또는 버전 변경
go mod tidy                     # 쓰지 않는 의존성 제거, 누락된 의존성 추가
```

Go 모듈은 의존성 버전을 고를 때 Minimal Version Selection을 사용한다. 요구된 버전들 중 조건을 만족하는 가장 낮은 버전을 고르기 때문에, 새 버전이 나왔다고 빌드 결과가 저절로 바뀌지 않는다.

### Go Generics

Go 1.18에서 타입 파라미터가 도입되었다. Go 블로그의 When To Use Generics는 기준을 이렇게 정리한다. 슬라이스, 맵, 채널처럼 언어가 제공하는 컨테이너를 다루는 함수나 연결 리스트 같은 범용 자료구조에는 타입 파라미터가 맞다. 반대로 값에 대해 메서드만 호출하면 되는 경우에는 인터페이스를 쓰라고 권한다. 같은 코드를 타입만 바꿔 여러 번 쓰고 있다면 그때 타입 파라미터를 고려하라는 것이 핵심이다.

`interface{}`(Go 1.18부터 `any`)는 어떤 값이든 담을 수 있지만, 꺼낼 때 타입 단언이 필요하고 잘못된 타입은 런타임에야 드러난다. 타입 파라미터는 같은 유연성을 컴파일 타임 타입 검사와 함께 제공한다.

```go
func Map[T, U any](s []T, f func(T) U) []U {
    r := make([]U, 0, len(s))
    for _, v := range s {
        r = append(r, f(v))
    }
    return r
}
```

### Go Interfaces

Go의 인터페이스는 암묵적으로 구현된다. Java처럼 `implements`를 선언하지 않고, 인터페이스가 요구하는 메서드를 모두 가진 타입이면 그 인터페이스를 만족한다. 그래서 인터페이스는 사용하는 쪽에서 필요한 만큼 작게 정의하는 경우가 많다.

### Go Struct and Interface Embedding

Go에는 상속이 없고 임베딩으로 조합한다. 구조체에 다른 타입을 필드 이름 없이 넣으면 그 타입의 필드와 메서드가 바깥 구조체로 승격(promote)되어 직접 호출할 수 있다. 인터페이스에 인터페이스를 임베딩하면 메서드 집합이 합쳐진다(`io.ReadWriter`가 `io.Reader`와 `io.Writer`를 임베딩하는 식). 구조체에 인터페이스를 임베딩하면 그 구조체는 인터페이스를 만족하지만, 임베딩된 값이 nil인 상태에서 직접 구현하지 않은 메서드를 호출하면 panic이 난다는 점을 Eli Bendersky의 글이 짚는다.

- https://ankur-a22.medium.com/struct-and-interface-embedding-f0da8517fa8a

### Go Method Receiver: Value Receiver vs Pointer Receiver

메서드는 리시버를 가진 함수다. 값 리시버(`func (c Counter) Get()`)는 호출 시 리시버의 복사본을 받으므로 메서드 안에서 필드를 바꿔도 원본에 반영되지 않는다. 포인터 리시버(`func (c *Counter) Inc()`)는 원본을 가리키므로 상태를 바꿀 수 있고 큰 구조체의 복사 비용도 피한다.

명세상 타입 `T`의 메서드 집합에는 값 리시버 메서드만, `*T`의 메서드 집합에는 둘 다 포함된다. 그래서 포인터 리시버 메서드로 인터페이스를 구현했다면 `T` 값은 그 인터페이스를 만족하지 않는다. Go FAQ는 한 타입의 메서드가 일부라도 포인터 리시버라면 일관성을 위해 전부 포인터 리시버로 맞추라고 권한다.

### Go Generics vs Interfaces

인터페이스 값은 런타임에 동적 타입 정보와 데이터를 함께 들고 다니며 메서드 호출이 간접 호출로 이루어진다. 제네릭은 컴파일 시점에 타입이 정해지므로 타입 안전성이 더 강하다. 다만 Go의 제네릭 구현은 타입마다 코드를 전부 따로 만들지 않고, 메모리 모양(GC shape)이 같은 타입끼리 코드를 공유하면서 딕셔너리로 타입 정보를 넘기는 방식이라 항상 인터페이스보다 빠른 것은 아니다.

### Go Arrays vs Slices

배열은 길이가 타입의 일부(`[4]int`와 `[5]int`는 다른 타입)이고, 대입하거나 함수에 넘기면 전체가 복사되는 값이다. 슬라이스는 내부 배열을 가리키는 포인터, 길이, 용량으로 이루어진 작은 구조이고 실무에서는 대부분 슬라이스를 쓴다.

### Go Slices Copy

슬라이스를 함수에 넘기면 슬라이스 헤더(포인터, 길이, 용량)가 값으로 복사된다. 헤더는 복사본이지만 같은 내부 배열을 가리키므로 함수 안에서 `s[0] = x`로 바꾼 요소는 호출한 쪽에서도 보인다. 반면 `append`가 용량을 넘겨 새 배열을 할당하면 그 뒤의 변경은 원본과 분리된다. 독립된 사본이 필요하면 내장 함수 `copy`를 쓴다. `copy`는 두 슬라이스 길이 중 작은 쪽만큼만 복사하므로 대상 슬라이스를 먼저 같은 길이로 만들어야 한다.

```go
dst := make([]int, len(src))
copy(dst, src)
```

### What is Panic in Golang

`panic`은 정상 흐름을 멈추고 현재 함수의 지연 함수(`defer`)를 실행한 뒤 호출 스택을 거슬러 올라가는 동작이다. 지연 함수 안에서 `recover`를 호출하면 panic을 멈추고 정상 흐름으로 돌아올 수 있으며, `recover`는 지연 함수 안에서만 의미가 있다. Go에서 panic은 프로그래밍 오류처럼 복구할 수 없는 상황에 쓰고, 예상 가능한 실패는 에러 값으로 다룬다.

```go
func safeDiv(a, b int) (q int, err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("recovered: %v", r)
        }
    }()
    return a / b, nil
}
```

### Error Handling in Go

Go의 에러는 `Error() string` 메서드를 가진 `error` 인터페이스 값이다. 함수는 결과와 함께 에러를 반환하고, 호출자는 `if err != nil`로 확인한다. Rob Pike의 Errors are values는 에러가 예외가 아니라 일반 값이므로, 반복되는 검사를 타입이나 메서드로 묶어 프로그래밍적으로 다룰 수 있다고 강조한다. Go 1.13부터는 `fmt.Errorf`의 `%w`로 에러를 감싸고 `errors.Is`, `errors.As`로 감싼 체인 안의 에러를 비교하거나 꺼낼 수 있다. 에러를 `==`로 비교할 때는 같은 값(sentinel error)이어야 같다고 판정되므로 비교 방식에 주의해야 한다.
